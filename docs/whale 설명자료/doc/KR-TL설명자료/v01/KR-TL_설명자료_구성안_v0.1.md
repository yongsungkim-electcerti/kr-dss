| 청중 | 웨일 기획·개발 혼합 (사전 공유 성격, 킥오프 기술리뷰 이전 단계) |

## 0. 이 자료의 서술 원칙

**대전제 — 웨일팀이 스스로 판단할 수 있게 만든다.**

이 자료는 "이렇게 만들어 주십시오"가 아니라 "이 구조에서는 이런 판단이 필요합니다"를 전달한다. 결론을 미리 채워 놓으면 웨일팀은 검토가 아니라 수용 여부만 답하게 되고, 그때부터 설계 논의가 아니라 범위 협상이 된다. 실증에서 필요한 것은 그 반대다.

구체적으로 다음 네 가지를 지킨다.

1. **판단 지점을 열어 둔다.** 각 장의 마지막에 "웨일팀이 정할 것"을 한 줄로 남기고, 그 자리에 우리 안(案)을 채우지 않는다. 안을 제시할 때는 "현재 초안" 또는 "검토안"이라고 명시해 확정과 구분한다.
2. **선택지와 트레이드오프를 같이 준다.** 방식이 둘 이상인 지점은 선택지를 나란히 놓고 각각의 대가를 적는다. 하나만 적으면 판단할 재료가 없어진다.
3. **제약의 출처를 밝힌다.** 규격상 반드시 그래야 하는 것, 제도상 그런 것, 우리가 그렇게 하자고 제안하는 것을 구분한다. 세 가지를 섞으면 조정 가능한 여지가 보이지 않는다.
4. **기능 단위로 말한다.** 제도 배경은 필요한 만큼만 깔고, 목록이 실제로 제공하는 기능 다섯 가지를 축으로 삼는다.

발표할 때도 같은 원칙으로 — 각 장에서 우리가 이미 정해 둔 것처럼 들리는 문장은 "현재 이렇게 보고 있는데 어떻게 보시는지"로 바꿔 말한다.

각 장은 **거버닝 메시지 → 본문 → 열어 둘 질문 → 발표 노트** 순으로 구성한다. "열어 둘 질문"은 슬라이드 하단에 실제로 인쇄해 웨일팀이 가져갈 수 있게 한다.

### S1. 표지

- 제목: **KR-TL — 국내 전자서명 신뢰목록 개요**
- 부제: 웨일 브라우저 PDF 전자서명 검증 실증 사전 공유
- 하단: ㈜일렉서티 / 2026.08

---

### S2. 오늘 다룰 것과, 오늘 정하지 않을 것

> **거버닝 메시지**
> KR-TL은 "이 서명을 믿어도 되는가"를 브라우저가 스스로 판단할 수 있게 해주는 기계판독 목록이다. 오늘은 그 구조와 기능을 공유하고, 판단이 필요한 지점을 목록으로 남긴다.

**본문 구성** — 좌우 2단

| 오늘 공유한다 | 오늘 정하지 않는다 |
|---|---|
| 신뢰목록의 개념과 KR-TL 데이터 구조 | 요구사항 항목별 수용 여부 |
| KR-TL이 제공하는 기능 5가지 | 화면 배치와 문구 |
| 웨일 검증 흐름에서의 개입 지점 | 지원 버전·플랫폼 범위 |
| 판단이 필요한 지점의 목록 | 구현 분담의 확정 |

**열어 둘 질문**
오늘 자료에서 빠져 있어 판단하기 어려운 정보가 있다면 무엇인지, 발표 중 언제든 말씀해 주시면 다음 자리에 반영한다.

**발표 노트**
우측 열을 먼저 읽는다. 오늘 결정 부담이 없다는 것을 알려 주면 질문이 열린다. 반대로 "오늘 합의합시다"로 시작하면 방어적인 답만 돌아온다.

---

### S3. 지금 브라우저에서 PDF 서명을 열면 벌어지는 일

> **거버닝 메시지**
> 브라우저는 서명값이 수학적으로 맞는지는 확인하지만, 그 인증서를 발급한 사업자를 믿어도 되는지는 답하지 못한다. 이 빈칸을 지금은 이용기관이 각자 메우고 있다.

**본문 구성** — 3단 비교 도식

```
[ 확인되는 것 ]            [ 확인되지 않는 것 ]
문서 무결성                 발급 사업자가 인정받은 곳인가
서명값 일치                 서명 시점에 그 사업자가 정상이었는가
인증서 유효기간             이 인증서가 어떤 용도로 발급된 것인가
                            폐지·정지 여부를 어디서 확인하는가
```

하단 밴드 — 그 결과로 벌어지는 일 세 가지.

1. 이용기관마다 신뢰 판단 기준이 다르고, 그 기준이 소스코드에 하드코딩되어 있다.
2. 사업자 지위가 바뀌어도 검증하는 쪽이 이를 알 방법이 없다.
3. 사용자에게는 "서명됨" 또는 "알 수 없음" 두 가지로만 보인다.

**열어 둘 질문**
웨일 내장 PDF 뷰어에서 서명 문서를 만났을 때 지금은 어떻게 처리되고 있는지, 그리고 이 빈칸이 실제로 문제로 올라온 적이 있는지 궁금하다.

**발표 노트**
이 장은 우리가 문제를 규정하는 장이 아니라, 웨일팀이 자기 제품에서 같은 문제를 확인하게 하는 장이다. 질문을 던지고 실제로 답을 듣는다. 답을 듣지 못하면 이후 장의 전제가 공중에 뜬다.

---

### S4. 신뢰목록이란 무엇인가

> **거버닝 메시지**
> 신뢰목록은 "국가가 인정한 전자서명 사업자와 그 서비스의 현재·과거 상태를, 국가가 서명해 배포하는 기계판독 목록"이다.

**본문 구성** — 정의 한 줄 + 성립 조건 네 가지

| 조건 | 의미 | 출처 |
|---|---|---|
| 권위 있는 발행자 | 목록 발행 주체가 인정제도 운영 기관과 일치한다 | 제도 |
| 기계판독 | 사람이 읽는 공고문이 아니라 검증 소프트웨어가 파싱하는 XML이다 | 규격 |
| 서명된 목록 | 목록 자체가 전자서명되어 위·변조를 검출한다 | 규격 |
| 이력 보존 | 현재 상태만이 아니라 언제부터 그 상태였는지를 담는다 | 규격 |

국제 사례는 각주 수준으로 — EU는 eIDAS 체계에서 ETSI TS 119 612 규격의 Trusted List를 회원국별로 발행하고 이를 LOTL로 묶어 배포한다. KR-TL은 이 구조를 국내 인정제도에 맞춰 적용한 것이다.

**열어 둘 질문**
없음. 이 장은 용어를 맞추는 장이다.

**발표 노트**
"인증서 목록"이 아니라 "서비스 상태 목록"이라는 점을 여기서 못 박는다. 다음 장의 대비가 여기서 갈린다. 우측 "출처" 열은 규격 제약과 제도 제약을 구분해 두려는 것이니, 지나가듯 한 번 짚는다.

---

### S5. 루트 저장소와 신뢰목록은 다른 층이다

> **거버닝 메시지**
> 루트 저장소가 "이 서버와 안전하게 연결해도 되는가"를 다룬다면, 신뢰목록은 "이 문서에 붙은 서명을 제도적으로 인정할 수 있는가"를 다룬다. 둘은 대체 관계가 아니다.

**본문 구성** — 대비표

| | 루트 저장소 (Chromium Root Store 등) | 신뢰목록 (KR-TL, EUTL) |
|---|---|---|
| 대상 | TLS 서버 인증서 | 전자서명·타임스탬프 서비스 |
| 단위 | CA 루트 인증서 | 사업자(TSP) 아래 서비스 단위 |
| 상태 표현 | 포함 / 미포함 (사실상 2값) | 인정·정지·철회 등 상태값 + 상태 개시시각 |
| 시점 처리 | 현재 시점 기준 | 서명 시점 기준 소급 판정 |
| 갱신 | 브라우저 릴리스에 동봉 | 목록을 주기 동기화 |
| 배포 형식 | 브라우저 내장 바이너리 | 서명된 XML |

**열어 둘 질문**
마지막 두 줄이 웨일 입장에서 가장 낯선 부분이다. 릴리스 주기와 무관하게 갱신되는 데이터를 브라우저가 들고 있는 사례가 웨일에 이미 있는지, 있다면 그 방식을 재사용할 수 있는지.

**발표 노트**
여기서 웨일팀이 기존 컴포넌트 업데이트 체계를 떠올린다면 이후 S9의 논의가 훨씬 빨라진다. 우리가 방식을 제안하기보다 그들이 가진 수단을 먼저 듣는 편이 낫다.

### S6. KR-TL이 담는 것 — 데이터 구조

> **거버닝 메시지**
> KR-TL은 ETSI TS 119 612 구조를 따르며, 계층은 스킴 → 사업자 → 서비스 → 상태 이력 네 단으로 내려간다.

**본문 구성** — 트리 도식 + 우측 요약

```
Scheme (스킴 정보)
├─ 운영 주체, 스킴 유형, 적용 국가, 목록 일련번호
├─ 발행시각 / 다음 갱신 예정시각
│
└─ TSP (전자서명인증사업자)
   ├─ 사업자명, 사업자 식별자, 소재지
   │
   └─ Service (서비스)
      ├─ 서비스 유형 (인증서 발급 / 타임스탬프 / 검증 등)
      ├─ 서비스 명칭
      ├─ Digital Identity — 서비스 인증서, 공개키, SKI
      ├─ 현재 상태 + 상태 개시시각
      ├─ 상태 이력 (과거 상태와 각 개시시각)
      └─ 부가 정보 — 적용 정책 OID, 제공 서비스 URI(OCSP/CRL 등)
```

우측 세 줄 요약.

- 검증 소프트웨어가 신뢰앵커로 쓰는 것은 Service의 Digital Identity다.
- 판정에 쓰는 것은 상태값 하나가 아니라 상태값과 개시시각의 쌍이다.
- 같은 사업자라도 서비스별로 상태가 다를 수 있으므로 서비스 단위로 조회한다.

**열어 둘 질문**
이 구조를 브라우저가 그대로 들고 있을지, 파싱한 뒤 필요한 필드만 정규화해 보관할지는 웨일 쪽 저장 정책에 달려 있다. 어느 쪽이 편한지 의견을 듣고 싶다.

**발표 노트**
필드를 다 읽지 않는다. 세 항목(Digital Identity, 상태+개시시각, 서비스 단위)만 짚는다. 나머지는 배포자료 부록으로 넘긴다.

### S7. KR-TL이 제공하는 기능 5가지 ★ 핵심

> **거버닝 메시지**
> KR-TL은 신뢰앵커 제공, 시점 기준 상태 판정, 서비스 유형 구분, 목록 자체의 진위 보장, 배포·동기화 다섯 가지 기능을 제공한다. 검증 엔진이 KR-TL에 요청하는 모든 것은 이 다섯 가지 안에 들어온다.

**본문 구성** — 5칸 가로 배열, 각 칸에 기능명 / 무엇을 해주는가 / 없으면 생기는 일

| | 기능 | 무엇을 해주는가 | 없으면 |
|---|---|---|---|
| F1 | **신뢰앵커 제공** | 인증서 경로 구성의 종착점이 될 서비스 인증서를 목록으로 내려준다 | 이용기관이 앵커를 직접 수집·하드코딩 |
| F2 | **시점 기준 상태 판정** | 서명 시점에 그 서비스가 어떤 상태였는지를 소급해 판정한다 | 과거 서명이 사업자 지위 변경만으로 무효화 |
| F3 | **서비스 유형 구분** | 서명용·타임스탬프·검증 서비스를 구분해 용도 밖 사용을 걸러낸다 | 타임스탬프용 인증서로 문서 서명해도 통과 |
| F4 | **목록의 진위 보장** | 목록에 서명·발행시각·유효기간을 부여해 위조와 노후화를 막는다 | 신뢰 판단의 근거 자체가 공격 대상 |
| F5 | **배포·동기화** | 정해진 주소에서 주기적으로 목록을 받아 최신 상태를 유지한다 | 상태 변경이 검증 시점에 반영되지 않음 |

하단 한 줄 — F1~F3은 검증 엔진이 **소비**하는 기능이고, F4~F5는 브라우저 쪽에 **실제 기능이 생기는** 영역이다.

**열어 둘 질문**
다섯 가지 중 웨일에서 부담이 큰 것과 작은 것이 어떻게 갈리는지. 특히 F5의 갱신 주체를 브라우저 본체로 볼지 별도 컴포넌트로 볼지는 웨일 구조를 아는 쪽에서 판단하는 편이 정확하다.

**발표 노트**
이 표가 오늘 자료의 중심이다. 이후 슬라이드가 F2·F4·F5를 풀어 쓴 것임을 미리 말해 두면 흐름이 잡힌다. F3는 구현 부담이 작아 표에서만 언급하고 넘어간다. 하단 한 줄을 읽은 뒤에는 잠깐 멈춰서 반응을 본다.

---

### S8. 기능 상세 ① 시점 기준 상태 판정 (F2)

> **거버닝 메시지**
> "지금 인정 상태인가"가 아니라 "서명한 그 시각에 인정 상태였는가"를 묻는다. 이 한 가지 때문에 목록은 현재 상태가 아닌 상태 이력을 담는다.

**본문 구성** — 타임라인 도식

```
2024.03 ──────── 2025.06 ──────── 2026.01 ──────── 오늘
   │                 │                 │
   인정 개시          서명 생성         인정 철회
                        ▲
                   판정 기준시각
```

세 갈래 결과.

| 조회 방식 | 판정 | 결과 |
|---|---|---|
| 현재 상태만 조회 | 신뢰 불가 | 정상적으로 만들어진 과거 서명이 전부 무효가 된다 |
| 상태 이력 + 서명시각 | 신뢰 가능 | 서명 시점 상태가 근거로 남는다 |
| 상태 이력 + 신뢰 못 할 시각원 | 판정 보류 | 서명시각을 신뢰할 수 없으면 시점 판정도 성립하지 않는다 |

세 번째 줄이 타임스탬프와 장기검증(LTV)으로 이어진다는 점을 한 줄로 연결한다.

**열어 둘 질문**
판정 기준시각을 사용자 화면에 어느 수준으로 노출할지. 감추면 결과 재현이 안 되고, 그대로 드러내면 일반 사용자에게는 읽히지 않는 정보가 하나 늘어난다. 이 균형은 웨일 UX 기준에 맞추는 것이 맞다고 본다.

**발표 노트**
"기준시각을 반드시 노출해야 한다"고 단정하지 않는다. 노출하지 않았을 때 생기는 문제(같은 문서가 다른 결과를 내는데 이유를 알 수 없음)만 정확히 전달하면, 판단은 웨일팀이 한다.

---

### S9. 기능 상세 ② 목록의 진위 보장 (F4)과 동기화 (F5)

> **거버닝 메시지**
> 목록을 받아오는 순간부터 목록은 공격 대상이 된다. 그래서 브라우저는 목록을 쓰기 전에 네 가지를 검사하고, 통과한 목록만 기존 목록을 대체한다.

**본문 구성** — 좌: 수용 검사 4단계 / 우: 동기화 상태 모델

좌측 — 목록 수용 전 검사 (규격 요구)

1. 출처 확인 — 배포 주소가 합의된 주소인가
2. 목록 서명 검증 — 고정된 신뢰앵커로 검증되는가
3. 발행시각 확인 — 이전에 적용한 목록보다 새 것인가 (롤백 방지)
4. 유효기간 확인 — 만료되지 않았는가

하나라도 실패하면 적용하지 않고 기존 정상 목록을 유지한다. 실패한 목록이 정상 목록을 밀어내지 않는다는 점은 강조 처리한다.

우측 — 동기화 상태에서 다뤄야 할 정보

| 상태 | 다뤄야 할 정보 |
|---|---|
| 정상 적용 | 적용 버전, 발행시각, 유효기간, 마지막 동기화 시각 |
| 동기화 실패 | 실패 원인, 재시도 가능 여부, 기존 목록 유지 여부 |
| 캐시 사용 | 캐시 기준시각, 만료까지 남은 시간, 재검증 필요 여부 |
| 목록 없음 | 신뢰 판정 불가 상태임을 명시 |

**열어 둘 질문 (이 장의 핵심)**

| 판단할 것 | 선택지 | 대가 |
|---|---|---|
| 갱신 주기 | 짧게 (예: 6시간) | 상태 변경 반영이 빠르나 트래픽·배터리 부담 |
| | 길게 (예: 24시간~7일) | 부담이 작으나 철회 반영이 늦어짐 |
| 갱신 주체 | 브라우저 본체 | 구현이 단순하나 릴리스와 결합 |
| | 별도 컴포넌트 업데이트 | 독립적이나 기존 체계에 항목이 하나 늘어남 |
| 캐시 저장 위치 | OS 보안 저장소 | 보호 수준이 높으나 플랫폼별 구현이 갈림 |
| | 프로파일 내 암호화 저장 | 구현이 균일하나 보호 수준 판단 필요 |

현재 검토안은 기본 24시간 주기 + OS 보안 저장소이나, 웨일 플랫폼 정책에 맞춰 조정한다.

**발표 노트**
이 표가 이 자리에서 가장 실질적인 산출물이다. 우리가 정한 값을 통보하는 대신 선택지를 놓고 웨일 쪽 제약을 듣는다. 다만 신뢰앵커 변경 기능을 브라우저에 두지 않는 것은 선택지가 아니라 규격·보안상 고정값이므로, 이 하나만은 분명히 구분해 말한다.

---

### S10. 검증 흐름에서 KR-TL이 개입하는 지점

> **거버닝 메시지**
> KR-TL 조회는 검증의 전부가 아니라 네 번째 단계다. 앞 단계가 실패하면 조회까지 가지 않고, 조회 결과는 뒤 단계 결과를 대체하지 않는다.

**본문 구성** — 가로 플로우 도식 (④만 강조색)

```
PDF 열기
  → ① 서명 존재 확인
  → ② 서명 구조·ByteRange·문서 무결성
  → ③ 서명값 검증 / 인증서 경로 구성
  → ④ [KR-TL 대조] 서비스 등록 여부·상태·기준시각
  → ⑤ 인증서 상태 확인 (CRL / OCSP)
  → ⑥ 결과 산출
```

하단 상세 박스.

**④에서 하는 일**
서명자 인증서의 발급자·서비스 식별정보를 적용 중인 KR-TL과 대조한다. 결과는 등록됨 / 미등록 / 서비스 철회 / 목록 만료 / 목록 접근 불가 / 목록 서명 오류로 구분한다.

**④에서 하지 않는 일**
문서 변조 판정, 서명값 유효성 판정, 폐지 여부 판정. 이 세 가지는 각각 ②③⑤의 결과다.

**열어 둘 질문**
④와 ⑤는 외부 통신이 필요하고 ①~③은 로컬에서 끝난다. 로컬 결과를 먼저 표시하고 외부 결과를 나중에 채우는 방식이 웨일 렌더링 구조에서 자연스러운지, 아니면 한 번에 표시하는 편이 나은지.

**발표 노트**
"KR-TL 미등록"이 곧 "서명 무효"가 아니라는 것이 다음 장의 전제다. 여기서 한 번 짚는다.

---

### S11. 결과를 어떻게 나눠 보여줄 것인가

> **거버닝 메시지**
> 변조·무효·미등록·확인불가는 원인도 대응도 다르다. 이를 같은 경고로 뭉치면 사용자는 정상 문서를 위조로 오인하거나 그 반대를 하게 된다.

**본문 구성** — 상: 구분해야 할 상황 / 하: 표시 체계 검토안

상단 — 반드시 구분해야 할 네 가지 (이것이 원칙)

| 상황 | 원인 | 사용자가 할 수 있는 일 | 뭉쳤을 때의 사고 |
|---|---|---|---|
| 문서 변조 | 서명 이후 내용 변경 | 문서를 신뢰하지 않는다 | — |
| KR-TL 미등록 | 인정받지 않은 사업자의 서명 | 발급처를 확인한다 | 정상 문서를 위조로 오인 |
| 목록 접근 불가 | 네트워크·서버 장애 | 연결 후 재검증한다 | 장애를 위조로 오인 |
| 상태정보 미확인 | CRL/OCSP 응답 없음 | 재검증한다 | 확인 안 된 것을 정상으로 오인 |

하단 — 표시 체계 **검토안** (확정 아님)

| 아이콘 | 문구 | 언제 |
|---|---|---|
| 흰 원 | 서명 없음 | 서명이 포함되지 않은 PDF |
| 초록 방패 | 진본 확인 | 모든 축이 통과 |
| 노란 삼각형 | 주의 필요 | 미등록·철회 등 신뢰 판단에 유보가 필요 |
| 회색 하이픈 | 확인 불가 | 외부 정보 접근 실패, 제한 검증 |
| 빨간 방패 | 서명 무효 | 문서 변조 또는 서명값 검증 실패에 한정 |

**열어 둘 질문**
상단 표의 네 가지를 구분한다는 원칙은 규격에서 오는 것이고, 하단의 아이콘·문구·상태 개수는 전적으로 웨일 UX 판단 영역이다. 5단계가 많다면 줄여도 되고, 웨일의 기존 보안 표시 체계와 맞추는 편이 나을 수도 있다. 이 부분은 웨일에서 안을 주시면 우리가 판정 로직을 맞춘다.

**발표 노트**
기획 쪽에서 가장 논의가 길어질 장이다. 하단 표를 "우리 안"이라고 분명히 말하고, 상단과 하단의 성격 차이(원칙 대 선택)를 명시적으로 갈라 준다. 여기서 웨일이 자기 안을 내놓게 되면 이 자리는 성공한 것이다.

### S12. 오프라인·장애 시 동작

> **거버닝 메시지**
> 네트워크가 없어도 문서 열람은 멈추지 않되, 만료된 캐시로 정상 판정을 내리지 않는다. 이 두 문장이 오프라인 정책의 뼈대다.

**본문 구성** — 분기 도식

```
동기화 시도
 ├─ 성공 → 목록 갱신 → 온라인 검증
 └─ 실패 ─┬─ 유효 캐시 있음 → 제한 검증 → "확인 불가 / 재검증 필요" 표시
          └─ 유효 캐시 없음 → 신뢰 판정 보류 → PDF 열람은 유지
```

고정 원칙 세 줄 (조정 대상 아님).

1. 어떤 경우에도 PDF 열람 자체는 차단하지 않는다.
2. 캐시는 서명·발행시각·유효기간을 재검증한 뒤 사용하고, 만료·손상 캐시는 폐기한다.
3. 제한 검증 결과에는 캐시 기준시각과 재검증 필요 여부를 함께 기록한다.

**열어 둘 질문**
온라인 복귀 시 재검증을 자동으로 돌릴지, 사용자가 누를 때만 돌릴지. 자동은 편하지만 사용자가 보고 있던 결과가 예고 없이 바뀐다. 이 선택은 웨일 UX 원칙에 따르는 것이 맞다.

**발표 노트**
고정 원칙 세 줄과 열어 둔 질문의 성격 차이를 분명히 한다. 앞 셋은 안전성 요건이라 협상 대상이 아니고, 재검증 시점은 순수하게 제품 판단이다.

### S13. 역할 경계 — 현재 초안

> **거버닝 메시지**
> 현재는 웨일이 브라우저에서 보이고 저장되는 부분을, 일렉서티가 판정 로직과 결과코드를, KISA가 목록과 기준정보를 맡는 것으로 그려 두었다. 경계선의 위치는 조정 가능하다.

**본문 구성** — 3열 표 (표 제목에 "초안" 명시)

| 웨일 | 일렉서티 | KISA |
|---|---|---|
| 내장 PDF 뷰어의 서명 탐지·검증 트리거 | 검증 SDK 및 연동 가이드 | KR-TL 발행·서명·배포 |
| 메뉴바 상태 표시, 상세 근거 화면 | KR-AdES 처리, 인증서 경로·상태 판정 | 신뢰앵커 및 배포 주소 제공 |
| 설정 화면 (주소·주기·동기화 이력) | 표준 결과코드 체계 | 발행기관 기준정보 API |
| 목록 캐시 저장·만료 관리 | XML 검증보고서 생성 (ETSI TS 119 102-2) | 보관서비스 확인 기준 |
| 보고서 저장·출력 UI | 오프라인 제한 검증 판정 규칙 | 실증 정책·예외 기준 |

하단 — 이 초안대로면 웨일이 새로 만드는 화면은 세 곳이다. 메뉴바 상태 표시, 검증 결과 상세, 설정 내 KR-TL 항목.

**열어 둘 질문**
경계가 어색한 항목이 있는지. 특히 캐시 저장·만료 관리를 SDK 안으로 넣는 편이 나을지, 브라우저가 직접 들고 있는 편이 나을지는 양쪽 다 성립하므로 웨일 쪽 선호를 듣고 정한다.

**발표 노트**
"어디까지 우리가 만드나"가 웨일팀의 첫 질문이다. 이 표를 먼저 띄우되 확정으로 말하지 않는다. 항목별 수용·조정·보류는 요구사항 추적표에서 다룬다는 점을 덧붙인다.

### S14. 기존 신뢰체계와의 관계

> **거버닝 메시지**
> KR-TL은 브라우저의 기존 신뢰체계를 바꾸지 않는다. TLS 신뢰와는 층이 다르고, 문서 서명 신뢰체계와는 병존한다.

**본문 구성** — 3층 도식

```
[ TLS 연결 신뢰 ]      Chromium Root Store        영향 없음
      ─────────────────────────────────────
[ 문서 서명 신뢰 ]     Adobe AATL / EUTL          병존, 상호 배타 아님
                       KR-TL                       국내 인정제도 반영
      ─────────────────────────────────────
[ 검증 절차 규격 ]     ETSI EN 319 102-1          공통 판정 절차
```

정리 세 줄.

- KR-TL 적용이 기존 TLS 인증서 검증 경로에 개입하지 않는다.
- 하나의 문서가 여러 신뢰체계에서 동시에 검증될 수 있으며, KR-TL 미등록이 다른 체계의 판정을 부정하지 않는다.
- 판정 절차와 결과 표현은 국제 규격을 따르므로 결과를 국외 검증 도구와 대조할 수 있다.

**열어 둘 질문**
웨일이 Chromium 업스트림과의 차이를 관리하는 기준선이 있다면, 이 기능이 그 기준에서 어느 쪽에 놓이는지 판단해 주시면 구현 형태를 그에 맞춘다.

**발표 노트**
"웨일 기존 동작에 리스크가 있는가"에 대한 선제 답변이다. 짧게 지나가되 반드시 넣는다.

## 3. 예상 질문과 대응

대응은 결론을 주는 형태가 아니라 판단 재료를 주는 형태로 준비한다.

| 질문 | 대응 요지 |
|---|---|
| 목록을 못 받아오면 브라우저가 느려지거나 멈추는가 | 검증은 비동기이며 PDF 열람 경로와 분리한다. 목록 조회 실패는 해당 결과 축만 확인 불가로 처리한다 |
| 목록 크기와 갱신 부담은 어느 정도인가 | 국내 인정사업자 수 기준으로 규모가 작다. 조건부 요청으로 변경 없을 때 본문 전송을 피하는 방식이 가능하며, 실제 주기는 웨일 판단에 맞춘다 |
| 신뢰앵커가 브라우저에 박히면 교체는 어떻게 하는가 | 실증 단계에서는 고정 앵커로 둔다. 앵커 갱신 절차는 KISA 운영정책 항목이며, 웨일 배포 체계와 맞물리는 부분이라 별도로 다룬다 |
| 사용자에게 "미등록"을 어떻게 설명하나 | 무효가 아니라 "확인된 인정사업자 목록에 없음"이라는 사실 진술이 성립한다. 실제 문구는 웨일 UX 기준으로 정한다 |
| PDF 원문이 외부로 나가는가 | 나가지 않는다. 외부 조회에는 식별정보와 해시만 전송하며 보고서에도 원문을 포함하지 않는다 |
| Chromium 업스트림과 충돌하지 않나 | TLS 신뢰 경로에 개입하지 않으며 PDF 뷰어 확장 지점에서 동작한다. 업스트림 차이 관리 기준은 웨일 쪽 판단을 따른다 |
| 이거 우리가 꼭 해야 하는 건가 | 실증 참여 범위는 협의 대상이다. 다만 브라우저에서 문서 서명을 표시하려면 신뢰 판단 근거가 필요하고, 지금은 그 근거가 없다는 점이 출발점이다 |

마지막 질문은 반드시 준비해 둔다. 사전 공유 자리에서 가장 나올 법한 질문이고, 여기서 방어적으로 답하면 이후 협의가 어려워진다.

## 부록 C. 문장 점검 기준

작성·검토 시 다음에 걸리는 문장은 고친다.

- 확정되지 않은 것을 확정형으로 쓴 문장 — "…한다"로 끝나지만 실제로는 웨일 판단이 필요한 항목
- 선택지 없이 하나의 방식만 제시한 문장 — 대안이 있는데 적지 않았다면 판단 재료가 부족한 것
- 규격 제약과 우리 제안이 같은 문단에 섞인 문장
- 웨일이 무엇을 얻는지 없이 무엇을 해야 하는지만 있는 문단
