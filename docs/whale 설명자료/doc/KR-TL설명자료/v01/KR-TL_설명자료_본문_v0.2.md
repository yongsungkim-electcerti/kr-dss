## 읽는 방법

각 페이지는 다음 네 블록으로 되어 있다.

- **슬라이드 문안** — 슬라이드에 그대로 인쇄되는 텍스트. 여기 없는 문장은 슬라이드에 넣지 않는다.
- **도식** — 배치와 라벨. HTML 스케치 단계에서 이대로 그린다.
- **열어 둘 질문** — 슬라이드 하단에 인쇄한다. 웨일팀이 가져갈 판단 항목이다.
- **발표 스크립트** — 말로 하는 부분. 슬라이드 문안을 읽지 않고 이 내용을 말한다.

슬라이드 문안과 발표 스크립트는 겹치지 않게 썼다. 슬라이드는 뼈대만 두고 살은 말로 붙인다.

# P01 — 표지

### 슬라이드 문안

```
KR-TL
국내 전자서명 신뢰목록 개요

웨일 브라우저 PDF 전자서명 검증 실증 사전 공유

㈜일렉서티
```

### 발표 스크립트 (20초)

일렉서티에서 전자서명 규격과 검증 쪽을 맡고 있는 ○○○입니다. 오늘은 KR-TL, 국내 전자서명 신뢰목록에 대해 말씀드리려고 합니다. 웨일 브라우저에서 PDF 전자서명을 검증하는 실증을 준비하고 있는데, 그 전에 KR-TL이 뭐고 브라우저 입장에서 뭐가 달라지는지를 먼저 맞춰 두는 게 좋겠다고 판단했습니다.

# P02 — 오늘 다룰 것과, 오늘 정하지 않을 것

**브레드크럼** 도입 › 범위

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 "이 서명을 믿어도 되는가"를 브라우저가 스스로 판단할 수 있게 해주는 기계판독 목록이다. 오늘은 구조와 기능을 공유하고, 판단이 필요한 지점을 목록으로 남긴다.

| 오늘 공유합니다 | 오늘 정하지 않습니다 |
|---|---|
| 신뢰목록의 개념과 KR-TL 데이터 구조 | 요구사항 항목별 수용 여부 |
| KR-TL이 제공하는 기능 5가지 | 화면 배치와 문구 |
| 웨일 검증 흐름에서의 개입 지점 | 지원 버전·플랫폼 범위 |
| 판단이 필요한 지점의 목록 | 구현 분담의 확정 |

### 열어 둘 질문

오늘 자료에서 빠져 있어 판단하기 어려운 정보가 있다면 발표 중 언제든 말씀해 주시기 바랍니다.

### 발표 스크립트 (30초)

먼저 오른쪽 열부터 봐 주시면 좋겠습니다. 오늘은 결정하는 자리가 아닙니다. 요구사항을 항목별로 받자는 것도 아니고, 화면을 이렇게 만들어 달라는 것도 아닙니다.

오늘 하려는 건 두 가지입니다. 하나는 KR-TL이라는 게 뭔지 같은 그림을 공유하는 것, 다른 하나는 이걸 브라우저에 붙일 때 누군가는 판단해야 하는 지점들이 있는데 그게 뭔지 목록으로 남기는 겁니다. 그 판단은 저희가 하는 것보다 웨일 쪽에서 하시는 게 맞는 게 대부분입니다. 마지막 장에 그 목록을 정리해 두었습니다.

# P03 — 지금 브라우저에서 PDF 서명을 열면

**브레드크럼** 문제 › 현재 상황

### 슬라이드 문안

**거버닝 메시지**
> 브라우저는 서명값이 맞는지는 확인하지만, 그 인증서를 발급한 사업자를 믿어도 되는지는 답하지 못한다. 이 빈칸을 지금은 이용기관이 각자 메우고 있다.

**그 결과**

1. 이용기관마다 신뢰 판단 기준이 다르고, 그 기준이 소스코드에 하드코딩되어 있다.
2. 사업자 지위가 바뀌어도 검증하는 쪽이 이를 알 방법이 없다.
3. 사용자에게는 "서명됨" 또는 "알 수 없음" 두 가지로만 보인다.

### 도식 — 2단 대비

```
┌─────────────────────────┬─────────────────────────┐
│  확인되는 것             │  확인되지 않는 것         │
├─────────────────────────┼─────────────────────────┤
│  문서 무결성             │  발급 사업자가 인정받은   │
│                         │  곳인가                  │
│  서명값 일치             │  서명 시점에 그 사업자가  │
│                         │  정상이었는가            │
│  인증서 유효기간         │  이 인증서가 어떤 용도로  │
│                         │  발급된 것인가           │
│                         │  폐지·정지 여부를        │
│                         │  어디서 확인하는가        │
└─────────────────────────┴─────────────────────────┘
   로컬에서 계산 가능          외부 근거가 필요
```

좌측은 회색 계열, 우측은 강조색. 하단 라벨 두 줄이 대비의 핵심이다.

### 열어 둘 질문

웨일 내장 PDF 뷰어에서 서명이 포함된 문서를 만났을 때 지금은 어떻게 처리되고 있는지, 이 빈칸이 실제로 이슈로 올라온 적이 있는지 궁금합니다.

### 발표 스크립트 (90초)

PDF에 전자서명이 붙어 있을 때 브라우저가 확인할 수 있는 건 왼쪽입니다. 문서가 서명 이후에 바뀌었는지, 서명값이 인증서의 공개키로 검증되는지, 인증서 유효기간이 지났는지. 이건 전부 로컬에서 계산으로 끝납니다.

문제는 오른쪽입니다. 그 인증서를 발급한 곳이 국가가 인정한 사업자인지, 서명하던 그 시점에 그 사업자가 정상 상태였는지, 이 인증서가 문서 서명용으로 발급된 건지 아니면 다른 용도인지. 이건 계산으로 안 나옵니다. 외부에 근거가 있어야 알 수 있습니다.

지금은 그 근거를 각 이용기관이 알아서 마련하고 있습니다. 어떤 곳은 특정 CA 인증서를 코드에 박아두고, 어떤 곳은 자체 화이트리스트를 관리합니다. 그러다 보니 같은 문서를 A 기관에서 열면 정상이고 B 기관에서 열면 알 수 없음이 됩니다. 사업자 지위가 바뀌어도 그 코드는 그대로 남아 있고요.

사용자 입장에서는 결국 두 가지밖에 안 보입니다. 서명됨, 또는 알 수 없음. 그 사이에 있어야 할 정보가 전부 사라집니다.

혹시 웨일에서는 지금 서명 붙은 PDF를 어떻게 처리하고 계신지 여쭤봐도 될까요.

# P04 — 신뢰목록이란 무엇인가

**브레드크럼** 개념 › 정의

### 슬라이드 문안

**거버닝 메시지**
> 신뢰목록은 국가가 인정한 전자서명 사업자와 그 서비스의 현재·과거 상태를, 국가가 서명해 배포하는 기계판독 목록이다.

**성립 조건 네 가지**

| 조건 | 의미 | 근거 |
|---|---|---|
| 권위 있는 발행자 | 목록 발행 주체가 인정제도 운영 기관과 일치한다 | 제도 |
| 기계판독 | 사람이 읽는 공고문이 아니라 검증 소프트웨어가 파싱하는 XML이다 | 규격 |
| 서명된 목록 | 목록 자체가 전자서명되어 위·변조를 검출한다 | 규격 |
| 이력 보존 | 현재 상태만이 아니라 언제부터 그 상태였는지를 담는다 | 규격 |

**참고** EU는 eIDAS 체계에서 ETSI TS 119 612 규격의 Trusted List를 회원국별로 발행하고, 이를 LOTL로 묶어 배포한다. KR-TL은 같은 구조를 국내 인정제도에 맞춰 적용한 것이다.

### 발표 스크립트 (60초)

신뢰목록을 한 줄로 정의하면 이렇습니다. 국가가 인정한 전자서명 사업자와 그 서비스의 상태를, 국가가 직접 서명해서 배포하는 목록.

네 가지가 갖춰져야 신뢰목록이라고 할 수 있습니다. 발행하는 주체가 실제로 인정제도를 운영하는 기관이어야 하고, 사람이 읽는 공고가 아니라 소프트웨어가 파싱하는 형식이어야 하고, 목록 자체에 서명이 붙어 있어야 하고, 마지막으로 과거 이력이 남아 있어야 합니다.

오른쪽 근거 열을 봐 주시면, 첫 줄만 제도에서 오는 거고 나머지 셋은 규격에서 옵니다. 이 구분을 오늘 자료 전체에서 유지하려고 합니다. 규격이라 어쩔 수 없는 것과, 저희가 이렇게 하자고 제안하는 걸 섞어 놓으면 어디를 조정할 수 있는지 안 보이니까요.

한 가지만 기억해 주시면 좋겠습니다. 이건 인증서 목록이 아니라 서비스 상태 목록입니다. 다음 장 대비가 여기서 갈립니다.

# P05 — 루트 저장소와 신뢰목록은 다른 층이다

**브레드크럼** 개념 › 기존 체계와의 차이

### 슬라이드 문안

**거버닝 메시지**
> 루트 저장소가 "이 서버와 안전하게 연결해도 되는가"를 다룬다면, 신뢰목록은 "이 문서에 붙은 서명을 제도적으로 인정할 수 있는가"를 다룬다. 둘은 대체 관계가 아니다.

| | 루트 저장소 (Chromium Root Store 등) | 신뢰목록 (KR-TL, EUTL) |
|---|---|---|
| 대상 | TLS 서버 인증서 | 전자서명·타임스탬프 서비스 |
| 단위 | CA 루트 인증서 | 사업자 아래 서비스 단위 |
| 상태 표현 | 포함 / 미포함 | 인정·정지·철회 등 상태값 + 상태 개시시각 |
| 시점 처리 | 현재 시점 기준 | 서명 시점 기준 소급 판정 |
| 갱신 | 브라우저 릴리스에 동봉 | 목록을 주기 동기화 |
| 배포 형식 | 브라우저 내장 바이너리 | 서명된 XML |

마지막 두 줄에 강조 표시.

### 열어 둘 질문

릴리스 주기와 무관하게 갱신되는 데이터를 브라우저가 들고 있는 사례가 웨일에 이미 있는지, 있다면 그 방식을 재사용할 수 있는지 궁금합니다.

### 발표 스크립트 (60초)

브라우저에 이미 신뢰 판단 체계가 있는데 왜 또 필요하냐는 질문이 나올 수 있어서 정리해 봤습니다.

루트 저장소는 TLS를 위한 겁니다. 이 서버와 암호화 연결을 맺어도 되는가. 대상이 서버 인증서고, 판단은 사실상 포함이냐 아니냐 두 가지입니다.

신뢰목록은 다릅니다. 대상이 서명 서비스고, 단위가 사업자가 아니라 사업자 아래 개별 서비스입니다. 한 사업자가 서명용 서비스는 정상인데 타임스탬프 서비스는 정지 상태일 수 있고, 목록은 그걸 따로 표현합니다.

웨일 입장에서 실질적으로 다른 건 아래 두 줄입니다. 루트 저장소는 브라우저 릴리스에 실려서 나가는데, 신뢰목록은 릴리스와 무관하게 갱신됩니다. 그러니까 브라우저가 목록을 주기적으로 가져오고, 캐시하고, 만료를 관리하는 기능을 새로 갖게 됩니다. 이 부분은 뒤에서 다시 다루겠습니다.

혹시 웨일에 이미 이런 식으로 따로 갱신되는 데이터가 있으면 그 방식을 그대로 쓰는 게 나을 수도 있겠습니다.

# P06 — KR-TL이 담는 것

**브레드크럼** 구조 › 데이터 모델

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 ETSI TS 119 612 구조를 따르며, 계층은 스킴 → 사업자 → 서비스 → 상태 이력 네 단으로 내려간다.

**검증에서 실제로 쓰는 것 세 가지**

- 신뢰앵커로 쓰는 것은 Service의 Digital Identity다.
- 판정에 쓰는 것은 상태값 하나가 아니라 상태값과 개시시각의 쌍이다.
- 같은 사업자라도 서비스별로 상태가 다를 수 있으므로 서비스 단위로 조회한다.

### 도식 — 계층 트리

```
Scheme  스킴 정보
├─ 운영 주체 · 스킴 유형 · 적용 국가 · 목록 일련번호
├─ 발행시각 · 다음 갱신 예정시각
│
└─ TSP  전자서명인증사업자
   ├─ 사업자명 · 사업자 식별자 · 소재지
   │
   └─ Service  서비스
      ├─ 서비스 유형          인증서 발급 / 타임스탬프 / 검증
      ├─ 서비스 명칭
      ├─ Digital Identity     서비스 인증서 · 공개키 · SKI      ★
      ├─ 현재 상태 + 상태 개시시각                              ★
      ├─ 상태 이력            과거 상태와 각 개시시각            ★
      └─ 부가 정보            정책 OID · OCSP/CRL 주소
```

★ 표시한 세 항목만 강조색. 나머지는 회색.

### 열어 둘 질문

이 구조를 브라우저가 그대로 보관할지, 파싱한 뒤 필요한 필드만 정규화해서 보관할지는 웨일 쪽 저장 정책에 달려 있습니다. 어느 쪽이 편한지 의견을 듣고 싶습니다.

### 발표 스크립트 (90초)

구조는 ETSI TS 119 612를 따릅니다. EU가 쓰는 것과 같은 규격입니다.

네 단입니다. 맨 위가 스킴 정보고, 이 목록이 언제 발행됐고 다음 갱신이 언제인지가 여기 들어갑니다. 그 아래가 사업자, 그 아래가 서비스입니다. 서비스가 실질적인 단위입니다.

별표 친 세 개만 봐 주시면 됩니다.

첫째, Digital Identity. 서비스 인증서가 들어 있고, 검증 엔진이 인증서 경로를 만들 때 이게 종착점이 됩니다. 그러니까 신뢰앵커를 어디서 가져오느냐는 질문의 답이 여기 있습니다.

둘째, 상태값과 개시시각이 한 쌍이라는 점. 지금 인정 상태라는 정보만으로는 부족하고, 언제부터 그 상태였는지가 같이 있어야 합니다. 왜 그런지는 다음 장에서 말씀드리겠습니다.

셋째, 상태 이력. 과거에 어떤 상태였고 그게 언제부터였는지가 전부 남아 있습니다. 목록이 현재 스냅샷이 아닌 이유입니다.

브라우저가 이 XML을 통째로 들고 있을지, 파싱해서 필요한 것만 남길지는 저희가 정할 문제가 아니라서 열어 두겠습니다.

# P07 — KR-TL이 제공하는 기능 5가지

**브레드크럼** 기능 › 전체

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 신뢰앵커 제공, 시점 기준 상태 판정, 서비스 유형 구분, 목록의 진위 보장, 배포·동기화 다섯 가지 기능을 제공한다. 검증 엔진이 KR-TL에 요청하는 모든 것은 이 다섯 안에 들어온다.

| | 기능 | 무엇을 해주는가 | 없으면 |
|---|---|---|---|
| **F1** | 신뢰앵커 제공 | 인증서 경로 구성의 종착점이 될 서비스 인증서를 목록으로 내려준다 | 이용기관이 앵커를 직접 수집·하드코딩 |
| **F2** | 시점 기준 상태 판정 | 서명 시점에 그 서비스가 어떤 상태였는지를 소급해 판정한다 | 과거 서명이 사업자 지위 변경만으로 무효화 |
| **F3** | 서비스 유형 구분 | 서명용·타임스탬프·검증 서비스를 구분해 용도 밖 사용을 걸러낸다 | 타임스탬프용 인증서로 문서 서명해도 통과 |
| **F4** | 목록의 진위 보장 | 목록에 서명·발행시각·유효기간을 부여해 위조와 노후화를 막는다 | 신뢰 판단의 근거 자체가 공격 대상 |
| **F5** | 배포·동기화 | 정해진 주소에서 주기적으로 목록을 받아 최신 상태를 유지한다 | 상태 변경이 검증 시점에 반영되지 않음 |

**F1~F3은 검증 엔진이 소비하는 기능이고, F4~F5는 브라우저 쪽에 실제 기능이 생기는 영역이다.**

### 도식

표의 F4·F5 행에 좌측 색 띠를 넣어 "브라우저 구현 영역"으로 묶는다. 하단 강조 문장과 색을 맞춘다.

### 열어 둘 질문

다섯 중 웨일에서 부담이 큰 것과 작은 것이 어떻게 갈리는지 궁금합니다. 특히 F5의 갱신 주체를 브라우저 본체로 볼지 별도 컴포넌트로 볼지는 웨일 구조를 아는 쪽에서 판단하는 편이 정확합니다.

### 발표 스크립트 (150초)

오늘 자료의 중심입니다. KR-TL이 해주는 일을 다섯 개로 정리했습니다.

F1, 신뢰앵커 제공. 인증서 경로를 만들 때 어디까지 올라가서 멈출지, 그 종착점을 목록이 내려줍니다. 이게 없으면 각자 앵커를 모아서 코드에 박아야 합니다. 지금 상황이 그렇습니다.

F2, 시점 기준 상태 판정. 지금 상태가 아니라 서명하던 그 시점의 상태로 판정합니다. 이게 없으면 사업자가 나중에 인정이 취소됐다는 이유로 3년 전에 정상적으로 서명한 문서가 전부 무효가 됩니다. 다음 장에서 자세히 보겠습니다.

F3, 서비스 유형 구분. 타임스탬프용으로 발급된 인증서로 문서를 서명하면 걸러냅니다. 목록에 서비스 유형이 들어 있어서 가능합니다. 구현 부담은 크지 않아서 오늘은 여기까지만 말씀드리겠습니다.

F4와 F5가 웨일 입장에서 중요합니다. 앞의 셋은 검증 엔진이 목록을 읽어서 쓰는 거라 SDK 안에서 처리됩니다. 그런데 F4와 F5는 브라우저에 실제로 기능이 생깁니다.

F4는 목록 자체를 믿을 수 있게 만드는 겁니다. 목록을 외부에서 받아오는 순간부터 목록이 공격 대상이 되니까, 받아온 걸 그대로 쓰면 안 됩니다.

F5는 그걸 주기적으로 받아오는 기능입니다. 언제 받아올지, 못 받아오면 어떻게 할지, 받아온 걸 어디에 둘지가 전부 여기 딸려 옵니다.

이 두 개를 다음 장에서 같이 보겠습니다. 오늘 논의가 필요한 부분이 거기 몰려 있습니다.

# P08 — 기능 상세 ① 시점 기준 상태 판정

**브레드크럼** 기능 › F2 상세

### 슬라이드 문안

**거버닝 메시지**
> "지금 인정 상태인가"가 아니라 "서명한 그 시각에 인정 상태였는가"를 묻는다. 이 한 가지 때문에 목록은 현재 상태가 아닌 상태 이력을 담는다.

| 조회 방식 | 판정 | 결과 |
|---|---|---|
| 현재 상태만 조회 | 신뢰 불가 | 정상적으로 만들어진 과거 서명이 전부 무효가 된다 |
| 상태 이력 + 서명시각 | 신뢰 가능 | 서명 시점 상태가 근거로 남는다 |
| 상태 이력 + 신뢰 못 할 시각원 | 판정 보류 | 서명시각을 신뢰할 수 없으면 시점 판정도 성립하지 않는다 |

세 번째 행이 타임스탬프와 장기검증으로 이어진다.

### 도식 — 타임라인

```
  2024.03 ─────────── 2025.06 ─────────── 2026.01 ─────────── 오늘
     │                   │                   │                  │
  인정 개시            서명 생성           인정 철회          검증 시점
                          ▲
                     ┌────┴────┐
                     │ 판정 기준시각 │
                     └─────────┘

  현재 상태로 판정   →  철회 상태  →  신뢰 불가
  서명시각으로 판정  →  인정 상태  →  신뢰 가능
```

두 줄의 결과를 각각 다른 색으로 대비시킨다.

### 열어 둘 질문

판정 기준시각을 사용자 화면에 어느 수준으로 노출할지 판단이 필요합니다. 감추면 같은 문서가 다른 결과를 낼 때 이유를 알 수 없고, 그대로 드러내면 일반 사용자에게 읽히지 않는 정보가 하나 늘어납니다. 이 균형은 웨일 UX 기준에 맞추는 것이 맞다고 봅니다.

### 발표 스크립트 (60초)

예를 들어 보겠습니다. 2024년 3월에 인정받은 사업자가 있고, 2025년 6월에 그 사업자 인증서로 문서에 서명을 했습니다. 그런데 2026년 1월에 그 사업자가 인정이 철회됐습니다. 오늘 그 문서를 열면 어떻게 판정해야 할까요.

현재 상태만 보면 철회 상태니까 신뢰 불가입니다. 그런데 그러면 정상적으로 만들어진 문서가 나중에 벌어진 일 때문에 전부 무효가 됩니다. 계약서라면 곤란합니다.

서명 시점으로 판정하면 그때는 인정 상태였으니 신뢰 가능입니다. 이게 맞는 판정이고, 그러려면 목록이 과거 이력을 들고 있어야 합니다.

세 번째 줄이 하나 더 있습니다. 서명시각을 못 믿으면 시점 판정 자체가 성립하지 않습니다. 서명 안에 적힌 시각은 서명한 쪽이 쓴 값이라 그것만으로는 부족합니다. 그래서 타임스탬프가 필요하고, 장기검증 얘기가 여기서 나옵니다. 오늘은 이 정도로만 짚고 넘어가겠습니다.

웨일 쪽에서 판단하실 게 하나 있습니다. 이 기준시각을 사용자에게 보여줄 건지입니다. 안 보여주면 같은 문서인데 결과가 다르게 나올 때 왜 그런지 설명할 방법이 없고, 보여주면 일반 사용자한테는 안 읽히는 정보가 하나 늘어납니다.

# P09 — 기능 상세 ② 목록의 진위 보장과 동기화

**브레드크럼** 기능 › F4·F5 상세

### 슬라이드 문안

**거버닝 메시지**
> 목록을 받아오는 순간부터 목록은 공격 대상이 된다. 그래서 브라우저는 목록을 쓰기 전에 네 가지를 검사하고, 통과한 목록만 기존 목록을 대체한다.

**목록 수용 전 검사** — 규격 요구

1. 출처 확인 — 배포 주소가 합의된 주소인가
2. 목록 서명 검증 — 고정된 신뢰앵커로 검증되는가
3. 발행시각 확인 — 이전에 적용한 목록보다 새 것인가 (롤백 방지)
4. 유효기간 확인 — 만료되지 않았는가

**하나라도 실패하면 적용하지 않고, 기존 정상 목록을 유지한다.**

**동기화 상태별로 다뤄야 할 정보**

| 상태 | 다뤄야 할 정보 |
|---|---|
| 정상 적용 | 적용 버전, 발행시각, 유효기간, 마지막 동기화 시각 |
| 동기화 실패 | 실패 원인, 재시도 가능 여부, 기존 목록 유지 여부 |
| 캐시 사용 | 캐시 기준시각, 만료까지 남은 시간, 재검증 필요 여부 |
| 목록 없음 | 신뢰 판정 불가 상태임을 명시 |

### 열어 둘 질문 — 이 장의 핵심

| 판단할 것 | 선택지 | 대가 |
|---|---|---|
| **갱신 주기** | 짧게 (예: 6시간) | 상태 변경 반영이 빠르나 트래픽·배터리 부담 |
| | 길게 (예: 24시간~7일) | 부담이 작으나 철회 반영이 늦어짐 |
| **갱신 주체** | 브라우저 본체 | 구현이 단순하나 릴리스와 결합 |
| | 별도 컴포넌트 업데이트 | 독립적이나 관리 항목이 하나 늘어남 |
| **캐시 저장 위치** | OS 보안 저장소 | 보호 수준이 높으나 플랫폼별 구현이 갈림 |
| | 프로파일 내 암호화 저장 | 구현이 균일하나 보호 수준 판단 필요 |

현재 검토안은 기본 24시간 주기 + OS 보안 저장소이나, 웨일 플랫폼 정책에 맞춰 조정한다.

**신뢰앵커 변경 기능은 브라우저에 두지 않는다. 이 항목만 선택지가 아니다.**

### 발표 스크립트 (60초)

목록을 외부에서 받아온다는 건, 받아오는 경로가 공격 대상이 된다는 뜻입니다. 그래서 받은 걸 바로 쓰지 않고 네 가지를 검사합니다. 주소가 맞는지, 목록 서명이 검증되는지, 지금 쓰고 있는 것보다 새 건지, 만료 안 됐는지.

여기서 중요한 건 하나라도 실패했을 때입니다. 실패한 목록은 적용하지 않고, 기존에 잘 쓰고 있던 목록을 그대로 둡니다. 이상한 목록을 밀어 넣어서 정상 목록을 지워버리는 공격을 막기 위한 겁니다.

오른쪽이 오늘 가장 논의가 필요한 부분입니다. 세 가지를 정해야 하는데, 저희가 정하는 것보다 웨일 쪽 제약을 듣고 맞추는 게 맞다고 봅니다.

갱신 주기는 짧으면 철회가 빨리 반영되고 길면 부담이 적습니다. 갱신 주체를 브라우저 본체로 할지 별도 컴포넌트로 할지도 웨일 구조에 따라 다를 겁니다. 캐시를 어디 둘지도 마찬가지고요.

지금 검토안은 24시간 주기에 OS 보안 저장소인데, 확정이 아닙니다.

하나만 예외입니다. 맨 아래 줄인데, 신뢰앵커를 브라우저에서 바꿀 수 있게 하지는 않습니다. 앵커를 바꿀 수 있으면 앞의 네 가지 검사가 다 무의미해지기 때문에, 이건 선택지가 아니라 고정입니다.

# P10 — 검증 흐름에서 KR-TL이 개입하는 지점

**브레드크럼** 연동 › 검증 흐름

### 슬라이드 문안

**거버닝 메시지**
> KR-TL 조회는 검증의 전부가 아니라 네 번째 단계다. 앞 단계가 실패하면 조회까지 가지 않고, 조회 결과는 뒤 단계 결과를 대체하지 않는다.

**④에서 하는 일**
서명자 인증서의 발급자·서비스 식별정보를 적용 중인 KR-TL과 대조한다. 결과는 등록됨 / 미등록 / 서비스 철회 / 목록 만료 / 목록 접근 불가 / 목록 서명 오류로 구분한다.

**④에서 하지 않는 일**
문서 변조 판정, 서명값 유효성 판정, 폐지 여부 판정. 이 셋은 각각 ②③⑤의 결과다.

### 도식 — 가로 플로우

```
 PDF 열기
    │
    ▼
 ① 서명 존재 확인            로컬
    ▼
 ② 서명 구조 · ByteRange · 문서 무결성      로컬
    ▼
 ③ 서명값 검증 · 인증서 경로 구성           로컬
    ▼
 ④ KR-TL 대조                              목록 참조   ★
    서비스 등록 여부 · 상태 · 기준시각
    ▼
 ⑤ 인증서 상태 확인 (CRL / OCSP)           외부 통신
    ▼
 ⑥ 결과 산출
```

④만 강조색. 우측 라벨(로컬 / 목록 참조 / 외부 통신)을 세로로 정렬해 경계가 보이게 한다.

### 열어 둘 질문

④와 ⑤는 외부 통신이나 목록 참조가 필요하고 ①~③은 로컬에서 끝납니다. 로컬 결과를 먼저 표시하고 나머지를 나중에 채우는 방식이 웨일 렌더링 구조에서 자연스러운지, 아니면 한 번에 표시하는 편이 나은지 판단이 필요합니다.

### 발표 스크립트 (90초)

KR-TL이 검증 어디에 들어가는지 보겠습니다. 여섯 단계인데 KR-TL은 네 번째입니다.

①부터 ③까지는 로컬에서 끝납니다. 서명이 있는지, 문서가 서명 이후에 바뀌었는지, 서명값이 맞는지, 인증서 경로가 구성되는지. 여기서 실패하면 ④까지 가지도 않습니다. 문서가 변조됐으면 그 사업자가 인정받았는지 따질 필요가 없으니까요.

④에서 목록을 봅니다. 이 인증서를 발급한 서비스가 목록에 있는지, 어떤 상태인지, 그게 서명 시점 기준으로 어땠는지. 결과는 여섯 가지로 갈립니다. 등록됨, 미등록, 서비스 철회, 목록 만료, 목록 접근 불가, 목록 서명 오류.

⑤는 인증서 자체가 폐지됐는지 확인하는 단계입니다. 이건 목록이 아니라 CRL이나 OCSP를 봅니다. 목록과는 다른 정보입니다.

말씀드리고 싶은 건 아래 박스입니다. ④에서 안 하는 일이 있습니다. 목록에 없다는 게 문서가 변조됐다는 뜻이 아니고, 서명값이 틀렸다는 뜻도 아니고, 인증서가 폐지됐다는 뜻도 아닙니다. 그건 각각 다른 단계의 결과입니다. 이게 다음 장의 전제입니다.

# P11 — 결과를 어떻게 나눠 보여줄 것인가

**브레드크럼** 연동 › 결과 표시

### 슬라이드 문안

**거버닝 메시지**
> 변조·무효·미등록·확인불가는 원인도 대응도 다르다. 이를 같은 경고로 뭉치면 사용자는 정상 문서를 위조로 오인하거나 그 반대를 하게 된다.

**반드시 구분해야 할 네 가지** — 원칙

| 상황 | 원인 | 사용자가 할 수 있는 일 | 뭉쳤을 때의 사고 |
|---|---|---|---|
| 문서 변조 | 서명 이후 내용 변경 | 문서를 신뢰하지 않는다 | — |
| KR-TL 미등록 | 인정받지 않은 사업자의 서명 | 발급처를 확인한다 | 정상 문서를 위조로 오인 |
| 목록 접근 불가 | 네트워크·서버 장애 | 연결 후 재검증한다 | 장애를 위조로 오인 |
| 상태정보 미확인 | CRL/OCSP 응답 없음 | 재검증한다 | 확인 안 된 것을 정상으로 오인 |

**표시 체계** — 검토안, 확정 아님

| 아이콘 | 문구 | 언제 |
|---|---|---|
| 흰 원 | 서명 없음 | 서명이 포함되지 않은 PDF |
| 초록 방패 | 진본 확인 | 모든 축이 통과 |
| 노란 삼각형 | 주의 필요 | 미등록·철회 등 신뢰 판단에 유보가 필요 |
| 회색 하이픈 | 확인 불가 | 외부 정보 접근 실패, 제한 검증 |
| 빨간 방패 | 서명 무효 | 문서 변조 또는 서명값 검증 실패에 한정 |

### 열어 둘 질문

위쪽 네 가지를 구분한다는 원칙은 규격에서 오는 것이고, 아래쪽 아이콘·문구·상태 개수는 웨일 UX 판단 영역입니다. 5단계가 많다면 줄여도 되고, 웨일의 기존 보안 표시 체계와 맞추는 편이 나을 수도 있습니다. 웨일에서 안을 주시면 저희가 판정 로직을 맞추겠습니다.

### 발표 스크립트 (60초)

이 장은 기획 쪽에서 논의가 길어질 부분입니다. 위와 아래의 성격이 다르다는 걸 먼저 말씀드리고 싶습니다.

위쪽은 원칙입니다. 네 가지 상황은 원인이 다르고 사용자가 할 수 있는 일도 다릅니다. 문서가 변조된 거면 그 문서를 믿으면 안 되지만, 목록 서버가 잠깐 죽은 거면 나중에 다시 열어보면 됩니다. 이걸 같은 빨간 경고로 뭉치면, 멀쩡한 문서를 위조로 오인하게 만듭니다. 반대로 확인이 안 된 걸 정상으로 표시하면 더 위험하고요.

아래쪽은 저희 검토안입니다. 아이콘 다섯 개에 문구를 붙여봤는데, 이건 확정이 아닙니다. 다섯이 많다고 보시면 줄여도 되고, 웨일에 이미 있는 보안 표시 체계에 맞추는 게 나을 수도 있습니다. 그 판단은 웨일 쪽이 훨씬 잘하실 겁니다.

저희가 지켜야 하는 건 위쪽 원칙뿐이고, 아래는 안을 주시면 거기에 판정 로직을 맞추겠습니다.

# P12 — 오프라인·장애 시 동작

**브레드크럼** 연동 › 예외 처리

### 슬라이드 문안

**거버닝 메시지**
> 네트워크가 없어도 문서 열람은 멈추지 않되, 만료된 캐시로 정상 판정을 내리지 않는다. 이 두 문장이 오프라인 정책의 뼈대다.

**고정 원칙** — 조정 대상 아님

1. 어떤 경우에도 PDF 열람 자체는 차단하지 않는다.
2. 캐시는 서명·발행시각·유효기간을 재검증한 뒤 사용하고, 만료·손상 캐시는 폐기한다.
3. 제한 검증 결과에는 캐시 기준시각과 재검증 필요 여부를 함께 기록한다.

### 도식 — 분기

```
 동기화 시도
    │
    ├─ 성공 ──────────→ 목록 갱신 ──→ 온라인 검증
    │
    └─ 실패 ─┬─ 유효 캐시 있음 ──→ 제한 검증
             │                    → "확인 불가 / 재검증 필요" 표시
             │
             └─ 유효 캐시 없음 ──→ 신뢰 판정 보류
                                  → PDF 열람은 유지
```

우측 두 결과 박스에 "열람 유지" 공통 라벨을 붙인다.

### 열어 둘 질문

온라인 복귀 시 재검증을 자동으로 실행할지, 사용자가 요청할 때만 실행할지 판단이 필요합니다. 자동은 편하지만 사용자가 보고 있던 결과가 예고 없이 바뀝니다. 이 선택은 웨일 UX 원칙에 따르는 것이 맞습니다.

### 발표 스크립트 (45초)

네트워크가 없을 때입니다. 원칙은 두 개입니다.

문서 열람 자체는 어떤 경우에도 막지 않습니다. 검증이 안 된다고 PDF를 못 열게 하면 그건 브라우저 기능을 망가뜨리는 겁니다.

대신 만료된 캐시로 정상 판정을 내리지는 않습니다. 유효기간이 남은 캐시가 있으면 그걸로 제한적으로 검증하고, 결과에 "이건 캐시 기준이고 재검증이 필요하다"는 걸 같이 적습니다. 캐시도 없으면 신뢰 판정은 보류하되 문서는 그대로 열립니다.

여기도 하나 열어 두겠습니다. 다시 온라인이 됐을 때 알아서 재검증을 돌릴지, 사용자가 누를 때만 돌릴지입니다. 자동이 편하긴 한데 보고 있던 결과가 갑자기 바뀌는 게 괜찮은지는 웨일 UX 기준에 따라야 할 것 같습니다.

**거버닝 메시지**
> 현재는 웨일이 브라우저에서 보이고 저장되는 부분을, 일렉서티가 판정 로직과 결과코드를, KISA가 목록과 기준정보를 맡는 것으로 그려 두었다. 경계선의 위치는 조정 가능하다.

경계가 어색한 항목이 있는지 봐 주시기 바랍니다. 특히 캐시 저장·만료 관리를 SDK 안으로 넣는 편이 나을지 브라우저가 직접 들고 있는 편이 나을지는 양쪽 다 성립하므로, 웨일 쪽 선호를 듣고 정하겠습니다.

### 발표 스크립트 (60초)

"그래서 우리가 뭘 만들어야 하나"에 대한 현재 그림입니다. 제목에 초안이라고 붙여 뒀는데, 확정이 아니라는 뜻입니다.

웨일 쪽은 화면과 저장입니다. PDF를 열 때 서명이 있는지 보고 검증을 시작하는 부분, 상태를 어디에 어떻게 보여줄지, 설정에 KR-TL 항목을 두는 것, 그리고 받아온 목록을 어디에 보관하고 만료를 관리하는 것.

경계가 어색해 보이는 게 있으면 말씀해 주시면 좋겠습니다. 특히 캐시 관리는 SDK 안에 넣을 수도 있고 브라우저가 들 수도 있는데, 어느 쪽이 나은지는 웨일 구조를 보셔야 알 것 같습니다.

# P14 — 기존 신뢰체계와의 관계

**브레드크럼** 보완 › 영향 범위

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 브라우저의 기존 신뢰체계를 바꾸지 않는다. TLS 신뢰와는 층이 다르고, 문서 서명 신뢰체계와는 병존한다.

- KR-TL 적용이 기존 TLS 인증서 검증 경로에 개입하지 않는다.
- 하나의 문서가 여러 신뢰체계에서 동시에 검증될 수 있으며, KR-TL 미등록이 다른 체계의 판정을 부정하지 않는다.
- 판정 절차와 결과 표현은 국제 규격을 따르므로 결과를 국외 검증 도구와 대조할 수 있다.

### 도식 — 3층

```
┌──────────────────────────────────────────────────┐
│  TLS 연결 신뢰      Chromium Root Store            │  영향 없음
├──────────────────────────────────────────────────┤
│  문서 서명 신뢰     Adobe AATL · EUTL              │  병존
│                     KR-TL                          │  국내 인정제도 반영
├──────────────────────────────────────────────────┤
│  검증 절차 규격     ETSI EN 319 102-1              │  공통 판정 절차
└──────────────────────────────────────────────────┘
```

가운데 층만 강조. 위층은 회색으로 눌러 "건드리지 않는다"를 시각화한다.

### 열어 둘 질문

웨일이 Chromium 업스트림과의 차이를 관리하는 기준선이 있다면, 이 기능이 그 기준에서 어느 쪽에 놓이는지 판단해 주시면 구현 형태를 거기에 맞추겠습니다.

### 발표 스크립트 (45초)

기존 동작에 영향이 있느냐는 질문이 나올 것 같아서 미리 정리했습니다.

위층은 TLS입니다. 여기는 건드리지 않습니다. KR-TL 때문에 사이트 접속이 달라지는 일은 없습니다.

가운데가 문서 서명 신뢰입니다. Adobe가 쓰는 AATL이나 EU의 EUTL이 여기 있고, KR-TL도 여기 들어갑니다. 서로 배타적이지 않습니다. 한 문서가 여러 체계에서 동시에 검증될 수 있고, KR-TL에 없다고 해서 다른 체계의 판정을 부정하지 않습니다.

아래층은 판정 절차인데 국제 규격을 그대로 씁니다. 그래서 저희가 낸 결과를 EU 쪽 검증 도구에 넣어도 같은 결론이 나오는지 대조할 수 있습니다.

여섯 개 다 저희가 정하고 통보할 수 있는 것들이지만, 그러면 웨일 제품에 안 맞는 결정이 나옵니다. 웨일 구조와 UX 기준을 아는 쪽에서 판단하시는 게 맞다고 봤습니다.

오른쪽은 그 판단을 실제로 확인해 볼 무대입니다. 정상, 오프라인, 예외 세 가지 시나리오로 실증합니다. 예외 시나리오가 사실 제일 중요한데, 변조와 미등록과 확인 불가가 화면에서 제대로 구분돼 보이는지를 여기서 봅니다.

기능요구사항서 초안과 추적표는 따로 보내드리겠습니다. 항목별로 수용할지 조정할지 보류할지를 추적표에 기록하면서 진행하려고 합니다. 실증 완료 기준일은 12월 10일입니다.

이 여섯 개 중에 지금 답이 나오는 게 있으면 바로 정리하고, 나머지는 회신 시점만 정하고 마무리하면 좋겠습니다.

# 부록 1. 질의응답 대응

결론을 주는 형태가 아니라 판단 재료를 주는 형태로 답한다.

| 질문 | 답변 |
|---|---|
| 목록을 못 받아오면 브라우저가 느려지거나 멈추는가 | 검증은 비동기로 돌고 PDF 열람 경로와 분리되어 있습니다. 목록 조회가 실패하면 그 결과 축만 확인 불가로 처리되고 문서는 그대로 열립니다. |
| 목록 크기와 갱신 부담은 어느 정도인가 | 국내 인정사업자 수 기준이라 목록 자체가 큽니다. 조건부 요청으로 변경이 없으면 본문을 받지 않는 방식이 가능하고, 실제 주기는 웨일 판단에 맞추겠습니다. |
| 신뢰앵커가 브라우저에 박히면 교체는 어떻게 하는가 | 실증 단계에서는 고정으로 둡니다. 앵커 갱신 절차는 KISA 운영정책 항목이고, 웨일 배포 체계와 맞물리는 부분이라 별도로 다뤄야 합니다. |
| 사용자에게 "미등록"을 어떻게 설명하나 | 무효가 아니라 "확인된 인정사업자 목록에 없음"이라는 사실 진술이 성립합니다. 실제 문구는 웨일 UX 기준으로 정하시는 게 맞습니다. |
| PDF 원문이 외부로 나가는가 | 나가지 않습니다. 외부 조회에는 식별정보와 해시만 전송하고 보고서에도 원문을 넣지 않습니다. |
| Chromium 업스트림과 충돌하지 않나 | TLS 신뢰 경로에 개입하지 않고 PDF 뷰어 쪽에서 동작합니다. 업스트림 차이 관리 기준은 웨일 쪽 판단을 따르겠습니다. |
| 이거 우리가 꼭 해야 하는 건가 | 참여 범위는 협의 대상입니다. 다만 브라우저에서 문서 서명 상태를 표시하려면 신뢰 판단 근거가 필요하고, 지금은 그 근거가 없다는 게 출발점입니다. |

마지막 질문은 반드시 준비해 둔다. 사전 공유 자리에서 가장 나올 법한 질문이고, 여기서 방어적으로 답하면 이후 협의가 어려워진다.

*목록 크기 관련 답변의 "작습니다"는 인정사업자 수를 확인한 뒤 확정한다.*

# 부록 3. 슬라이드 제작 지침

**공통 레이아웃 (16:9)**

```
┌──────────────────────────────────────────────────────┐
│  KR-TL 신뢰목록 개요            기능 › F4·F5 상세      │  헤더
├──────────────────────────────────────────────────────┤
│  거버닝 메시지 — 1문장, 좌측 색 띠                     │
├──────────────────────────────────────────────────────┤
│                                                      │
│  본문 — 도식 또는 표                                  │
│                                                      │
├──────────────────────────────────────────────────────┤
│  ? 열어 둘 질문 — 회색 박스, 본문과 구분              │
├──────────────────────────────────────────────────────┤
│  ㈜일렉서티                                    09/15  │  푸터
└──────────────────────────────────────────────────────┘
```

**규칙**

- 배경은 흰색. 도식은 벡터·플랫로 그리고 그림자와 그라디언트를 쓰지 않는다.
- 본문 10~14pt, 거버닝 메시지 16pt, 슬라이드 제목 20pt.
- 강조색은 한 가지만 쓴다. 나머지는 회색 계열로 눌러 강조 대상이 하나로 보이게 한다.
- 표는 헤더 행에만 배경색을 넣고 본문 행에는 넣지 않는다.
- "열어 둘 질문" 박스는 모든 페이지에서 같은 위치·같은 회색으로 둔다. 질문이 없는 페이지(P01, P04, P07 일부)는 박스 자체를 빼고 본문 영역을 넓힌다.
- 아이콘은 P11에서만 쓴다. 다른 페이지에서 장식용 아이콘을 넣지 않는다.

**확정과 검토안의 시각 구분**

| 성격 | 표기 |
|---|---|
| 규격·제도상 고정 | 표 우측에 "규격" / "제도" 라벨 |
| 안전성 요건, 조정 불가 | 굵게 + 좌측 색 띠 |
| 우리 검토안 | 표 제목에 "검토안" 명시, 회색 배경 |
| 웨일 판단 영역 | 하단 "열어 둘 질문" 박스로 분리 |

이 네 가지가 시각적으로 구분되지 않으면 자료 전체의 취지가 무너진다. HTML 스케치 단계에서 가장 먼저 확인할 항목이다.
