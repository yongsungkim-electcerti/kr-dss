# P02 — 지금 PDF 서명을 열면

**브레드크럼** 문제 › 현재 상황

### 슬라이드 문안

**거버닝 메시지**
> 브라우저는 서명값이 맞는지는 확인하지만 그 인증서를 발급한 사업자를 믿어도 되는지는 답하지 못한다. 그리고 더 큰 문제는, 일반 사용자가 서명을 확인해야 한다는 사실 자체를 모른다는 것이다.

**우측 상단 — 확인되는 것** (로컬에서 계산 가능)

- 문서 무결성
- 서명값 일치
- 인증서 유효기간

**우측 하단 — 확인되지 않는 것** (외부 근거가 필요)

- 발급 사업자가 인정받은 곳인가
- 서명 시점에 그 사업자가 정상이었는가
- 이 인증서가 어떤 용도로 발급된 것인가
- 폐지·정지 여부를 어디서 확인하는가

**하단 강조 밴드**
> 사용자는 왼쪽 화면에서 "이 문서에 서명이 붙어 있다"는 사실조차 인지하지 못한다. 확인할 수단이 없는 것이 아니라, 확인해야 한다는 것을 모른다.

### 도식 — 좌우 이등분

```
┌──────────────────────────┬──────────────────────────┐
│                          │  확인되는 것              │
│   [ PDF 뷰어 화면 캡처 ]   │  · 문서 무결성            │
│                          │  · 서명값 일치            │
│   assets/                │  · 인증서 유효기간         │
│   p02_pdf_viewer.png     │        로컬에서 계산 가능   │
│                          ├──────────────────────────┤
│   서명된 PDF를 브라우저    │  확인되지 않는 것          │
│   내장 뷰어로 연 상태      │  · 발급 사업자가 인정받은  │
│                          │    곳인가                 │
│                          │  · 서명 시점에 정상이었나  │
│                          │  · 어떤 용도로 발급됐나    │
│                          │  · 폐지·정지는 어디서 보나 │
│                          │        외부 근거가 필요     │
└──────────────────────────┴──────────────────────────┘
      하단 밴드 — 사용자는 확인해야 한다는 것을 모른다
```

좌측은 캡처 자리표시 박스(점선). 우측은 상단 회색·하단 강조색 카드 2단.

### 발표 스크립트 (90초)

왼쪽이 지금 브라우저에서 전자서명된 PDF를 연 화면입니다. 보시면 이 문서에 서명이 붙어 있다는 표시가 없거나, 있어도 무슨 뜻인지 알 수 없습니다.

오른쪽 위가 브라우저가 확인할 수 있는 것들입니다. 문서가 서명 이후에 바뀌었는지, 서명값이 인증서 공개키로 검증되는지, 인증서 유효기간이 지났는지. 이건 전부 로컬에서 계산으로 끝납니다.

오른쪽 아래가 확인되지 않는 것들입니다. 그 인증서를 발급한 곳이 국가가 인정한 사업자인지, 서명하던 시점에 그 사업자가 정상 상태였는지, 이 인증서가 문서 서명용으로 발급된 건지. 이건 계산으로 안 나옵니다. 외부에 근거가 있어야 합니다.

그런데 오늘 말씀드리고 싶은 진짜 문제는 아래 밴드입니다. 기술적으로 확인이 안 되는 것보다 앞선 문제가 있습니다. 사용자가 이 문서의 서명을 확인해야 한다는 것 자체를 모릅니다. 확인 수단을 만들어 놔도 찾아 들어가지 않습니다. 그래서 브라우저가 문서를 여는 순간 자동으로 판단하고 보여주는 구조가 필요하다고 봤습니다.

혹시 웨일에서는 지금 서명 붙은 PDF를 어떻게 처리하고 계신지 여쭤봐도 될까요.

# P03 — PKI 전자서명 인증 체계

**브레드크럼** 배경 › 기존 신뢰체계

### 슬라이드 문안

**거버닝 메시지**
> 전자서명의 신뢰는 지금까지 인증서 경로 검증으로 해결해 왔다. 서명자 인증서에서 신뢰앵커까지 경로가 하나로 이어질 때만 성립하는 방식이다.

**좌측 — CMS 구조와 인증서 체인 검증** (별도 이미지 삽입)

이 영역은 **이미지 삽입 박스로 비워 둔다.** 기존 자료의 CMS 구조·체인 검증 도식을 그대로 쓰거나 별도 제작해 `assets/p03_cms_chain.png`로 저장한다. 파일을 두면 자리표시 박스가 자동으로 대체된다.

이미지에 담길 내용은 다음과 같다. 서명 데이터는 CMS(SignedData) 구조에 담기고, 그 안의 서명자 정보에서 인증서 체인을 따라 올라가 신뢰앵커에 도달하는지를 검증한다. SignedData → 서명자 인증서 → 중간 CA → 루트(신뢰앵커)로 이어지는 세로 체인이 보이면 된다.

박스 아래에는 보조 정보 2행만 남긴다.

| 항목 | 내용 |
|---|---|
| 경로 제약 | 유효기간 · Basic Constraints · Key Usage · 정책 |
| 폐지 상태 | CRL / OCSP |

**우측 상단 — GPKI · NPKI 구조**

행정 영역의 GPKI와 민간 영역의 NPKI가 각각 최상위 인증기관을 두고, 두 체계를 연결해 경로가 이어지도록 운영해 왔다. 어느 쪽에서 발급한 인증서든 검증하는 쪽이 도달할 수 있는 앵커가 있었다.

**우측 하단 — 민간사업자 개별 구조**

전자서명 인증사업자가 다원화되면서 사업자별로 독립된 체계가 만들어졌다. 사업자 사이를 잇는 경로가 없고, 검증하는 쪽이 도달할 공통 앵커도 없다.

**하단 강조**
> 경로가 끊긴 곳에서는 경로 검증이 성립하지 않는다. 이용기관은 사업자별 앵커를 개별 수집해 코드에 넣는 방식으로 대응하고 있다.

### 도식 — 좌 1 / 우 2단

```
┌─────────────────────────┬────────────────────────────────┐
│  CMS 구조와 체인 검증     │  GPKI · NPKI 구조               │
│                         │                                │
│  ┌───────────────────┐  │   [GPKI Root]   [NPKI Root]    │
│  │                   │  │        │             │         │
│  │  이미지 삽입 박스   │  │     행정 서명      민간 서명     │
│  │  p03_cms_chain.png│  │        └──── 연결 ────┘        │
│  │                   │  │        경로가 이어진다           │
│  └───────────────────┘  ├────────────────────────────────┤
│                         │  민간사업자 개별 구조             │
│  경로 제약  유효기간 ···  │                                │
│  폐지 상태  CRL / OCSP   │  [A사]   [B사]   [C사]   [D사]  │
│                         │   각자 루트 · 상호 연결 없음      │
│                         │        ✕  경로 단절              │
└─────────────────────────┴────────────────────────────────┘
   하단 — 경로가 끊긴 곳에서는 경로 검증이 성립하지 않는다
```

좌측 박스는 점선 자리표시로 두고, 이미지가 들어가면 그 자리를 채운다. 아래 보조 표 2행은 그대로 남긴다.

우측 하단 블록만 경고 톤(주황 계열 점선)으로 처리해 단절을 시각화한다.

### 발표 스크립트 (90초)

KR-TL 얘기를 하기 전에, 지금까지 전자서명 신뢰를 어떻게 해결해 왔는지 짚고 가겠습니다.

왼쪽 그림이 기본 구조입니다. 서명 데이터는 CMS라는 구조에 담깁니다. 그 안에 서명자 정보가 있고, 거기서 인증서를 따라 위로 올라갑니다. 서명자 인증서에서 중간 CA로, 중간 CA에서 루트로. 이 경로가 신뢰앵커까지 이어지면 검증이 성립합니다. 여기에 유효기간이나 폐지 상태 확인이 붙습니다. 이걸 경로 검증이라고 합니다.

오른쪽 위가 우리가 오래 써온 구조입니다. 행정 쪽 GPKI와 민간 쪽 NPKI가 각각 최상위를 두고, 둘을 연결해서 경로가 끊기지 않게 운영했습니다. 어느 쪽 인증서든 검증하는 쪽에서 올라갈 수 있는 앵커가 있었습니다.

오른쪽 아래가 지금입니다. 인증사업자가 여럿으로 늘어나면서 사업자마다 독립된 체계가 생겼습니다. 서로 연결이 없습니다. A사 인증서로 서명한 문서를 B사 앵커로는 검증할 수 없고, 둘을 잇는 상위 구조도 없습니다.

경로 검증은 경로가 이어져 있을 때만 되는 방식입니다. 경로가 끊기면 방법이 없습니다. 그래서 지금은 이용기관이 사업자별 앵커를 하나씩 모아서 코드에 박아 놓고 씁니다. 이게 앞 장에서 말씀드린 "확인되지 않는 것"의 실제 원인입니다.

웨일이 지금 문서 서명 검증에 쓰는 신뢰앵커가 있다면 어디서 오는지, 그 목록을 어떻게 갱신하고 계신지도 알고 싶습니다.

# P04 — 신뢰목록이란 무엇인가

**브레드크럼** 개념 › 정의

### 슬라이드 문안

**거버닝 메시지**
> 신뢰목록은 국가가 인정한 전자서명 사업자와 그 서비스의 현재·과거 상태를, 국가가 서명해 배포하는 기계판독 목록이다. 끊어진 경로를 잇는 대신, 신뢰의 근거를 목록으로 옮긴 방식이다.

**성립 조건 네 가지**

| 조건 | 의미 | 근거 |
|---|---|---|
| 권위 있는 발행자 | 목록 발행 주체가 인정제도 운영 기관과 일치한다 | 제도 |
| 기계판독 | 사람이 읽는 공고문이 아니라 검증 소프트웨어가 파싱하는 XML이다 | 규격 |
| 서명된 목록 | 목록 자체가 전자서명되어 위·변조를 검출한다 | 규격 |
| 이력 보존 | 현재 상태만이 아니라 언제부터 그 상태였는지를 담는다 | 규격 |

**참고**
EU는 eIDAS 체계에서 ETSI TS 119 612 규격의 Trusted List를 회원국별로 발행하고, 이를 LOTL로 묶어 배포한다. KR-TL은 같은 구조를 국내 인정제도에 맞춰 적용한 것이다.

**하단 강조**
> 인증서 목록이 아니라 서비스 상태 목록이다.

### 발표 스크립트 (60초)

그래서 나온 게 신뢰목록입니다. 접근이 다릅니다. 끊어진 경로를 억지로 잇는 대신, 신뢰의 근거를 목록으로 옮깁니다.

정의는 이렇습니다. 국가가 인정한 전자서명 사업자와 그 서비스의 상태를, 국가가 직접 서명해서 배포하는 목록.

네 가지가 갖춰져야 신뢰목록이라고 할 수 있습니다. 발행 주체가 실제로 인정제도를 운영하는 기관이어야 하고, 사람이 읽는 공고가 아니라 소프트웨어가 파싱하는 형식이어야 하고, 목록 자체에 서명이 붙어 있어야 하고, 과거 이력이 남아 있어야 합니다.

오른쪽 근거 열을 보시면 첫 줄만 제도에서 오고 나머지 셋은 규격에서 옵니다. 이 구분을 오늘 자료 전체에서 유지하려고 합니다. 규격이라 어쩔 수 없는 것과 저희가 제안하는 걸 섞어 놓으면 어디를 조정할 수 있는지 안 보이니까요.

하나만 기억해 주시면 좋겠습니다. 이건 인증서 목록이 아니라 서비스 상태 목록입니다.

# P05 — 신뢰목록 사용, 지금은 수동이다

**브레드크럼** 개념 › 현재 이용 방식

### 슬라이드 문안

**거버닝 메시지**
> 지금은 확인이 필요할 때 사람이 각 인증센터에 접속해 눈으로 대조한다. 신뢰목록은 이 확인을 검증 소프트웨어가 하도록 옮기는 것이다.

**좌측 — 적용 전: 인증센터 수동관리** (현재)

상단은 인증센터 조회 화면 캡처(`assets/p05_ca_manual.png`), 하단은 절차 4단계.

| 단계 | 주체 | 동작 |
|---|---|---|
| 1 | 담당자 | 사업자별 인증센터 사이트에 접속 |
| 2 | 담당자 | 인증서·서비스 정보를 화면에서 조회 |
| 3 | 담당자 | 유효 여부를 눈으로 대조 |
| 4 | 담당자 | 필요 시 앵커를 내려받아 시스템에 반영 |

**우측 — 적용 후: 인증센터 자동연결 구조** (신뢰목록 적용)

| 단계 | 주체 | 동작 |
|---|---|---|
| 1 | KISA | 인정사업자 정보를 수집해 KR-TL 발행·서명 |
| 2 | 브라우저 | 배포 주소에서 목록을 주기 동기화 |
| 3 | 브라우저 | 목록 서명·발행시각·유효기간 검증 후 적용 |
| 4 | 검증 엔진 | 문서를 열 때 목록을 조회해 자동 판정 |
| 5 | 사용자 | 결과를 화면에서 즉시 확인 |

**하단 강조**
> 사람이 하는 확인은 재현되지 않고 근거도 남지 않는다. 사업자가 늘어날수록 확인 비용이 사업자 수만큼 늘어난다.

### 도식 — 좌우 이등분 (적용 전 → 적용 후)

```
┌──────────────────────────┬──────────────────────────┐
│  적용 전 · 수동관리 (현재)  │  적용 후 · 자동연결 구조    │
│                          │                          │
│   [ 인증센터 화면 캡처 ]    │  KISA                    │
│                          │   └ KR-TL 발행·서명       │
│   assets/                │        │ 주기 동기화       │
│   p05_ca_manual.png      │        ▼                 │
│                          │  브라우저                  │
│   1. 사이트 접속           │   └ 목록 검증 후 적용      │
│   2. 정보 조회            │        │                 │
│   3. 눈으로 대조           │        ▼                 │
│   4. 수동 반영            │  검증 엔진 → 자동 판정      │
│                          │        │                 │
│   사업자 수만큼 반복        │        ▼                 │
│                          │  사용자 — 즉시 확인         │
└──────────────────────────┴──────────────────────────┘
```

좌측은 캡처 자리표시 + 단계 목록(회색 톤), 우측은 세로 흐름 도식(강조색). 왼쪽에서 오른쪽으로 읽으면 현재 → 지향이 된다.

### 발표 스크립트 (75초)

신뢰목록이 없으면 지금 어떻게 하고 있는지부터 보겠습니다. 왼쪽입니다.

확인이 필요하면 담당자가 각 사업자 인증센터 사이트에 들어갑니다. 거기서 인증서 정보를 찾아 화면으로 봅니다. 유효한지 눈으로 대조하고, 필요하면 앵커를 내려받아 시스템에 넣습니다. 이걸 사업자 수만큼 반복합니다.

문제는 두 가지입니다. 사람이 한 확인은 재현이 안 됩니다. 어제 확인한 사람과 오늘 확인한 사람의 결과가 다를 수 있고, 왜 그렇게 판단했는지 근거가 남지 않습니다. 그리고 사업자가 늘어날수록 비용이 그만큼 늘어납니다.

오른쪽이 신뢰목록을 적용한 뒤입니다. KISA가 인정사업자 정보를 모아 목록으로 만들고 서명해서 배포합니다. 브라우저는 그 주소에서 주기적으로 목록을 받아 검증하고 적용합니다. 문서를 열면 검증 엔진이 목록을 조회해서 자동으로 판정하고, 사용자는 결과를 바로 봅니다.

사람이 하던 확인을 소프트웨어가 하게 만드는 것, 그게 신뢰목록의 실질입니다.

혹시 웨일에서 외부 기준정보를 주기적으로 받아 쓰는 기존 사례가 있으면, 그 갱신 경로를 재사용할 수 있을지 궁금합니다.

# P06 — KR-TL의 구조

**브레드크럼** 구조 › 데이터 모델

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 ETSI TS 119 612 구조를 따르며, 계층은 스킴 → 사업자 → 서비스 → 상태 이력 네 단으로 내려간다.

**검증에서 실제로 쓰는 것 세 가지**

- 신뢰앵커로 쓰는 것은 Service의 **Digital Identity**다.
- 판정에 쓰는 것은 상태값 하나가 아니라 **상태값과 개시시각의 쌍**이다.
- 같은 사업자라도 서비스별로 상태가 다를 수 있으므로 **서비스 단위**로 조회한다.

### 도식 — 계층 트리

```
Scheme  스킴 정보
├─ 운영 주체 · 스킴 유형 · 적용 국가 · 목록 일련번호
├─ 발행시각 · 다음 갱신 예정시각
│
└─ TSP  전자서명인증사업자
   ├─ 사업자명 · 사업자 식별자 · 소재지
   │
   └─ Service  서비스
      ├─ 서비스 유형          인증서 발급 / 타임스탬프 / 검증
      ├─ 서비스 명칭
      ├─ Digital Identity     서비스 인증서 · 공개키 · SKI      ★
      ├─ 현재 상태 + 상태 개시시각                              ★
      ├─ 상태 이력            과거 상태와 각 개시시각            ★
      └─ 부가 정보            정책 OID · OCSP/CRL 주소
```

★ 표시한 세 항목만 강조색, 나머지는 회색.

### 발표 스크립트 (90초)

구조는 ETSI TS 119 612를 따릅니다. EU가 쓰는 것과 같은 규격입니다.

네 단입니다. 맨 위가 스킴 정보고, 이 목록이 언제 발행됐고 다음 갱신이 언제인지가 여기 들어갑니다. 그 아래가 사업자, 그 아래가 서비스입니다. 서비스가 실질적인 단위입니다.

별표 친 세 개만 봐 주시면 됩니다.

첫째, Digital Identity. 서비스 인증서가 들어 있고, 검증 엔진이 인증서 경로를 만들 때 이게 종착점이 됩니다. 앞에서 말씀드린 "끊어진 경로의 앵커를 어디서 가져오느냐"의 답이 여기 있습니다.

둘째, 상태값과 개시시각이 한 쌍이라는 점. 지금 인정 상태라는 정보만으로는 부족합니다. 서명은 과거에 이뤄졌으니 그 시점의 상태를 알아야 합니다.

셋째, 상태 이력. 과거에 어떤 상태였고 그게 언제부터였는지가 전부 남아 있습니다. 목록이 현재 스냅샷이 아닌 이유입니다.

브라우저가 이 XML을 통째로 들고 있을지, 파싱해서 필요한 것만 남길지는 저희가 정할 문제가 아니라서 열어 두겠습니다.

# P07 — 제공 기능 5가지

**브레드크럼** 기능 › 전체

### 슬라이드 문안

**거버닝 메시지**
> KR-TL은 신뢰앵커 제공, 시점 기준 상태 판정, 서비스 유형 구분, 목록의 진위 보장, 배포·동기화 다섯 가지 기능을 제공한다. 검증 엔진이 KR-TL에 요청하는 모든 것은 이 다섯 안에 들어온다.

| | 기능 | 무엇을 해주는가 | 없으면 |
|---|---|---|---|
| F1 | 신뢰앵커 제공 | 인증서 경로 구성의 종착점이 될 서비스 인증서를 목록으로 내려준다 | 이용기관이 앵커를 직접 수집·하드코딩 |
| F2 | 시점 기준 상태 판정 | 서명 시점에 그 서비스가 어떤 상태였는지를 소급해 판정한다 | 과거 서명이 사업자 지위 변경만으로 무효화 |
| F3 | 서비스 유형 구분 | 서명용·타임스탬프·검증 서비스를 구분해 용도 밖 사용을 걸러낸다 | 타임스탬프용 인증서로 문서 서명해도 통과 |
| F4 | 목록의 진위 보장 | 목록에 서명·발행시각·유효기간을 부여해 위조와 노후화를 막는다 | 신뢰 판단의 근거 자체가 공격 대상 |
| F5 | 배포·동기화 | 정해진 주소에서 주기적으로 목록을 받아 최신 상태를 유지한다 | 상태 변경이 검증 시점에 반영되지 않음 |

**하단 강조**
> F1~F3은 검증 엔진이 소비하는 기능이고, F4~F5는 브라우저 쪽에 실제 기능이 생기는 영역이다. 다음 세 장이 F4·F5와 F1의 실제 동작이다.

### 도식

5칸 가로 배열. 각 칸에 기능 번호 / 기능명 / 설명 / "없으면". F4·F5 칸만 강조 테두리.

### 발표 스크립트 (150초)

오늘 자료의 중심입니다. KR-TL이 해주는 일을 다섯 개로 정리했습니다.

F1, 신뢰앵커 제공. 인증서 경로를 만들 때 어디까지 올라가서 멈출지, 그 종착점을 목록이 내려줍니다. 앞에서 본 단절된 구조에서 각 사업자 앵커를 코드에 박던 걸 대신합니다.

F2, 시점 기준 상태 판정. 지금 상태가 아니라 서명하던 그 시점의 상태로 판정합니다. 사업자가 나중에 인정이 취소됐다는 이유로 3년 전에 정상적으로 서명한 문서가 전부 무효가 되면 곤란하니까요.

F3, 서비스 유형 구분. 타임스탬프용으로 발급된 인증서로 문서를 서명하면 걸러냅니다. 목록에 서비스 유형이 들어 있어서 가능합니다.

F4와 F5가 웨일 입장에서 중요합니다. 앞의 셋은 검증 엔진이 목록을 읽어서 쓰는 거라 SDK 안에서 처리됩니다. 그런데 F4와 F5는 브라우저에 실제로 기능이 생깁니다.

F4는 목록 자체를 믿을 수 있게 만드는 겁니다. 목록을 외부에서 받아오는 순간부터 목록이 공격 대상이 되니까, 받아온 걸 그대로 쓰면 안 됩니다.

F5는 그걸 주기적으로 받아오는 기능입니다. 언제 받아올지, 못 받아오면 어떻게 할지, 받아온 걸 어디에 둘지가 전부 여기 딸려 옵니다.

다음 세 장에서 F4, F5, 그리고 실제 조회를 차례로 보겠습니다.

다섯 개 중에 웨일에서 부담이 큰 것과 작은 것이 어떻게 갈리는지 들어보고 싶습니다. 특히 F5의 갱신 주체를 브라우저 본체로 볼지 별도 컴포넌트로 볼지는 웨일 구조를 아는 쪽에서 판단하시는 게 정확합니다.

# P08 — 상세 기능: 배포시점 확인 · 목록 진위 확인

**브레드크럼** 기능 › F4 상세

### 슬라이드 문안

**거버닝 메시지**
> 목록을 받아오는 순간부터 목록은 공격 대상이 된다. 브라우저는 쓰기 전에 배포시점과 진위를 각각 확인하고, 네 가지를 모두 통과한 목록만 기존 목록을 대체한다.

**좌측 — 배포시점 확인**

| 확인 항목 | 판단 |
|---|---|
| 발행시각 | 지금 적용 중인 목록보다 새 것인가 — 롤백 방지 |
| 다음 갱신 예정시각 | 갱신 주기를 넘겨 방치되고 있지 않은가 |
| 유효기간 | 만료되지 않았는가 |

만료된 목록은 정상 신뢰 판정에 사용하지 않는다. 기존 목록보다 오래된 목록으로 교체하지 않는다.

**우측 — 목록 진위 확인**

| 확인 항목 | 판단 |
|---|---|
| 출처 | 배포 주소가 합의된 주소인가 |
| 목록 서명 | 고정된 신뢰앵커로 서명이 검증되는가 |
| 서명자 | 목록 서명자가 지정된 발행 주체인가 |

신뢰앵커는 브라우저에서 변경할 수 없다. 앵커가 바뀔 수 있으면 나머지 검사가 모두 무의미해진다.

**하단 강조 (조정 대상 아님)**
> 네 가지 중 하나라도 실패하면 적용하지 않고, 기존 정상 목록을 그대로 유지한다. 실패한 목록이 정상 목록을 밀어내지 않는다.

### 도식 — 좌우 2단 + 하단 밴드

각 단은 검사 항목 표 + 규칙 문장. 하단 밴드는 검은 좌측 띠로 "조정 대상 아님"을 표시.

### 발표 스크립트 (60초)

목록을 외부에서 받아온다는 건, 받아오는 경로가 공격 대상이 된다는 뜻입니다. 그래서 받은 걸 바로 쓰지 않고 두 가지를 확인합니다.

왼쪽은 배포시점입니다. 이 목록이 지금 쓰는 것보다 새 건지, 갱신 주기를 넘겨 방치된 건 아닌지, 만료되지 않았는지. 특히 첫 줄이 중요합니다. 오래된 목록을 다시 밀어 넣어서 이미 철회된 사업자를 정상으로 되돌리는 공격을 막습니다.

오른쪽은 목록 자체의 진위입니다. 합의된 주소에서 온 게 맞는지, 목록 서명이 고정된 앵커로 검증되는지, 서명한 주체가 지정된 발행 기관인지.

여기서 앵커는 브라우저에서 바꿀 수 없게 합니다. 앵커를 바꿀 수 있으면 앞의 검사가 전부 의미가 없어지니까요. 이건 선택지가 아니라 고정입니다.

아래 밴드가 규칙입니다. 하나라도 실패하면 적용하지 않고 기존 목록을 그대로 둡니다. 이상한 목록을 밀어 넣어서 정상 목록을 지워버리는 걸 막기 위한 겁니다.

이 앵커를 브라우저 어디에 두는 게 웨일 배포 구조에서 자연스러운지는 여쭤보고 싶습니다. 앵커 갱신 절차는 KISA 운영정책 항목이라 오늘은 빼겠습니다.

**거버닝 메시지**
> 목록은 브라우저 릴리스와 무관하게 갱신된다. 그래서 브라우저에 동기화 기능이 새로 생기고, 주기·주체·저장 위치를 정해야 한다.

| 항목 | 선택지 | 대가 |

| | 길게 (24시간~7일) | 부담이 작으나 철회 반영이 늦어짐 |
| 갱신 주체 | 브라우저 본체 | 구현이 단순하나 릴리스와 결합 |

| | 프로파일 내 암호화 저장 | 구현이 균일하나 보호 수준 판단 필요 |

현재 검토안은 기본 24시간 주기 + OS 보안 저장소이나, 웨일 플랫폼 정책에 맞춰 조정한다.

### 발표 스크립트 (60초)

앞 장이 받은 목록을 검사하는 얘기였다면, 이 장은 그 목록을 언제 어떻게 받아오느냐입니다.

위쪽이 필요한 기능입니다. 주기적으로 자동으로 받아오고, 설정에서 수동으로도 받을 수 있고, 지금 어떤 목록을 쓰고 있는지 상태가 보이고, 실패하면 왜 실패했는지 알 수 있어야 합니다. 마지막 줄은 구현 시 놓치기 쉬운 부분인데, 이전 동기화가 돌고 있으면 새로 시작하지 않게 해야 합니다.

아래가 오늘 가장 논의가 필요한 부분입니다. 세 가지를 정해야 하는데, 저희가 정해서 통보하는 것보다 웨일 쪽 제약을 듣고 맞추는 게 맞다고 봅니다.

갱신 주기는 짧으면 철회가 빨리 반영되고 길면 부담이 적습니다. 갱신 주체를 브라우저 본체로 할지 별도 컴포넌트로 할지도 웨일 구조에 따라 다를 겁니다. 캐시를 어디 둘지도 마찬가지고요.

지금 검토안은 24시간 주기에 OS 보안 저장소인데, 확정이 아닙니다.

어느 조합이 웨일에 맞는지 의견을 주시면 저희가 판정 로직과 결과코드를 거기에 맞추겠습니다.

# P10 — 핵심 검증: 목록 조회

**브레드크럼** 검증 › 목록 조회

### 슬라이드 문안

**거버닝 메시지**
> 목록 조회는 검증의 전부가 아니라 네 번째 단계다. 앞 단계가 실패하면 조회까지 가지 않고, 조회 결과는 뒤 단계 결과를 대체하지 않는다.

**검증 흐름**

① 서명 존재 확인 → ② 서명 구조·ByteRange·문서 무결성 → ③ 서명값 검증·인증서 경로 구성 → **④ 목록 조회** → ⑤ 인증서 상태 확인(CRL/OCSP) → ⑥ 결과 산출

①~③ 로컬 · ④ 목록 참조 · ⑤ 외부 통신

**좌측 — 조회에 넣는 것**

| 입력 | 내용 |
|---|---|
| 발급자 식별정보 | 서명자 인증서의 발급자 |
| 서비스 식별정보 | 서비스 인증서·공개키·SKI 대조값 |
| 판정 기준시각 | 서명시각 또는 시각증거 기준 |

**우측 — 조회에서 나오는 것**

| 결과 | 의미 |
|---|---|
| 등록됨 | 목록에 있고 해당 시점 인정 상태 |
| 미등록 | 목록에 없음 |
| 서비스 철회 | 목록에 있으나 해당 시점 철회 상태 |
| 목록 만료 | 적용 중인 목록의 유효기간 경과 |
| 목록 접근 불가 | 목록을 가져오지 못함 |
| 목록 서명 오류 | 목록 진위 검증 실패 |

**하단 강조**
> 조회가 하지 않는 일 — 문서 변조 판정, 서명값 유효성 판정, 폐지 여부 판정. 이 셋은 각각 ② ③ ⑤의 결과다.

### 도식

상단에 6단계 가로 흐름 바(④만 강조), 하단에 입력/출력 2단 표.

### 발표 스크립트 (90초)

목록을 받아 놨으면 이제 씁니다. 검증 흐름에서 어디에 들어가는지 보겠습니다.

여섯 단계인데 목록 조회는 네 번째입니다. ①부터 ③까지는 로컬에서 끝납니다. 서명이 있는지, 문서가 서명 이후에 바뀌었는지, 서명값이 맞는지, 인증서 경로가 구성되는지. 여기서 실패하면 ④까지 가지도 않습니다. 문서가 변조됐으면 그 사업자가 인정받았는지 따질 필요가 없으니까요.

④에서 목록을 봅니다. 왼쪽이 넣는 값입니다. 서명자 인증서의 발급자 정보, 서비스를 식별할 수 있는 값, 그리고 판정 기준시각. 기준시각이 들어가는 게 중요합니다. 지금이 아니라 서명한 시점으로 판정하니까요.

오른쪽이 나오는 값입니다. 여섯 가지로 갈립니다. 등록됨, 미등록, 서비스 철회, 목록 만료, 목록 접근 불가, 목록 서명 오류.

말씀드리고 싶은 건 아래 밴드입니다. 목록에 없다는 게 문서가 변조됐다는 뜻이 아니고, 서명값이 틀렸다는 뜻도 아니고, 인증서가 폐지됐다는 뜻도 아닙니다. 그건 각각 다른 단계의 결과입니다. 이게 다음 장의 전제입니다.

하나 여쭤보면, ④와 ⑤는 외부 참조가 필요하고 ①~③은 로컬에서 끝납니다. 로컬 결과를 먼저 표시하고 나머지를 나중에 채우는 방식이 웨일 렌더링 구조에서 자연스러운지 궁금합니다.

# P11 — 표시 체계: 무엇을 보여줄 것인가

**브레드크럼** 표시 › 결과 표현

### 슬라이드 문안

**거버닝 메시지**
> 변조·무효·미등록·확인불가는 원인도 대응도 다르다. 이를 같은 경고로 뭉치면 사용자는 정상 문서를 위조로 오인하거나 그 반대를 하게 된다.

**반드시 구분해야 할 네 가지** (원칙)

| 상황 | 사용자가 할 수 있는 일 | 뭉쳤을 때의 사고 |
|---|---|---|
| 문서 변조 | 문서를 신뢰하지 않는다 | — |
| 목록 미등록 | 발급처를 확인한다 | 정상 문서를 위조로 오인 |
| 목록 접근 불가 | 연결 후 재검증한다 | 장애를 위조로 오인 |
| 상태정보 미확인 | 재검증한다 | 확인 안 된 것을 정상으로 오인 |

**표시 체계** (검토안, 확정 아님)

| 아이콘 | 문구 | 언제 |
|---|---|---|
| 흰 원 | 서명 없음 | 서명이 없는 PDF |
| 초록 방패 | 진본 확인 | 모든 축이 통과 |
| 노란 삼각형 | 주의 필요 | 미등록·철회 등 유보가 필요 |
| 회색 하이픈 | 확인 불가 | 외부 정보 접근 실패, 제한 검증 |
| 빨간 방패 | 서명 무효 | 문서 변조 또는 서명값 검증 실패에 한정 |

### 발표 스크립트 (60초)

이 장은 기획 쪽에서 논의가 길어질 부분입니다. 왼쪽과 오른쪽의 성격이 다르다는 걸 먼저 말씀드리고 싶습니다.

왼쪽은 원칙입니다. 네 가지 상황은 원인이 다르고 사용자가 할 수 있는 일도 다릅니다. 문서가 변조된 거면 그 문서를 믿으면 안 되지만, 목록 서버가 잠깐 죽은 거면 나중에 다시 열어보면 됩니다. 이걸 같은 빨간 경고로 뭉치면 멀쩡한 문서를 위조로 오인하게 만듭니다. 반대로 확인이 안 된 걸 정상으로 표시하면 더 위험하고요.

오른쪽은 저희 검토안입니다. 아이콘 다섯 개에 문구를 붙여봤는데 확정이 아닙니다. 다섯이 많다고 보시면 줄여도 되고, 웨일에 이미 있는 보안 표시 체계에 맞추는 게 나을 수도 있습니다. 그 판단은 웨일 쪽이 훨씬 잘하실 겁니다.

저희가 지켜야 하는 건 왼쪽 원칙뿐이고, 오른쪽은 안을 주시면 거기에 판정 로직을 맞추겠습니다.

# P12 — 오프라인·장애 시 동작

**브레드크럼** 표시 › 예외 처리

### 슬라이드 문안

**거버닝 메시지**
> 네트워크가 없어도 문서 열람은 멈추지 않되, 만료된 캐시로 정상 판정을 내리지 않는다. 이 두 문장이 오프라인 정책의 뼈대다.

**분기**

| 상황 | 동작 | 표시 |
|---|---|---|
| 동기화 성공 | 목록 갱신 후 온라인 검증 | 정상 결과 |
| 실패 · 유효 캐시 있음 | 캐시로 제한 검증 | 확인 불가 / 재검증 필요 |
| 실패 · 유효 캐시 없음 | 신뢰 판정 보류 | PDF 열람은 유지 |

**고정 원칙** (조정 대상 아님)

1. 어떤 경우에도 PDF 열람 자체는 차단하지 않는다.
2. 캐시는 서명·발행시각·유효기간을 재검증한 뒤 사용하고, 만료·손상 캐시는 폐기한다.
3. 제한 검증 결과에는 캐시 기준시각과 재검증 필요 여부를 함께 기록한다.

### 발표 스크립트 (45초)

네트워크가 없을 때입니다. 원칙은 두 개입니다.

문서 열람 자체는 어떤 경우에도 막지 않습니다. 검증이 안 된다고 PDF를 못 열게 하면 그건 브라우저 기능을 망가뜨리는 겁니다.

대신 만료된 캐시로 정상 판정을 내리지는 않습니다. 유효기간이 남은 캐시가 있으면 그걸로 제한적으로 검증하고, 결과에 "이건 캐시 기준이고 재검증이 필요하다"는 걸 같이 적습니다. 캐시도 없으면 신뢰 판정은 보류하되 문서는 그대로 열립니다.

여기도 하나 열어 두겠습니다. 다시 온라인이 됐을 때 알아서 재검증을 돌릴지, 사용자가 누를 때만 돌릴지입니다.

# P13 — 역할 분담: 웨일 / KISA

**브레드크럼** 협업 › 역할 분담

일렉서티는 양쪽 사이에서 검증 SDK와 KR-AdES 처리, 표준 결과코드 체계, 판정 규칙, 검증보고서 생성(ETSI TS 119 102-2)을 제공한다.

**하단 강조**
> 이 초안대로면 웨일이 새로 만드는 화면은 세 곳이다 — 검증 상태 표시, 검증 결과 상세, 설정 내 KR-TL 항목.

### 발표 스크립트 (60초)

"그래서 우리가 뭘 만들어야 하나"에 대한 현재 그림입니다. 확정이 아니라 초안입니다.

웨일 쪽은 브라우저에서 보이고 저장되는 부분입니다. PDF를 열 때 서명이 있는지 보고 검증을 시작하는 부분, 결과를 어디에 어떻게 보여줄지, 설정에 KR-TL 항목을 두는 것, 그리고 목록을 받아와 보관하고 만료를 관리하는 것.

KISA는 목록 자체와 기준정보입니다. 목록을 만들고 서명하고 배포하는 것, 그 목록을 검증할 앵커를 주는 것, 배포 주소를 운영하는 것.

저희 일렉서티는 그 사이에서 검증 SDK와 판정 로직, 결과코드 체계, 검증보고서 생성을 맡습니다.

아래 줄을 보시면 이 초안대로면 웨일이 새로 만드는 화면은 세 곳입니다. 검증 상태 표시, 결과 상세, 설정.

경계가 어색해 보이는 게 있으면 말씀해 주시면 좋겠습니다.

| 질문 | 답변 |
|---|---|
| 목록을 못 받아오면 브라우저가 느려지거나 멈추는가 | 검증은 비동기로 돌고 PDF 열람 경로와 분리되어 있습니다. 목록 조회가 실패하면 그 결과만 확인 불가로 처리되고 문서는 그대로 열립니다. |

v02의 "열어 둘 질문" 박스는 삭제했다. 본문 영역이 그만큼 넓어졌으므로 표와 도식이 세로로 더 여유 있게 배치된다.

**규칙**

- 배경 흰색. 도식은 벡터·플랫로 그리고 그림자와 그라디언트를 쓰지 않는다.
- 본문 13px, 거버닝 메시지 16px, 슬라이드 제목 21px.
- 강조색은 메인 블루 하나만 쓴다. 나머지는 회색으로 눌러 강조 대상이 하나로 보이게 한다.
- 아이콘은 P11에서만 쓴다. 다른 페이지에 장식용 아이콘을 넣지 않는다.
- 슬라이드에 질문을 인쇄하지 않는다. 질문은 발표 스크립트로만 던진다.
- P03 우측 하단(민간 단절)만 예외적으로 경고 톤을 쓴다.
- 캡처 자리표시 박스는 점선 테두리 + 파일 경로 안내. 실제 파일이 있으면 자동 대체된다.

**확정과 검토안의 시각 구분**

| 성격 | 표기 |
|---|---|
| 규격·제도상 고정 | 표 우측 "규격" / "제도" 라벨 |
| 안전성 요건, 조정 불가 | 굵게 + 좌측 검은 띠 |
| 우리 검토안 | "검토안" 명시, 회색 배경 |
| 웨일 판단 영역 | 슬라이드에 표기하지 않고 발표 스크립트로 구두 전달 |
