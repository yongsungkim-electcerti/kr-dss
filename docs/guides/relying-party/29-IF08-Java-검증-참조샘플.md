# 29. IF-08 이용기관용 Java 검증 참조 샘플

이용기관이 자체 검증 모듈을 연결할 때 단계와 책임을 이해할 수 있도록 [Java 소스](../../../examples/if08-verification/If08VerificationSample.java)를 제공한다. 제품 서버·SDK에는 아직 연결하지 않았다. 외부 의존성 없는 흐름 참조용 코드이며 암호 검증 구현은 인터페이스로 남긴다. 실제 키 파일 생성은 [27](../../design/poc/tl-management/pki/27-PoC-키파일-디렉터리-설계.md)의 후속 작업이다.

## 1. 호출 경계

```text
이용기관 앱 / PDF 뷰어
  ├─ IF-07: TL XML 내려받기 → 후보 파일 스냅숏
  └─ IF-08: 선택한 PDF 서명 검증
       └─ If08VerificationSample.verify(input, crypto, policy)
            ├─ CryptoVerifier → 실제 DSS/KR-DSS/암호모듈 어댑터
            └─ TrustPolicy    → TL 순번·시각·이력 및 서비스 인정 판정
```

IF-08은 로컬 Java 호출 예시다. HTTP 검증 API나 PDF 업로드 서버를 새로 만들지 않는다. PDF 서명 한 개를 선택하는 `signatureIndex`를 명시한다. 다중 서명 PDF는 이용기관이 각 서명을 열거해 별도 호출하고 전체 문서 판정 정책을 적용해야 한다.

## 2. 단계별 설명과 어댑터 계약

| 단계 | 입력·책임 | 통과 근거 / 실패·보류 예 |
|---|---|---|
| 1 TL_SIGNATURE | 후보 XML, 사전 설정된 TL 앵커·중간 인증서 | XML 서명 대상·서명값·인증 경로 확인. TL 내부 임의 인증서를 앵커로 삼지 않음 |
| 2 TL_ACCEPTANCE | 서명 확인된 TL, 직전 수용본, 검증 시각 | 형식·순번·만료·발행 시각·이력 확인. 하위 번호·동일 번호 다른 내용·시간 모순은 거부 |
| 3 DOCUMENT_SIGNATURE | 선택한 PDF 서명 | ByteRange·서명값·해시·서명 범위와 이후 변경의 허용 여부 확인. 서명자 체인·서명 시각 증거 추출 |
| 4 CERTIFICATE_PATH | 앞 단계에서 추출한 체인, 수용한 TL | 인증서 서명·유효기간·제약과 TL 서비스 공개키·Subject 연결. 이름 일치만으로 통과시키지 않음 |
| 5 REVOCATION | 같은 경로와 정책상 기준 시각 | OCSP/CRL 서명·응답자 권한·신선도·대상 일치 확인. 폐지는 FAILED, 자료 부족은 INDETERMINATE |
| 6 SERVICE_HISTORY | 같은 경로의 서비스, 서명 시각 증거, TL 이력 | 해당 시점의 인정 여부. 정지·철회는 비인정, 시각 없음·미지원 상태·근거 부족은 보류 |

모든 단계가 통과해야 선택 서명에 대해 PASSED를 반환한다. 앞 단계가 FAILED 또는 INDETERMINATE이면 후속 단계는 NOT_RUN이다. 실패와 미실행을 구별해 화면에 표시한다. 모듈 예외·결과 누락도 성공으로 간주하지 않는다.

`CryptoVerifier`는 실제 암호 연산과 형식 검증 책임을 맡는다. `TrustPolicy`는 업무 신뢰 규칙을 맡는다. 이 인터페이스 분리는 책임 경계이며, 같은 실행의 서명·경로·파싱 결과를 서로 다르게 선택해도 된다는 뜻은 아니다. 실제 연결 시 호출당 검증 컨텍스트로 증거를 공유하고 각 결과에 서명 식별자·TL 순번·경로·사유를 연결한다. 파일은 읽기 전 스냅숏으로 고정해 단계 사이 교체를 막는다.

TL 검증용 KISA Root와 문서 서명자를 판정하는 TL 서비스 신뢰점은 별개다. 서명 시각은 PDF에서 추출하며 호출자가 입력한 임의 시각으로 대체하지 않는다. TSA 없는 claimed signing time을 쓰는 PoC 정책과 신뢰 가능한 시각 증거를 구분하고, LTV·PQC 등 장기 검증 완료로 표시하지 않는다.

## 3. 오류 발행 PoC와 연결

관리 화면은 잘못된 순번·시각의 TL도 생성한다. 이 샘플의 수신 검증 정책에는 오류 허용 옵션을 전달하지 않는다. `acceptTl()`이 [26](../../design/common/kr-tl/26-EU-기준-이력-버전-모델.md)의 검사를 수행해야 한다.

IF-07의 HTTP 200은 단계 1·2 통과 근거가 아니다. 거부한 후보로 활성 캐시를 교체하지 않는다. 이전 유효 TL 사용 여부는 호출 측이 결정하고, 이전본으로 다시 검증한 결과에는 사용한 순번과 갱신 실패 사실을 표시한다. 이 흐름 샘플 자체는 파일 다운로드·캐시 교체를 수행하지 않는다.

## 4. 실행과 실제 연결

저장소 루트에서 다음과 같이 실행할 수 있다(Java 17 이상, 프로젝트 개발 기준 Java 21).

```powershell
java '-Dfile.encoding=UTF-8' examples/if08-verification/If08VerificationSample.java
```

기본 실행은 실제 파일을 읽지 않는 **미연결 상태 예시**다. 첫 단계에서 `CRYPTO_NOT_CONFIGURED / INDETERMINATE`, 이후 5단계에서 `NOT_RUN`이 나와야 한다. 이는 실제 암호 검증 시험이 아니다.

2026-10-07 Java 17 소스 실행으로 위 결과를 확인했다. 실제 서명·인증서 검증과 Java 21 환경의 통합 검증은 아직 수행하지 않았다.

후속 개발에서 이용기관은 `CryptoVerifier` 4개 메서드와 `TrustPolicy` 2개 메서드를 구현해 `verify()`에 전달한다. 실제 검증 결과를 Check로 변환하며 무조건 PASSED를 반환하는 연결 코드는 제공하지 않는다. 기존 `PdfBaselineVerifier`는 재사용 후보지만, 기존 데모의 폐지 확인 생략 설정을 이 참조 계약의 통과 근거로 사용하지 않는다.

실제 모듈 연결 후에는 정상·변조 문서, 잘못된 TL 서명, 하위 순번·시간 오류, 폐지·조회 불가, 서비스 상태 경계와 미지원 상태를 검사한다. 구체적 시연 표본과 순서는 향후 PoC 시나리오에서 결정한다.
