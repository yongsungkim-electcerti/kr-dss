# 21. 시연 운영 절차 (D8 · 검토 우선 작업 5)

> 자료 분류: 기존 상세 설계·검토 자료. 현재 PoC 구현 범위는 [확정 범위](../../../design/poc/tl-management/scope.md)를 우선한다. 고정 시나리오·HSM·별도 WEB 등은 현재 필수 개발로 간주하지 않는다.

> 1차 설계 검토([16](../../../development/poc/tl-management/reviews/16-설계-보완사항-조치목록.md)) §5 우선 작업 5 — D8.
> **완료 기준:** 시연자 한 명이 준비 → 기동 → R1~R6 → 초기화 · 재실행을 이 문서만 보고 같은 결과로 반복한다.
> 시험 데이터 · 기대 결과는 [20](../../../design/poc/tl-management/scenarios/20-시험데이터-비교화면.md), 조작 흐름은 [19](../../../design/poc/tl-management/publication/19-변경-발행-수신-흐름.md), 판정 규칙은 [18](../../../design/common/kr-tl/18-신뢰경로-판정표.md).

## 0. 전제와 미결 항목

| 항목 | 내용 |
|---|---|
| 브라우저 이용환경 | 웨일 대신 **크롬 확장**으로 우선 대체한다 (PoC). 확장은 TL 수신 · 보유와 **표본 정보(서명자 체인 · 서명 시각)로 TL 판정**만 한다. PDF 서명 값 검증은 웨일의 역할로 하지 않는다. 웨일 탑재는 후속 |
| 운영 범위 | 시연 운영만 다룬다. 정기 발행 주기 · 키 교체 · 장애 복구 같은 실제 운영 절차는 **향후 결정** (00 D8-1~6) |
| 결과 수집 방법 | 이용환경 판정 결과(D-11)를 M-08로 모으는 방법 — **논의 후 결정** |
| 시험 시계 구현 | 시험 기준 시각을 넣는 방식(설정 · API · 화면) — **논의 후 결정**. 이 문서는 "시험 시계를 ○○로 맞춘다"로만 적는다 |

## 1. 구성과 포트

| 구성요소 | PoC 모듈 | 포트 | 비고 |

- 이용환경의 자동 확인 주기(10분)는 시연 중 판정을 흐리게 하므로 **끈다**. 수신은 "지금 확인"으로만 한다.

## 4. 실행 R1~R6 — 운영 체크리스트

공통: 각 실행 전 시험 시계를 맞추고, 실행 ID를 정한다(예: `R3-2026-11-03`). 검증 시 시험 시계는 2026-11-05T18:00+09:00 (20 §1.2).

| 실행 | 시험 시계 (발행) | 시연자 조작 | 확인 (기대 = 20 §2 · 18 §5) |
|---|---|---|---|
| **R1** | — (TL #1 보유) | 이용기관(PDF) · 확장(표본 정보)에서 표본 9개 검증 | #1 열. U-S1 보류 `NOT_IN_TL`, W · V 통과 |
| **R2** | 11-02T10:00 | M-02 JA 등재 · 인정(t1) 입력 → M-04 확정 → M-05 발행 #2 → M-06 반출 → 양쪽 "지금 확인" → 검증 | #2 열. U-S1 통과, U-S0 보류 `NOT_ACCREDITED_AT_TIME` |
| **R3** | 11-03T10:00 | M-03 JA 정지(t2) → 확정 → 발행 #3 → 반출 → **이용기관만** 확인 → U-S2 양쪽 검증 → 확장 확인 → 다시 검증 | 이용기관 실패 / 확장 통과 → 둘 다 실패 `SERVICE_SUSPENDED_AT_TIME`. W-S2 통과 |
| **R4** | 11-04T10:00 | JA 복원(t3) → 확정 → 발행 #4 → 반출 → 양쪽 확인 → 검증 | U-S3 통과, U-S2 실패 유지 |
| **R5** | 11-05T10:00 | JA 철회(t4) → 확정 → 발행 #5 → 반출 → 양쪽 확인 → 검증 | U-S4 실패 `SERVICE_WITHDRAWN_AT_TIME`, U-S1 · S3 통과 |
| **R6** (보조) | 11-05T18:00 | ① 변조 TL #6을 배포에 반출 ② TL #2 재반출 ③ 검증 시험 시계를 #5 NextUpdate 이후로 | ① `SIGNATURE_INVALID` 거부 ② `VERSION_NOT_INCREASING` 거부 ③ `NO_VALID_TL` 보류 |

- 각 실행 끝에 M-08 판정표 보기로 기대값과 다른 칸이 없는지 확인한다. 다른 칸이 있으면 §6.
- R3의 핵심 장면은 "같은 서명, 같은 체인, 다른 TL 버전 → 다른 판정"이다. 확장 수신 전후를 나란히 보여 준다.

## 5. 초기화 · 부분 재실행

| 방식 | 언제 | 방법 |
|---|---|---|
| **전체 초기화** | 시연 처음부터 | 20 §4 표대로 — 등재 정보 · 발행본 · 배포 게시 이력 · 이용환경 보유본을 시드로 덮어쓰고 시험 기록 삭제 |
| **실행 단위 재시작** | 특정 Rn부터 다시 | 시드 대신 **체크포인트**를 쓴다 — 각 실행 종료 시점의 `registry/` · `published/` · 배포 최신 · 이용환경 `cache/`를 `checkpoints/Rn/`에 복사해 두고 되돌림 |
| **이용환경만 되돌리기** | R3 장면 반복 | 이용기관 `cache/` · 확장 저장소를 TL #2로 되돌림 (관리 · 배포는 그대로) |

- 초기화 후 반드시 §3 기동 확인 표를 다시 본다 (보유 TL 번호).
- 확장 저장소 되돌리기는 팝업의 "시드로 초기화" 동작으로 한다 (개발용 기능).

## 6. 이상 상황 대응

| 증상 | 원인 후보 | 조치 |
|---|---|---|
| 발행 실패 "번호 미사용" | TL 서명 키 파일 경로 · 암호 | 키 파일 확인 후 다시 발행 (19 §5) |
| 발행 중단 "효력 시각 이전" | 시험 시계가 효력 시각보다 늦음 | 시험 시계 또는 효력 시각 수정 |
| 반출 후 "게시 안 됨" | 배포 미기동 · 포트 | 배포 기동 후 M-06 다시 반출 (같은 번호 · 같은 내용은 `ALREADY_PUBLISHED`) |
| 이용환경 "새 TL 거부" (R6 외) | 앵커 불일치 · 검증 시험 시계가 NextUpdate 이후 | P-4 앵커 지문 확인, 시험 시계 확인 |
| 판정이 기대값과 다름 | 보유 TL 번호 다름 · 표본 재생성 | 판정 결과의 사용 TL 번호부터 확인 → 체크포인트로 되돌림 |
| 확장 판정 없음 | 확장 미로드 · 서비스 워커 중지 | `chrome://extensions`에서 다시 로드 |
