# 19. 인증 없는 변경 · 발행 · 수신 흐름 (검토 우선 작업 3)

> 1차 설계 검토([16](16-설계-보완사항-조치목록.md)) §5 우선 작업 3 — D2 · D5 · D6.
> **완료 기준:** 시연자 한 명이 입력 확정부터 발행 · 동기화까지 조작하며, 스냅숏 · 서명 · 게시 순서와 기본 오류가 정해져 있다.

## 1. 전제

| 전제 | 내용 |
|---|---|
| 조작자 | 시연자 1명. 로그인 · 역할 · 승인 분리 없음 |
| 발행 | **단일 발행** — 한 번에 하나의 TL만 만든다. 동시 발행 없음 |
| 실패 처리 | **수동 재시도** — 자동 복구 없음. 화면에 실패를 보여 주고 시연자가 다시 누른다 |
| 시각 | 한국 시간, ISO 8601 `+09:00` |
| 시험 시계 | 시연용 날짜(18 §3의 11-01~11-05)를 쓰기 위해 관리 시스템 · 이용환경에 **시험 기준 시각**을 넣을 수 있다. 넣지 않으면 실제 시각 |

## 2. 흐름 — 6단계

```
① 입력 ─▶ ② 확정 ─▶ ③ 발행(스냅숏 · 편성 · 서명) ─▶ ④ 반출 · 게시 ─▶ ⑤ 수신 ─▶ ⑥ 적용
 관리 콘솔   관리 콘솔     TL 발행 서버 · HSM           배포 WAS          이용환경    이용환경
```

| 단계 | 화면 · IF | 하는 일 | 결과 상태 | 기록 |
|---|---|---|---|---|
| **① 입력** | M-02 · M-03 · M-04 (IF-02) | 신뢰정보 입력, 상태 변경 입력(상태 · 효력 시각 · 사유), 또는 사업자 제출(IF-01) 수신 | 입력됨 | 입력 내용 |
| **② 확정** | M-04 · M-03 | 입력을 확정 → `krtl/registry/`에 반영 (상태 변경은 이력에 추가) | 확정됨 | 확정 시각 |
| **③ 발행** | M-05 (IF-04 · IF-05) | 확정된 등재 정보 **스냅숏** → TL 편성(일련번호 +1, 발행 일시, NextUpdate +7일) → 효력 시각 검사 → XAdES 서명 → `krtl/published/<seq>/kr-tl.xml` 보관 | 발행됨 (seq 확정) | 발행 TL 번호 · 차이 |
| **④ 반출 · 게시** | M-06 (IF-06) | 서명된 TL을 배포 WAS로 push → 배포 WAS가 서명 · 일련번호 확인 → 최신 버전 교체 | 게시됨 | 게시 결과 |
| **⑤ 수신** | 이용환경 (IF-07) | 풀 방식으로 버전 확인 → 새 TL 수신 → 서명 · 일련번호 · NextUpdate 확인 → 보유본 교체 | 수신됨 | 수신 TL 번호 |
| **⑥ 적용** | 이용환경 | 신뢰 색인 다시 생성 → 이후 검증에 사용, 검증 결과에 TL 번호 기록 | 적용됨 | 사용 TL 번호 · 판정 |

- 시연에서는 ⑤를 기다리지 않도록 이용환경에 **"지금 확인"** 동작을 둔다. 방식은 그대로 풀이다.
- ②와 ③을 나눈 이유: 시연자가 여러 변경을 확정해 두고 **한 번에 발행**하거나, 발행 직전 차이를 확인할 수 있게 하기 위해서다.

## 3. TL 버전의 네 가지 상태

같은 TL 번호라도 "어디까지 갔는가"가 다르다. 비교 화면(M-08)은 이 네 가지를 구분해 보여 준다.

| 상태 | 뜻 | 어디서 확인 |
|---|---|---|
| **발행** | 관리 시스템이 서명해 보관함 | 관리 시스템 `published/` · M-05 |
| **게시** | 배포 WAS의 최신 버전이 됨 | 배포 WAS · M-06 |
| **수신** | 이용환경이 받아 검증하고 보유함 | 이용환경 보유본 · M-07(접속 기록은 보조) |
| **적용** | 이용환경이 그 TL로 실제 판정함 | 검증 결과의 사용 TL 번호 · M-08 |

- 적용 여부는 이용환경이 남긴 **사용 TL 번호와 판정 결과**로 확인한다. 별도 적용 확인 API나 이용기관 등록 체계는 두지 않는다.

## 4. 단계별 규칙

### 4.1 발행 (③)

| 규칙 | 내용 |
|---|---|
| 대상 | 발행 버튼을 누른 순간까지 **확정된** 등재 정보 (스냅숏). 그 뒤 확정은 다음 TL로 |
| 일련번호 | **서명에 성공했을 때 확정**한다. 편성 · 서명이 실패하면 번호를 쓰지 않는다 (다음 시도도 같은 번호) |
| 효력 시각 검사 | 새로 생긴 상태의 효력 시각 ≥ 발행 시각. 어기면 발행 중단 → M-03에서 수정 |
| 변경 없음 | 확정된 변경이 없으면 "변경 없음 — 재발행"으로 표시하고 발행할 수 있다 (NextUpdate 갱신 목적) |

### 4.2 반출 · 게시 (④)

| 규칙 | 내용 |
|---|---|
| 순서 | 발행이 끝난 TL만 반출한다 |
| 같은 번호 · 같은 내용 재전송 | `ALREADY_PUBLISHED` — 정상으로 처리 (재시도 안전) |
| 같은 번호 · 다른 내용 | `CONFLICT` — 거부. 발행된 TL은 바꾸지 않는다 |
| 이전 번호 | `VERSION_NOT_INCREASING` — 거부 |
| 서명 검증 실패 | `SIGNATURE_INVALID` — 거부 |
| 반출 실패 (연결 오류 등) | TL은 "발행됨"으로 남고 "게시됨"이 아니다. M-06에서 다시 반출 |

### 4.3 수신 · 적용 (⑤ · ⑥)

| 규칙 | 내용 |
|---|---|
| 수용 조건 | ① 서명을 KISA TL RootCA까지 검증 ② 일련번호 > 보유본 ③ NextUpdate 이내 (시험 시계 기준) |
| 실패 | 새 TL을 버리고 보유본 유지, 화면에 사유 표시 |
| 기한 경과 | 보유본의 NextUpdate가 지나면 보유본도 버림 → 판단 보류(`NO_VALID_TL`) |
| 적용 시점 | 수신에 성공한 직후 신뢰 색인을 다시 만들고, 그 뒤 검증부터 새 TL을 쓴다 |

## 5. 오류와 화면 표시

| 단계 | 오류 | 화면 | 시연자 조치 |
|---|---|---|---|
| ② | 효력 시각이 과거 | M-03 "발행 시각 이전 효력 시각은 입력할 수 없음" | 시각 수정 |
| ③ | 서명 실패 (키 파일 없음 등) | M-05 "서명 실패 — 번호 미사용" | 원인 해결 후 다시 발행 |
| ④ | 반출 실패 | M-06 "#n 발행됨 · 게시 안 됨" | 다시 반출 |
| ④ | 배포 WAS 거부 (`CONFLICT` 등) | M-06 사유 코드 | 원인 확인 (정상 시연에서는 발생하지 않음) |
| ⑤ | TL 거부 (서명 · 번호 · 기한) | 이용환경 "새 TL 거부 — 보유 #n 유지" | SC-08 보조 시연에서 의도적으로 확인 |
