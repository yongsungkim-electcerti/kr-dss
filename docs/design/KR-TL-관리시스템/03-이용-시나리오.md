# 03. 주체별 프로세스와 이용 시나리오

> TL을 여러 상황에서 관리해 보면서 **관리자 · 인증사업자 · 가입자 · 이용자 · 브라우저가 각각 어떻게 동작하고, 무엇을 검증해야 하는지**를 정리한다.
> PoC는 이 시나리오들을 실제로 돌려 보는 것으로 개념을 증명한다.

## 1. 주체별 프로세스

### 1.1 관리자 (KISA)

```
신뢰정보 변경 발생 (사업자 제출 · 자동 수집 · 직권)
  → 심사 (M-04)               승인 또는 반려
  → 상태 변경 (M-03)          효력 시각 · 사유 기록
  → TL 발행 (M-05)            초안 → 차이 확인 → 승인(다른 사람) → 서명 → 반출
  → 배포 확인 (M-06)          게시 성공 여부
  → 수신 확인 (M-07)          미수신 이용자 확인 · 안내
```

### 1.2 인증사업자

```
등록 신청 / 서비스 변경 / 상태 신고   ─ IF-01 (VPN, 서명된 제출서)
처리 결과 조회                       ─ IF-01
자동 수집 엔드포인트 유지            ─ IF-02 (KISA가 주기적으로 가져감)
```

### 1.3 가입자 (서명 주체)

```
인증서 발급 (IF-09) → 문서 전자서명 (KR-AdES) → 타임스탬프 부착 (IF-10, 선택) → 이용자에게 제출 (IF-11)
```

- 가입자는 TL을 직접 다루지 않는다. 그러나 **TL 변경의 영향을 받는 쪽**이다. 자기 인증사업자가 정지되면 그 뒤에 한 서명은 거부된다.
- 타임스탬프를 붙인 서명은 "언제 서명했는지"가 증명되므로, 나중에 사업자가 정지·철회되어도 **그 이전 서명은 유효**하게 남는다. 이것이 가입자 측에서 PoC가 보여 줄 핵심이다.

### 1.4 이용자 (검증) — 검증 프로세스

```
[A] TL 확보
  A1  캐시된 TL이 있고 다음 발행 예정(NextUpdate) 전이면 → 버전 확인만 (IF-08, 변경 없으면 그대로)
  A2  새 버전이면 다운로드
  A3  TL 서명 검증 — TL 서명 인증서 → KISA CA → KISA Root CA(미리 보유한 신뢰 기준)까지 체인 확인
  A4  일련번호가 캐시보다 큰지 확인 (예전 TL로 되돌리기 공격 방지)
  A5  실패하면 새 TL을 버리고 캐시 유지 + 경보

[B] 전자서명 검증
  B1  서명값 · 문서 무결성 확인
  B2  서명자 인증서 → 발급 CA 인증서 체인 구성
  B3  체인의 CA 인증서가 TL의 서비스 인증서(D-04)와 일치하는지 → 없으면 "신뢰할 수 없는 발급자"
  B4  서명 시각 확인 — 타임스탬프가 있으면 그 시각. 없으면 검증 정책에 따름 (01 §4.2 개념)
  B5  B4 시각에 해당 서비스의 TL 상태(D-03 이력) 확인
  B6  가입자 인증서 폐지 여부 확인 (IF-13: OCSP·CRL)
  B7  판정 + 근거 + 사용한 TL 버전 기록 (D-11)
```

| 조건 | 판정 |
|---|---|
| B1~B6 모두 정상, 서명 시각에 서비스가 granted | **PASSED** |
| 서명 시각에 서비스가 suspended·withdrawn, 또는 인증서 폐지, 서명값 불일치 | **FAILED** |
| 발급 CA가 TL에 없음, TL이 기한 경과, 폐지 상태 확인 불가(OCSP 무응답 등) | **INDETERMINATE** |

> 판정 기준의 세부(예: 타임스탬프 없는 서명, 기한 지난 TL의 취급)는 **검증 정책으로 향후 결정**한다. PoC는 정책에 따라 결과가 어떻게 달라지는지를 보여 주는 것으로 개념을 설명한다.

### 1.5 브라우저 (웨일) — 서명된 결과 확인

```
TL 수신 (IF-08)        이용자와 같은 방식: 버전 확인 → 다운로드 → TL 서명 검증 → 일련번호 역행 거부
서명된 결과 수신 (IF-12) 이용자 시스템이 제공한 서명 문서·증명서
서명 검증             1.4의 [B] 절차와 같음 (인증서 상태 확인은 IF-13)
결과 표시             판정과 사용한 TL 버전을 사용자에게 보여 줌
```

- 이용자는 서비스를 처리하기 위해, 브라우저는 **결과를 받아 보는 사람의 입장**에서 검증한다.
- 같은 서명을 같은 TL 버전으로 검증하면 **이용자와 브라우저의 판정이 같아야 한다.** TL 버전이 다르면 판정이 달라질 수 있고, 그 차이가 TL 동기화의 중요성을 보여 준다.

## 2. 시나리오 목록

PoC 1차 범위는 ★ 표시.

| ID | 시나리오 | 무엇을 증명하는가 |
|---|---|---|
| ★SC-01 | 신규 사업자 등재 | TL에 실려야만 신뢰된다 |
| SC-02 | 서비스 인증서 갱신 | 신·구 인증서 공존 기간에도 검증이 끊기지 않는다 |
| ★SC-03 | 서비스 정지 (긴급 발행) | 정지가 시점까지 정확히 반영된다 |
| ★SC-04 | 정지 해제 | 이력이 남은 채로 다시 신뢰된다 |
| ★SC-05 | 인정 철회 | 철회 이후만 무효, 이전 서명은 유효 |
| ★SC-06 | 이용자·브라우저 동기화와 미수신 추적 | 관리자가 반영 범위를 확인할 수 있다 |
| SC-07 | TL 기한 경과 | 갱신이 멈추면 이용자가 알아챈다 |
| ★SC-08 | 배포된 TL 변조 | 배포 시스템이 뚫려도 위조 TL은 통하지 않는다 |
| SC-09 | TL 서명키 교체 | 서명키를 바꿔도 이용자·브라우저의 신뢰 기준(KISA Root CA)은 그대로다 |
| SC-10 | 관리·배포 시스템 장애 | 한쪽이 멈춰도 검증은 계속된다 |
| ★SC-11 | 내부 통제 | 혼자서는 TL을 바꿀 수 없고, 기록은 고칠 수 없다 |
| SC-12 | 잘못된 제출 반려 | 검증되지 않은 정보는 TL에 들어가지 않는다 |

|---|---|---|

| 서비스 인증서 복수 등재 | SC-02 | KR-TL 모델 |
| 긴급 발행 | SC-03 | 관리 시스템 |
| TL 일련번호 역행 거부, TL 서명 검증 실패 시 캐시 유지 | SC-08 | 이용자 SDK |
| **서명 시각 기준** 서비스 상태 판단 | SC-03·04·05 | 이용자 SDK |
| 검증 결과에 사용 TL 버전 기록 | SC-01·03 | 이용자 SDK |
| NextUpdate 경과 판단 | SC-07 | 이용자 SDK |
