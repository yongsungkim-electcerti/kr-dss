# KR-TL 관리 시스템 설계

> 대상: KISA가 운영하는 한국형 신뢰목록(KR-TL)의 관리·배포 체계
> 성격: **전체 시스템 설계, 목표는 PoC(개념 증명)**
> 범위: 1차 — 기본 KR-TL (Attestation·장치 신뢰목록 제외)
> 최종 갱신: 2026-10-07 · **설계 초안 v1.0** ([24](24-설계-베이스라인.md)), PoC 구현 차이 검토 착수 ([25](25-PoC-구현-차이-검토.md))

## 무엇을 증명하는가

> 인증서 체인은 그대로인데, **TL의 등재 · 상태와 이용환경이 가진 TL 버전**에 따라 같은 서명의 판정이 서명 시각 기준으로 달라진다. KISA가 발행한 TL이 배포를 거쳐 이용기관 · 브라우저의 판정까지 위조 없이 전달된다.

## 구성

**인증사업자** ─ **신뢰체계 관리 시스템 (KISA · 신뢰앵커)** ─ **이용환경 (가입자 · 브라우저 · 이용자)**

## 읽는 순서

**다음 세션:** 개발 전에 폴더 구조를 정리한다. [30 인계와 목표 구조](30-새세션-폴더정리-인계.md)에 중복 자료의 main 로컬 백업·Git 제외 원칙을 기록했다. 폴더 이동은 아직 수행하지 않았다.

이용기관의 IF-08 구현 참조는 [29 Java 검증 샘플](29-IF08-Java-검증-참조샘플.md)을 따른다. 암호 검증은 인터페이스로 분리하고 6단계별 책임·결과를 설명한다. 기본 실행은 모듈 미연결 상태이며 실제 검증 성공을 반환하지 않는다.

WAS와 PDF 뷰어·이용기관의 조회 연계는 [28 IF-07 TL 조회 API](28-IF07-TL-조회-API.md)를 따른다. GET으로 서명 XML과 보조 해시를 제공하며, HTTP 전송 성공과 검증 모듈의 TL 수용을 구별한다.

키 파일 기반 발행의 디렉터리·인증체인은 [27 PoC 키 파일 디렉터리 설계](27-PoC-키파일-디렉터리-설계.md)에 정리했다. 실제 키·인증서 생성과 디렉터리별 체인 README 작성은 후속 개발에서 수행한다.

이력·버전 구현은 [26 EU 기준 상세 모델](26-EU-기준-이력-버전-모델.md)을 따른다. 형식 버전과 발행 순번, 현재 서비스와 이력을 분리한다. **PoC 관리 화면은 순번·시각 오류가 있는 TL도 생성·제공할 수 있게 하고, 수신 검증 모듈에서 반드시 판정한다.**

PoC 개발은 [기존 구현과 최신 설계 비교](25-PoC-구현-차이-검토.md)부터 읽는다. 구현 차이 16건에 사용자 범위 결정 6건(2026-10-07)을 반영했다. 신뢰체계 개념 증명을 우선하며 인증·감사는 제외, 접수·심사·보완·반려는 메뉴만 제공한다. 키 파일 서명, 최신 IF-01~08, Spring Boot WAS를 기준으로 구현하고 PoC 시나리오는 향후 결정한다. 제외·유보 항목은 필수 개발량에 포함하지 않는다.

통합 설계서는 [구글독스](https://docs.google.com/document/d/1jaEztftE4CA5eIsZQ2oRdYtELsUSMYhI8Wmsf-SIv0U/edit)에 작성했다. [본문 보관본](완성본/KR-TL-시스템-및-신뢰체계-설계서.md)과 [draw.io 원본](완성본/diagrams)을 함께 보관한다. 다음 세션의 보정 작업은 [세션 인계](완성본/세션-인계.md)를 읽고, 사람이 수정한 최신 문서를 먼저 확인한다.

## 확정된 구성 원칙

1. 관리 시스템은 폐쇄망, TL 서명은 관리 시스템 HSM에서만 한다.
2. 관리 ↔ 배포는 채널 하나(IF-06 패키지 반출)이며 방화벽으로 통제하고, 연결은 관리 쪽에서만 시작한다.
3. 외부에 노출되는 것은 배포 WEB뿐이다. 배포 WAS가 접속 기록을 저장하고 수신 현황을 보여 준다.
4. 인증사업자는 기존 VPN으로 관리 시스템에 연결한다.
5. 관리자 접근 채널과 외부 배포 채널은 분리한다.
