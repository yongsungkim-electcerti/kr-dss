# 01. 시스템 구성도 — 구조 · 인터페이스 · 데이터

> 이 문서는 아래 **구성도 1장**을 설명한다. 구성요소(무엇이 있는가), 인터페이스(무엇이 오가는가), 데이터(무엇을 누가 갖는가) 순서로 읽는다.
> 구성도에는 구성요소 이름과 인터페이스 번호·이름만 적는다. 설명은 이 문서가 맡는다. DB·저장소는 각 서버의 내부 요소로 보고 구성도에 그리지 않는다.
> 편집본: [`diagrams/krtl-system.drawio`](diagrams/krtl-system.drawio)

![KR-TL 시스템 구성도](diagrams/krtl-system.drawio.png)

## 1. 개념

KR-TL은 "**어떤 인증사업자의 어떤 서비스를 언제부터 언제까지 신뢰하는가**"를 KISA가 서명해 공표한 목록이다.

구성도는 세 영역으로 나뉜다.

```
 인증사업자            신뢰체계 관리 시스템 (KISA · 신뢰앵커)            이용환경
 CA · OCSP · TSA  ─▶  관리 시스템 (폐쇄망) ─▶ 배포 시스템        ─▶  가입자 · 브라우저 · 이용자
```

- **인증사업자**와 **이용환경** 사이에 **신뢰체계 관리 시스템(KISA)** 이 있다. 이용환경은 인증사업자를 직접 믿지 않고, KISA가 서명한 TL을 통해 믿는다.
- KISA는 **신뢰앵커**다. 이용환경이 미리 갖고 있는 것은 KISA TL RootCA 인증서 하나뿐이고, 나머지 신뢰는 모두 TL을 거쳐 전달된다.
이 체계에는 네 주체가 있다.

| 주체 | 정의 | 하는 일 | TL과의 관계 |
|---|---|---|---|
| **관리자 (KISA)** | TL 운영 기관 | 인증사업자 신뢰정보를 심사하고 TL을 발행한다 | TL을 **만든다** |
| **인증사업자** | 전자서명 인정사업자 | 가입자에게 인증서를 발급하고, 자신의 서비스 정보를 KISA에 제출한다 | TL에 **실린다** |
| **가입자** | 인증사업자에게서 인증서를 받은 사람 또는 법인 | **서명의 주체.** 인증서로 문서에 전자서명하고, 서명 결과를 브라우저로 검증한다 | TL에 실린 사업자를 통해 **신뢰받는다** |
| **이용자** | 전자서명을 이용해 서비스하는 기관 | 가입자가 제출한 전자서명을 **검증**하고 서비스한다 | TL을 **사용한다** |
| **브라우저 (웨일)** | 서비스를 이용하는 사람의 브라우저 | 이용자가 제공한 **서명된 결과를 검증**해 보여 준다 (사용자 입장의 확인) | TL을 **사용한다** |

> 검증은 두 곳에서 일어난다. **이용자**는 서비스 처리를 위해 검증하고, **브라우저**는 서명된 결과를 받아 보는 사람의 입장에서 다시 확인한다.

PoC가 증명할 핵심 명제:

> **관리자가 TL을 바꾸면, 그 변화가 배포를 거쳐 이용자·브라우저의 검증 결과에 정확하게(시점까지 맞게) 반영된다. 그리고 그 과정은 위조·누락 없이 추적된다.**

## 2. 구성요소

구성도에는 구성요소 **이름만** 적고, 역할은 아래 표에서 설명한다.

### 관리 시스템 (폐쇄망)

| 구성요소 | 역할 |
|---|---|
| **관리 콘솔** | 관리자(시연자) 화면 — 신뢰정보 입력 · 확정, 상태 변경, TL 발행, 결과 비교. PoC는 로그인 · 역할 · 승인 분리 · 감사 없음 |
| **사업자 연계 서버** | 인증사업자의 신뢰정보 제출 접수(IF-01). 기존 VPN으로 연결 |
| **신뢰정보 관리 서버** | 사업자·서비스·서비스 인증서·**상태 이력**의 원천 관리, 제출 건 확정 |
| **TL 발행 서버** | 확정된 신뢰정보로 TL 편성 → 서명 → 반출 |
| **KISA TL RootCA** | KISA 최상위 인증기관. 이용자·브라우저가 TL을 신뢰하는 **최종 기준(신뢰 앵커)**. 평상시 오프라인 |
| **KISA TL CA** | KISA TL RootCA가 발급한 하위 인증기관. TL 서명 인증서 발급 |
| **TL 서명 인증서** | TL 서명키에 대응하는 인증서. KISA CA가 발급, TL에 함께 실려 이용자가 서명을 검증하는 데 쓴다 |
| **HSM** | TL 서명키 생성·보관·서명. 키는 밖으로 나가지 않음 |

### 배포 시스템

| 구성요소 | 역할 |
|---|---|
| **배포 WEB** | 외부 접점. TLS·프록시만, 데이터 없음 |
| **배포 WAS** | 서명된 TL 보관(버전별)·배포, 버전 확인(변경 여부 응답), 반출된 패키지 검증·게시, 접속 기록 저장과 **수신 현황 조회** |

### 인증사업자 · 가입자 · 이용자 · 브라우저

| 구성요소 | 역할 |
|---|---|
| **CA** | 가입자 인증서 발급 (기존 서비스 채널) |
| **OCSP** | 인증서 폐지 상태 응답 (기존 서비스 채널) |
| **TSA** | 타임스탬프 발급 (기존 서비스 채널, **PoC 미사용** — 서명 시각은 서명에 기록된 값) |
| **가입자** | 인증서로 문서에 전자서명 (KR-AdES), 서명 결과 검증 요청 (IF-09) |
| **이용자 시스템 (KR-DSS SDK)** | TL 수신·TL 서명 검증·캐시, 가입자 전자서명 검증, 서명된 결과 제공 |
| **웨일 브라우저** | TL 수신, 서명된 결과 검증·표시 (가입자 요청 IF-09, 이용자 제공 IF-08) |

## 3. 인터페이스

> 각 IF의 상세(오퍼레이션·데이터 항목·처리 규칙·오류)는 [06 IF 명세서](06-IF-명세서.md)에 있다.

| IF | 이름 | 출발 → 도착 | 언제 | 오가는 데이터 | 이 IF에서 확인할 것 |
|---|---|---|---|---|---|
| **IF-01** | 신뢰정보 제출 | 인증사업자 → 사업자 연계 서버 (KISA) | 등록·변경·상태 신고 시, 주기적 갱신 | 제출 내용(JSON: 사업자·서비스·인증서·상태 변경) | 제출자 인증(mTLS), 제출 형식 |
| **IF-02** | 관리 조작 | 관리자 → 관리 콘솔 | 시연 시 | 입력 확정, 상태 변경, TL 발행, 조회 | 소급 금지, 확정된 입력만 발행 |
| **IF-03** | 심사 요청 | 사업자 연계 서버 → 신뢰정보 관리 서버 | 제출 직후 | 제출 건 | 자동 반영 금지 — 확정 대기로만 |
| **IF-04** | 발행 대상 전달 | 신뢰정보 관리 서버 → TL 발행 서버 | 발행 시 | 확정된 신뢰정보 스냅숏 | 스냅숏 시점 고정 |
| **IF-05** | TL 서명 | TL 발행 서버 ↔ HSM | 서명 시 | 서명 대상 → 서명값 | 서명키는 HSM 밖으로 나가지 않음 |
| **IF-06** | TL 반출 | TL 발행 서버 → 배포 WAS | 발행 직후 (push) | 서명된 TL (XML) 하나 | 배포측 TL 서명 검증, 버전 단조 증가 |
| **IF-07** | TL 수신 | 이용자 시스템·웨일 브라우저 → 배포 WEB | 주기적·수시 | 버전 확인 요청 / 서명된 TL | 변경 시에만 다운로드, 요청자 기록 |
| **IF-08** | 서명 결과 제공 | 이용자 시스템 → 웨일 브라우저 | 결과 조회 시 | 서명된 결과 (문서·증명서 등) | — |
| **IF-09** | 서명 결과 검증 | 가입자 → 웨일 브라우저 | 결과 확인 시 | 서명된 결과 (문서·증명서 등) | 브라우저가 TL 기준으로 검증, 사용 TL 버전 표시 |

### 기존 서비스 채널 (IF 아님)

인증사업자가 이용환경에 직접 제공하는 서비스와, 가입자가 이용자에게 전자서명을 제출하는 흐름은 KR-TL 체계의 인터페이스가 아니다. 기존 전자서명 서비스 채널이며, 구성도에는 **점선**으로만 표시한다.

| 채널 | 제공 → 이용 | 내용 |
|---|---|---|
| 인증서 발급 | CA → 가입자 | 가입자 인증서 (PoC는 시뮬레이터 사용) |
| 타임스탬프 | TSA → 가입자 | 서명 시각 증명 (PoC 미사용) |
| 인증서 상태 확인 | OCSP → 이용자 시스템·웨일 브라우저 | 인증서 폐지 상태 (OCSP·CRL) |
| 전자서명 제출 | 가입자 → 이용자 시스템 | 전자서명 문서 (KR-AdES) |

채널 원칙 (상세는 [부록 A](부록/A-아키텍처-결정기록.md))
- 관리 ↔ 배포는 **IF-06 한 채널**뿐이고 연결은 **관리 쪽에서만** 시작한다 (방화벽 통제).
- 인증사업자는 기존 **VPN**으로 관리 시스템에 연결한다 (IF-01).
- 관리자 접근(IF-02)과 외부 배포(IF-07)는 다른 채널이다.
- 외부에 노출되는 것은 배포 WEB뿐이다.

### TL 신뢰 체인

```
KISA TL RootCA ──발급──▶ KISA TL CA ──발급──▶ TL 서명 인증서 ── (키: HSM) ──IF-05──▶ TL 서명
```

KISA 인증체계 안의 인증서 발급 관계(Root CA → KISA TL CA → TL 서명 인증서)는 **인터페이스가 아니다.** 인증체계 내부 관계로 보고 구성도에는 번호 없는 선으로만 잇는다.

이용자·브라우저는 **KISA TL RootCA 인증서 하나만** 미리 갖고 있으면 된다. TL에 실린 인증서 체인(TL 서명 인증서 → KISA TL CA)을 Root CA까지 따라가 TL 서명을 검증한다. 그래서 TL 서명키를 바꿔도(SC-09) 이용자 쪽 신뢰 기준은 바꾸지 않는다.

## 4. 데이터

### 4.1 데이터 목록

| 데이터 | 주요 항목 | 원천 | 흐르는 곳 |
|---|---|---|---|
| **D-01 사업자** | 사업자 식별자, 명칭, 연락처, 인정 상태 | 신뢰정보 관리 서버 | TL |
| **D-02 서비스** | 서비스 유형(CA·OCSP·TSA), 서비스명, **현재 상태와 상태 시작 시각** | 신뢰정보 관리 서버 | TL |
| **D-03 서비스 상태 이력** | (상태, 시작 시각, 사유, 근거 제출 건) 목록 | 신뢰정보 관리 서버 | TL (이력 포함) |
| **D-04 서비스 디지털 ID** | 서비스 인증서 — **같은 공개키**의 인증서만 여러 장 가능 (키가 바뀌면 새 서비스, 12 §2.3) | 신뢰정보 관리 서버 | TL |
| **D-05 제출 건** | 제출 유형, 내용, 확정 상태·의견 | 신뢰정보 관리 서버 | 관리 시스템 안 |
| **D-06 TL** | 일련번호, 발행 시각, **다음 발행 예정(NextUpdate)**, D-01~04 스냅숏 | TL 발행 서버 | 배포 시스템 |
| **D-07 발행본** | 서명된 TL(XML) — TL 서명 인증서 체인 포함 | TL 발행 | 배포 WAS |
| **D-08 TL 서명키·인증서** | 서명키(HSM 안), TL 서명 인증서 → KISA TL CA 인증서 → KISA TL RootCA 인증서 (인증서 체인) | HSM · KISA TL CA · KISA TL RootCA | 인증서 체인은 TL에 실림. 이용자·브라우저는 **KISA TL RootCA 인증서만** 미리 보유 |
| **D-09 접속 기록** | 시각, 요청자(기관·클라이언트 유형·버전), 요청 버전, 결과(신규 수신/변경 없음) | 배포 WAS | 배포 시스템 안 (수신 현황 조회) |
| **D-10 시험 기록** | 시험 실행 ID, 변경 내용 · 발행 TL 버전 · 이용환경 결과 (감사 기록은 PoC 핵심 범위 밖) | 관리 시스템 | 관리 시스템 안 |
| **D-11 검증 결과** | 판정(PASSED·FAILED·INDETERMINATE), 사유, **사용한 TL 버전** | 이용자 | 이용자 안 |

### 4.2 데이터가 TL 상태 판단에 쓰이는 방식

이용자와 브라우저는 서명을 검증할 때 TL에서 **"서명 시점에 그 서비스가 어떤 상태였는가"** 를 본다. 그래서 TL에는 현재 상태뿐 아니라 **상태 이력(D-03)** 이 실려야 한다.

```
가상공동인증A CA 상태 이력:  인정(11-02T10:00) ── 정지(11-03T10:00) ── 인정(11-04T10:00) ── 철회(11-05T10:00)

서명 시각 11-02T15:00+09:00  → 인정 구간 → 통과
서명 시각 11-03T15:00+09:00  → 정지 구간 → 실패
서명 시각 11-01T15:00+09:00  → 최초 인정 이전 → 판단 보류
```

- **PoC 기준 시각은 서명에 기록된 서명 시각(한국 시간, ISO 8601 `+09:00`)** 이다. TSA로 증명하지 않는다.
- 경계 · 최초 인정 이전 · 서명 시각 없음 규칙과 표본별 판정은 [18 신뢰 경로 판정표](18-신뢰경로-판정표.md).

### 4.3 인증서 발급 관계와 TL 신뢰 관계

| 관계 | 내용 | TL이 바뀔 때 |
|---|---|---|
| **인증서 발급 관계** | RootCA → CA → 가입자 인증서 (인증기관이 만듦) | **바뀌지 않음** |
| **TL 신뢰 관계** | KISA TL RootCA → TL → TL 신뢰점(등재된 Root 또는 CA)과 그 상태 | 등재 · 상태 · 이력이 바뀜 |

TL은 인증서 발급 관계를 다시 만들지 않는다. 같은 인증서 체인이라도 TL 신뢰 관계에 따라 수용 · 거부가 달라진다 ([18](18-신뢰경로-판정표.md) §6).

## 5. 한 번의 TL 변경이 흐르는 경로

```
인증사업자 신고(IF-01) ─▶ 심사(IF-03, IF-02) ─▶ 발행·서명(IF-04, IF-05)
   ─▶ 반출(IF-06) ─▶ 이용자·브라우저 TL 수신(IF-07) ─▶ 검증 결과 변화(D-11)
   ─▶ 배포 WAS가 접속 기록(D-09) 저장 ─▶ "누가 아직 안 받았는지" 확인
```

이 경로 하나하나가 [03 시나리오](03-이용-시나리오.md)에서 검증 대상이 된다.
