# 01. 시스템 구성도 — 구조 · 인터페이스 · 데이터

> 이 문서는 아래 **구성도 1장**을 설명한다. 구성요소(무엇이 있는가), 인터페이스(무엇이 오가는가), 데이터(무엇을 누가 갖는가) 순서로 읽는다.
> 구성도에는 구성요소 이름과 인터페이스 번호만 적는다. 설명은 이 문서가 맡는다.
> 편집본: [`diagrams/krtl-system.drawio`](diagrams/krtl-system.drawio)

![KR-TL 시스템 구성도](diagrams/krtl-system.drawio.png)

## 1. 개념

KR-TL은 "**어떤 인증사업자의 어떤 서비스를 언제부터 언제까지 신뢰하는가**"를 KISA가 서명해 공표한 목록이다.
이 체계에는 네 주체가 있다.

| 주체 | 하는 일 | TL과의 관계 |
|---|---|---|
| **관리자 (KISA)** | 인증사업자 신뢰정보를 심사하고 TL을 발행한다 | TL을 **만든다** |
| **인증사업자** | 사용자에게 인증서를 발급하고, 자신의 서비스 정보를 KISA에 제출한다 | TL에 **실린다** |
| **사용자 (서명자)** | 인증사업자가 발급한 인증서로 문서에 전자서명한다 | TL에 실린 사업자를 **통해 신뢰받는다** |
| **이용자 (검증)** | 이용기관 서비스·브라우저 에이전트. 받은 전자서명을 TL로 검증한다 | TL을 **사용한다** |

PoC가 증명할 핵심 명제:

> **관리자가 TL을 바꾸면, 그 변화가 배포를 거쳐 이용자의 검증 결과에 정확하게(시점까지 맞게) 반영된다. 그리고 그 과정은 위조·누락 없이 추적된다.**

## 2. 구성요소

구성도에는 구성요소 **이름만** 적고, 역할은 아래 표에서 설명한다.

### 관리 시스템 (폐쇄망)

| 구성요소 | 역할 |
|---|---|
| **관리 콘솔** | 관리자 화면. 역할별 권한(운영자·심사자·승인자·감사자). 통계 조회 포함 |
| **사업자 연계 서버** | 인증사업자 제출 접수(IF-01), 사업자 정보 자동 수집(IF-02). 기존 VPN으로 연결 |
| **신뢰정보 관리 서버** | 사업자·서비스·서비스 인증서·**상태 이력**의 원천 관리, 제출 건 심사 |
| **TL 발행 서버** | 승인된 신뢰정보로 TL 편성 → 승인 → 서명 → 배포 패키지 생성 |
| **HSM** | TL 서명키 보관·서명. 키는 밖으로 나가지 않음 |
| **관리 DB** | 신뢰정보 원천, TL 버전 |
| **감사로그 DB** | 모든 변경·승인·서명 기록 (해시 연결) |
| **연계 서버** | 배포 시스템과 통하는 **유일한 통로**. 패키지 반출, 배포 결과·접속 기록 회수 |
| **통계 서버** | 접속 기록 집계 — 어느 이용자가 어느 TL 버전을 받았는가 |
| **통계 DB** | 장기 통계 |

### 배포 시스템

| 구성요소 | 역할 |
|---|---|
| **배포 WEB** | DMZ에 두는 유일한 구성요소. TLS·프록시만, 데이터 없음 |
| **배포 WAS** | TL 배포, 버전 확인(변경 여부 응답), 접속 기록 수집, 반출된 패키지 검증·게시 |
| **배포 저장소** | 서명된 TL 사본, 버전별 보관 |
| **배포 DB** | 배포 이력, 접속 기록 |

### 인증사업자 · 사용자 · 이용자 (기존 체계)

| 구성요소 | 역할 |
|---|---|
| **CA** | 사용자 인증서 발급 (IF-12) |
| **OCSP** | 인증서 폐지 상태 응답 (IF-14) |
| **TSA** | 서명 시각을 증명하는 타임스탬프 발급 (IF-15) |
| **사용자** | 인증서로 문서에 전자서명 (KR-AdES) |
| **이용기관 시스템 (KR-DSS SDK)** | TL 동기화·TL 서명 검증·캐시, 전자서명 검증 |
| **브라우저 에이전트** | 브라우저에서 TL을 받아 검증에 사용 |

## 3. 인터페이스

| IF | 출발 → 도착 | 언제 | 오가는 데이터 | 이 IF에서 확인할 것 |
|---|---|---|---|---|
| **IF-01** | 인증사업자 → 사업자 연계 서버 | 사업자가 등록·변경·상태 신고할 때 | 제출서(사업자·서비스·인증서·상태 변경), 사업자 전자서명 | 제출자 인증, 제출서 서명·형식 |
| **IF-02** | 사업자 연계 서버 → 인증사업자 | 주기적 | 사업자가 공개하는 서비스 인증서·상태 | 관리 DB 기준값과의 차이 |
| **IF-03** | 관리자 → 관리 콘솔 | 운영 시 | 심사 결정, 상태 변경, 발행 승인, 조회 | 역할 권한, 생성자 ≠ 승인자 |
| **IF-04** | 사업자 연계 서버 → 신뢰정보 관리 서버 | 제출·수집 직후 | 제출 건, 변경 후보 | 자동 반영 금지 — 심사 대기로만 |
| **IF-05** | 신뢰정보 관리 서버 → TL 발행 서버 | 발행 시 | 승인된 신뢰정보 스냅숏 | 스냅숏 시점 고정 |
| **IF-06** | TL 발행 서버 ↔ HSM | 서명 시 | 서명 대상 → 서명값 | 승인 이력이 있는 요청만 |
| **IF-07** | TL 발행 서버 → 연계 서버 | 서명 직후 | 배포 패키지 | 패키지 해시·서명 |
| **IF-08** | 연계 서버 → 배포 WAS | 발행 직후 (push) | 배포 패키지 | 배포측 서명 검증, 버전 단조 증가 |
| **IF-09** | 연계 서버 → 배포 WAS | 주기적 (pull) | 배포 결과, 접속 기록 | 누락 없는 회수 (이어받기) |
| **IF-10** | 연계 서버 → 통계 서버 | 회수 직후 | 접속 기록 | — |
| **IF-11** | 이용기관 시스템·브라우저 에이전트 → 배포 WEB | 주기적·수시 | 버전 확인 요청 / 서명된 TL | 변경 시에만 다운로드, 요청자 기록 |
| **IF-12** | CA → 사용자 | 기존 체계 | 사용자 인증서 | (PoC 범위 밖, 시뮬레이터 사용) |
| **IF-13** | 사용자 → 이용기관 시스템 | 서명 제출 시 | 전자서명 문서 (KR-AdES) | — |
| **IF-14** | 이용기관 시스템 → OCSP | 검증 시 | 인증서 폐지 상태 (OCSP·CRL) | 기존 체계 그대로 사용 |
| **IF-15** | 사용자 → TSA | 서명 시 | 타임스탬프 | 서명 시각 증명 — 시점별 판단의 근거 |

채널 원칙 (상세는 [부록 A](부록/A-아키텍처-결정기록.md))
- 관리 ↔ 배포는 **IF-08·09 한 채널**뿐이고 연결은 **관리 쪽에서만** 시작한다 (방화벽 통제).
- 인증사업자는 기존 **VPN**으로 관리 시스템에 연결한다 (IF-01·02).
- 관리자 접근(IF-03)과 외부 배포(IF-11)는 다른 채널이다.
- DMZ에는 배포 WEB만 둔다.

## 4. 데이터

### 4.1 데이터 목록

| 데이터 | 주요 항목 | 원천 | 흐르는 곳 |
|---|---|---|---|
| **D-01 사업자** | 사업자 식별자, 명칭, 연락처, 인정 상태 | 관리 DB | TL |
| **D-02 서비스** | 서비스 유형(CA·OCSP·TSA), 서비스명, **현재 상태와 상태 시작 시각** | 관리 DB | TL |
| **D-03 서비스 상태 이력** | (상태, 시작 시각, 사유, 근거 제출 건) 목록 | 관리 DB | TL (이력 포함) |
| **D-04 서비스 디지털 ID** | 서비스 인증서(복수 가능: 갱신 중 신·구 공존) | 관리 DB | TL |
| **D-05 제출 건** | 제출 유형, 내용, 제출 서명, 심사 상태·의견 | 관리 DB | 관리 시스템 안 |
| **D-06 TL** | 일련번호, 발행 시각, **다음 발행 예정(NextUpdate)**, D-01~04 스냅숏 | 관리 DB(버전) | 배포 패키지 |
| **D-07 배포 패키지** | 서명된 TL(XML·JWS), 매니페스트(버전·해시), TL 서명 인증서 | TL 발행 | 배포 저장소 |
| **D-08 TL 서명키·인증서** | 서명키(HSM 안), 서명 인증서(공개 — 이용자의 신뢰 기준) | HSM | 인증서만 이용자에게 |
| **D-09 접속 기록** | 시각, 요청자(기관·클라이언트 유형·버전), 요청 버전, 결과(신규 수신/변경 없음) | 배포 DB | 통계 DB |
| **D-10 감사 기록** | 누가·언제·무엇을·왜, 이전 기록 해시 | 감사로그 DB | 관리 시스템 안 |
| **D-11 검증 결과** | 판정(PASSED·FAILED·INDETERMINATE), 사유, **사용한 TL 버전** | 이용자 | 이용자 안 |

### 4.2 데이터가 TL 상태 판단에 쓰이는 방식

이용자는 서명을 검증할 때 TL에서 **"서명 시점에 그 서비스가 어떤 상태였는가"** 를 본다. 그래서 TL에는 현재 상태뿐 아니라 **상태 이력(D-03)** 이 실려야 한다.

```
서비스 X 상태 이력:  granted(2026-01-01) ── suspended(2026-11-10 09:00) ── granted(2026-11-12 18:00)

서명 시각 2026-11-09  → granted 구간 → 신뢰
서명 시각 2026-11-11  → suspended 구간 → 불신
타임스탬프 없음       → 서명 시각 증명 불가 → 검증 정책에 따름 (아래 개념 참고)
```

서명 시각은 **타임스탬프(TSA, IF-15)** 로 증명한다.

**개념 — 타임스탬프 없는 서명**: 서명 시각을 증명할 수 없으므로 "언제 기준으로 상태를 볼 것인가"가 정해지지 않는다. 검증 시점의 상태로 볼 수도, 판단을 보류할 수도 있다. 이 기준은 **검증 정책으로 향후 결정**하며, PoC에서는 두 경우의 결과 차이를 보여 주는 것으로 개념을 설명한다.

## 5. 한 번의 TL 변경이 흐르는 경로

```
인증사업자 신고(IF-01) ─▶ 심사(IF-04, IF-03) ─▶ 발행·서명(IF-05, IF-06)
   ─▶ 반출(IF-07, IF-08) ─▶ 이용자 동기화(IF-11) ─▶ 검증 결과 변화(D-11)
   ─▶ 접속 기록 회수(IF-09, IF-10) ─▶ 관리자가 "누가 아직 안 받았는지" 확인
```

이 경로 하나하나가 [03 시나리오](03-이용-시나리오.md)에서 검증 대상이 된다.
