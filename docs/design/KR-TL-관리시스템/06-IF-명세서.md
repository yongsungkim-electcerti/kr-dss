# 06. 인터페이스(IF) 명세서

> 대상: [01 시스템 구성도](01-시스템-구성도.md)의 인터페이스 IF-01 ~ IF-09
> 성격: PoC 기준 명세. 프로토콜·경로·항목명은 **PoC 구현 기준안**이며, 운영 환경 값(주기·보존기간 등)은 향후 결정한다.
> 기존 서비스 채널(인증서 발급·타임스탬프·OCSP·전자서명 제출)과 KISA 인증체계 내부 발급 관계는 IF가 아니므로 이 문서에서 다루지 않는다.

## 1. IF 목록

| IF | 이름 | 송신 | 수신 | 구간 | 방식 | 발생 시점 |
|---|---|---|---|---|---|---|
| **IF-01** | 신뢰정보 제출 | 인증사업자 | 사업자 연계 서버 | 외부 → 관리 시스템 (VPN) | HTTPS REST · mTLS · 서명된 제출서 | 등록·변경·상태 신고, 주기적 갱신 |
| **IF-02** | 관리 접속 | 관리자 | 관리 콘솔 | 관리자 → 관리 시스템 | HTTPS 웹 화면 · 로그인 세션 | 운영 시 |
| **IF-03** | 심사 요청 | 사업자 연계 서버 | 신뢰정보 관리 서버 | 관리 시스템 내부 | 내부 API | 제출 검증 직후 |
| **IF-04** | 발행 대상 전달 | 신뢰정보 관리 서버 | TL 발행 서버 | 관리 시스템 내부 | 내부 API | 발행 초안 생성 시 |
| **IF-05** | TL 서명 | TL 발행 서버 | HSM | 관리 시스템 내부 | PKCS#11 (PoC: 소프트 키스토어) | 발행 승인 후 |
| **IF-06** | 패키지 반출 | TL 발행 서버 | 배포 WAS | 관리 시스템 → 배포 시스템 (단일 채널) | HTTPS REST · mTLS · push | 서명 직후 |
| **IF-07** | TL 수신 | 이용자 시스템 · 웨일 브라우저 | 배포 WEB (→ 배포 WAS) | 외부 → 배포 시스템 | HTTPS GET · 조건부 요청 | 주기적·수시 |
| **IF-08** | 서명 결과 제공 | 이용자 시스템 | 웨일 브라우저 | 이용환경 | HTTPS (이용자 서비스 화면) | 결과 조회 시 |
| **IF-09** | 서명 결과 검증 | 가입자 | 웨일 브라우저 | 이용환경 | 브라우저 내 검증 요청 (파일 열기) | 결과 확인 시 |

## 2. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 문자 인코딩 | UTF-8 |
| 메시지 형식 | JSON (`application/json`). 파일은 원본 형식 그대로 |
| 시각 | ISO 8601, UTC (`2026-11-10T00:00:00Z`) |
| TL 일련번호 | 양의 정수, 발행마다 1씩 증가 (`seq`) |
| 식별자 | 사업자 `providerId`, 서비스 `serviceId`, 제출 건 `submissionId` — 관리 시스템이 부여하는 문자열 |
| 서명 형식 | 제출서·매니페스트: JWS(RFC 7515). TL: XML(ETSI TS 119 612 + XAdES), JWS 두 형식 |
| 버전 | 경로에 API 버전 표기 (`/v1/`) |
| 감사 | IF-01 ~ IF-06의 모든 요청·결과는 감사 기록(D-10)에 남긴다 |

### 2.1 공통 오류 응답

```json
{ "code": "SIGNATURE_INVALID", "message": "제출서 서명 검증 실패", "traceId": "..." }
```

| 코드 | 의미 | 주로 쓰는 IF |
|---|---|---|
| `UNAUTHORIZED` | 인증 실패 (인증서·세션) | IF-01, 02, 06 |
| `FORBIDDEN` | 권한 없음 (역할·생성자=승인자 등) | IF-02 |
| `INVALID_FORMAT` | 형식·필수 항목 오류 | 전체 |
| `SIGNATURE_INVALID` | 서명 검증 실패 | IF-01, 06, 07 |
| `VERSION_NOT_INCREASING` | 일련번호가 현재보다 크지 않음 | IF-06, 07 |
| `NOT_FOUND` | 대상 없음 | IF-01, 07 |
| `CONFLICT` | 상태 충돌 (이미 처리된 건 등) | IF-02, 03 |

## 3. IF 상세

### IF-01 신뢰정보 제출

| 항목 | 내용 |
|---|---|
| 목적 | 인증사업자가 자기 사업자·서비스·서비스 인증서·상태 정보를 KISA에 제출한다 |
| 송신 → 수신 | 인증사업자 → 사업자 연계 서버 |
| 연결 | 기존 VPN, HTTPS + mTLS (사업자 연계 인증서로 사업자 식별) |
| 관련 데이터 | D-01 ~ D-05 |
| 관련 화면·시나리오 | M-04 · SC-01, 02, 03, 05, 12 |

**오퍼레이션**

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/provider/v1/submissions` | 제출서 제출 |
| GET | `/provider/v1/submissions/{submissionId}` | 처리 결과 조회 |

**제출서 (JWS payload)**

| 항목 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `providerId` | string | ○ | 사업자 식별자 (신규 등록 시 생략) |
| `type` | enum | ○ | `REGISTER_PROVIDER` · `ADD_SERVICE` · `UPDATE_SERVICE` · `ADD_DIGITAL_ID` · `REMOVE_DIGITAL_ID` · `STATUS_CHANGE` · `PERIODIC_RENEWAL` |
| `provider` | object | △ | 사업자 정보 (D-01) — 등록·변경 시 |
| `service` | object | △ | 서비스 유형(CA·OCSP·TSA)·서비스명 (D-02) |
| `digitalIds[]` | base64 DER | △ | 서비스 인증서 (D-04) |
| `statusChange` | object | △ | `{ status, effectiveAt, reason }` — 상태 신고 시 |
| `submittedAt` | datetime | ○ | 제출 시각 |

**응답**

| 항목 | 설명 |
|---|---|
| `submissionId` | 접수 번호 |
| `status` | `RECEIVED` → `UNDER_REVIEW` → `APPROVED` · `REJECTED` → `PUBLISHED` |
| `publishedTlSeq` | 반영된 TL 일련번호 (반영 후) |
| `reason` | 반려 사유 |

**처리 규칙**
1. mTLS 인증서가 등록된 사업자인지 확인한다. 아니면 `UNAUTHORIZED`.
2. 제출서 JWS 서명을 사업자 인증서로 검증한다. 실패하면 `SIGNATURE_INVALID`로 즉시 반려하고 심사로 넘기지 않는다 (SC-12).
3. 검증된 제출서만 IF-03으로 심사 요청한다. **TL에 자동 반영하지 않는다.**

---

### IF-02 관리 접속

| 항목 | 내용 |
|---|---|
| 목적 | 관리자가 관리 콘솔에서 심사·상태 변경·발행·조회를 한다 |
| 송신 → 수신 | 관리자 → 관리 콘솔 |
| 연결 | 관리자 전용 접근 경로, HTTPS, 로그인 세션 (PoC: 역할 선택 로그인) |
| 관련 데이터 | D-01 ~ D-06, D-10 |
| 관련 화면·시나리오 | M-01 ~ M-09 · 전체, SC-11 |

**주요 기능 (콘솔 → 관리 서버 API)**

| 기능 | 경로 (PoC 기준안) | 역할 |
|---|---|---|
| 제출 건 심사 | `POST /admin/v1/submissions/{id}/decision` `{ decision, comment }` | 심사자 |
| 상태 변경 요청 | `POST /admin/v1/services/{serviceId}/status` `{ status, effectiveAt, reason, urgent }` | 운영자 |
| TL 초안 생성 | `POST /admin/v1/tl/drafts` → 직전 버전과 차이 반환 | 운영자 |
| 발행 승인 | `POST /admin/v1/tl/drafts/{draftId}/approve` | 승인자 |
| 조회 | `GET /admin/v1/providers`, `/tl/versions`, `/audit` | 전체 |

**처리 규칙**
1. 역할별 권한을 검사한다. 권한 밖이면 `FORBIDDEN`.
2. 초안 작성자와 승인자가 같으면 `FORBIDDEN`으로 거부하고 감사 기록에 남긴다 (SC-11).
3. 상태 변경의 `effectiveAt`이 과거이면 소급 표시를 붙인다. 허용 범위는 향후 결정한다.

### IF-03 심사 요청

| 항목 | 내용 |
|---|---|
| 목적 | 검증을 통과한 제출서를 심사 대기열에 등록한다 |
| 송신 → 수신 | 사업자 연계 서버 → 신뢰정보 관리 서버 |
| 연결 | 관리 시스템 내부 API |
| 관련 데이터 | D-05 |

**요청 항목**

| 항목 | 설명 |
|---|---|
| `submissionId` | IF-01 접수 번호 |
| `providerId`, `type` | 제출서 값 |
| `payload` | 제출서 원문 (JWS 그대로) |
| `verification` | 제출자 인증·서명 검증 결과 |
| `receivedAt` | 접수 시각 |

**응답**: `{ caseId, status: "UNDER_REVIEW" }`

**처리 규칙**: 같은 `submissionId`가 다시 오면 기존 건을 돌려준다 (중복 등록 없음).

---

### IF-04 발행 대상 전달

| 항목 | 내용 |
|---|---|
| 목적 | 승인된 신뢰정보를 한 시점으로 고정해 TL 발행 서버에 넘긴다 |
| 송신 → 수신 | 신뢰정보 관리 서버 → TL 발행 서버 |
| 연결 | 관리 시스템 내부 API |
| 관련 데이터 | D-01 ~ D-04 → D-06 |

**전달 항목 (스냅숏)**

| 항목 | 설명 |
|---|---|
| `snapshotId`, `takenAt` | 스냅숏 식별자·고정 시각 |
| `baseSeq` | 직전 TL 일련번호 (차이 계산 기준) |
| `providers[]` | 사업자 → 서비스 → 서비스 인증서(복수) → **상태 이력** 전체 |
| `urgent` | 긴급 발행 여부 (SC-03) |

**처리 규칙**
1. 스냅숏 이후의 변경은 이번 TL에 들어가지 않는다.
2. TL 발행 서버는 `baseSeq` 대비 차이를 계산해 IF-02(M-05)로 보여 준다.

### IF-05 TL 서명

| 항목 | 내용 |
|---|---|
| 목적 | 승인된 TL과 매니페스트에 TL 서명키로 서명한다 |
| 송신 → 수신 | TL 발행 서버 → HSM |
| 연결 | PKCS#11 (PoC: PKCS#12 소프트 키스토어) |
| 관련 데이터 | D-06, D-07, D-08 |

**요청 / 응답**

| 구분 | 항목 | 설명 |
|---|---|---|
| 요청 | `keyLabel` | TL 서명키 식별자 |
| 요청 | `algorithm` | 예: `SHA256withECDSA`, `SHA256withRSA` |
| 요청 | `toBeSigned` | 서명 대상 (해시 또는 서명 입력값) |
| 요청 | `approvalRef` | 발행 승인 기록 참조 |
| 응답 | `signatureValue` | 서명값 |

**처리 규칙**
1. 승인 기록(`approvalRef`)이 없는 요청은 서명하지 않는다.
2. 서명키는 HSM 밖으로 나가지 않는다.
3. TL에는 TL 서명 인증서 체인(TL 서명 인증서 → KISA CA)을 함께 싣는다.

### IF-06 패키지 반출

| 항목 | 내용 |
|---|---|
| 목적 | 서명된 TL 배포 패키지를 배포 시스템에 게시한다 |
| 송신 → 수신 | TL 발행 서버 → 배포 WAS |
| 연결 | 관리 시스템 → 배포 시스템 **단일 채널**, HTTPS + mTLS. 연결은 관리 시스템에서만 시작한다 |
| 관련 데이터 | D-07 |
| 관련 화면·시나리오 | M-05, M-06 · SC-03, 08, 10 |

**오퍼레이션**: `POST /dist/v1/packages` (multipart)

**배포 패키지**

| 파일 | 설명 |
|---|---|
| `manifest.json` | `seq`, `issuedAt`, `nextUpdate`, 파일 목록과 각 해시 |
| `manifest.jws` | 매니페스트 서명 (IF-05) |
| `kr-tl-{seq}.xml` | TL — ETSI TS 119 612 + XAdES |
| `kr-tl-{seq}.jws` | TL — JWS |

**응답**: `{ seq, publishedAt, status: "PUBLISHED" | "ALREADY_PUBLISHED" }`

**처리 규칙 (배포 WAS)**
1. 매니페스트 서명을 KISA Root CA까지 체인 검증한다. 실패하면 `SIGNATURE_INVALID`.
2. 파일 해시를 매니페스트와 대조한다.
3. `seq`가 현재 게시 버전보다 작으면 `VERSION_NOT_INCREASING`, 같으면 `ALREADY_PUBLISHED` (재전송 허용).
4. 검증을 마친 뒤 최신 버전을 한 번에 교체한다.

### IF-07 TL 수신

| 항목 | 내용 |
|---|---|
| 목적 | 이용자 시스템과 웨일 브라우저가 최신 TL을 받는다 |
| 송신 → 수신 | 이용자 시스템 · 웨일 브라우저 → 배포 WEB (배포 WAS가 처리) |
| 연결 | 공개 HTTPS |
| 관련 데이터 | D-06, D-09 |
| 관련 화면·시나리오 | M-07 · SC-01, 03, 06, 07, 08 |

**오퍼레이션**

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/tl/v1/latest?format=xml\|jws` | 최신 TL |
| GET | `/tl/v1/{seq}?format=xml\|jws` | 특정 버전 |
| GET | `/tl/v1/latest/meta` | `seq`, `issuedAt`, `nextUpdate`, 해시 |

**요청 헤더**

| 헤더 | 설명 |
|---|---|
| `If-None-Match` | 갖고 있는 TL의 ETag. 같으면 `304 Not Modified` |
| `X-KRTL-Client` | 클라이언트 유형·버전 (예: `sdk/1.2`, `whale/4.x`) |

**응답**: `200` + TL 본문 + `ETag` / `304` (변경 없음)

**처리 규칙**
- 배포 WAS는 모든 요청을 접속 기록(D-09)으로 남긴다: 시각, 클라이언트 유형·버전, 요청 버전, 결과(200/304).
- **수신 측 의무** (이용자 시스템·브라우저):
  1. TL 서명을 KISA Root CA까지 체인 검증한다.
  2. `seq`가 보유본보다 작으면 거부한다 (되돌리기 방지).
  3. 검증 실패 시 새 TL을 버리고 보유본을 유지한다.
  4. 보유본이 `nextUpdate`를 지났는지 확인한다 (판정 정책은 향후 결정).

### IF-08 서명 결과 제공

| 항목 | 내용 |
|---|---|
| 목적 | 이용자 시스템이 처리한 서명 결과(서명 문서·증명서 등)를 브라우저에 제공한다 |
| 송신 → 수신 | 이용자 시스템 → 웨일 브라우저 |
| 연결 | 이용자 서비스 화면 (HTTPS) |
| 관련 데이터 | D-11 |
| 관련 시나리오 | SC-03 |

**제공 항목**

| 항목 | 설명 |
|---|---|
| 서명 결과 파일 | KR-AdES 서명 문서 (PDF 등) |
| `verification` (선택) | 이용자 시스템의 판정·사유·사용한 TL 버전 |

**처리 규칙**: 브라우저는 이용자 시스템의 판정을 그대로 믿지 않고 자기 TL로 다시 검증한다. 같은 TL 버전이면 판정이 같아야 한다.

### IF-09 서명 결과 검증

| 항목 | 내용 |
|---|---|
| 목적 | 가입자가 자기 서명 결과를 브라우저에서 검증한다 |
| 송신 → 수신 | 가입자 → 웨일 브라우저 |
| 연결 | 브라우저 안 (파일 열기·끌어 놓기) |
| 관련 데이터 | D-11 |
| 관련 시나리오 | SC-03, 04, 05 |

**입력 / 출력**

| 구분 | 항목 | 설명 |
|---|---|---|
| 입력 | 서명 결과 파일 | 가입자가 연 서명 문서 |
| 출력 | 판정 | PASSED · FAILED · INDETERMINATE |
| 출력 | 사유 | 발급자 미등재, 서명 시점 서비스 정지, 인증서 폐지 등 |
| 출력 | 사용한 TL 버전 | `seq`, `issuedAt` |
| 출력 | 서명 시각 근거 | 타임스탬프 유무와 시각 |

**처리 규칙**: 검증 절차는 이용자 시스템과 같다 ([03](03-이용-시나리오.md) 1.4 [B]). 서명 시각에 해당하는 서비스 상태를 TL 상태 이력에서 찾는다.
