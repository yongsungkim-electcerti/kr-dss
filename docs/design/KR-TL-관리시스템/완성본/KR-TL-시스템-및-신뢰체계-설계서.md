# KR-TL 시스템 및 신뢰체계 설계서

KR-TL은 어떤 인증사업자의 어떤 서비스를 어느 시점에 신뢰할 수 있는지 판단하는 데 쓰는 서명된 신뢰목록이다. KISA가 확인한 사업자·서비스 정보와 상태 이력을 TL에 담아 발행하면, 이용기관과 브라우저는 이를 받아 가입자 서명의 신뢰 여부를 판단한다.

이 설계의 중심은 관리자의 변경이 이용환경의 판정까지 이어지는 구조다. 인증서 발급 체인은 그대로 두어도 TL의 등재 정보, 상태 이력, 이용환경이 보유한 버전이 달라지면 같은 서명의 판정이 달라질 수 있다. 각 장은 그 연결을 시스템·인증서·데이터·시간의 관점에서 설명한다.

## 1 시스템 구성

### 1.1 시스템 구성도

인증사업자는 가입자 인증서를 발급하고 자신의 서비스 정보를 KISA에 제출한다. KISA의 관리 시스템은 제출 내용을 확인하여 등재 정보를 관리하고 TL을 발행한다. 배포 시스템은 서명된 TL을 게시하며, 이용기관과 브라우저는 각자 TL을 받아 검증에 사용한다.

가입자는 인증서를 사용해 문서에 서명하는 사람 또는 법인이다. 이용기관은 제출된 서명을 검증해 서비스를 처리한다. 브라우저 검증 모듈은 결과를 받는 사용자의 관점에서 신뢰정보를 확인한다. 이후 본문에서 ‘이용환경’은 이용기관 시스템과 브라우저 검증 모듈을 함께 가리킨다.

| 브라우저 검증 모듈 | 사용자 측 TL 활용과 결과 표시 | 자체 보유 TL, 서명 또는 표본 정보, 판정 |

### 1.2 관리 시스템

관리 시스템은 제출 접수, 신뢰정보 관리, TL 발행을 나누어 맡는다. 제출을 접수했다는 사실만으로 서비스가 TL에 실리지는 않는다. 입력 확정 이후의 정보만 발행 대상이 되며, 발행 중에 들어온 변경은 다음 버전에 반영한다.

| 구성요소 | 책임 | 입력과 출력 |
| --- | --- | --- |
| 관리 콘솔 | 사업자·서비스 조회, 입력 확정, 상태 변경, 발행과 결과 비교 | 관리자 조작 → 처리 결과 |
| 사업자 연계 서버 | 제출자 인증과 형식 확인, 접수 결과 제공 | 제출 JSON → 확정 대기 제출 건 |
| 신뢰정보 관리 서버 | 사업자·서비스·디지털 ID·상태 이력의 원천 관리 | 확정된 제출 → 등재 정보와 스냅숏 |
| TL 발행 서버 | 스냅숏 편성, TL 서명 요청, 발행본 보관과 반출 | 스냅숏 → 서명된 TL |
| HSM | TL 서명키 보관과 서명 연산 | 서명 입력 → 서명값 |

HSM이 반환하는 것은 서명값이다. TL 발행 서버는 이를 XML 서명 구조에 반영한다. 서명키 자체는 TL이나 배포 데이터에 포함하지 않는다. 개념 구성에서의 HSM은 PoC에서 파일 키로 대체하지만, 실제 키 보호 수준까지 같다고 보지는 않는다.

### 1.3 배포 시스템

배포 WEB은 외부 HTTPS 요청을 받아 배포 WAS로 전달한다. 배포 WAS는 게시할 TL을 검증하고 버전별로 보관하며 최신 TL, 특정 버전, 변경 확인 정보를 제공한다. 배포 시스템은 등재 상태를 결정하거나 TL을 새로 서명하지 않는다.

[도식 원본 — krtl-network](diagrams/krtl-network.drawio)

그림 2 관리 영역과 배포 영역의 접근 경계

인증사업자는 기존 VPN과 mTLS를 사용하는 제출 경로로 관리 시스템에 접근한다. 관리자의 콘솔 접근은 공개 배포 경로와 분리한다. 관리 시스템과 배포 시스템 사이의 반출 연결은 관리 쪽에서 시작하며, 배포 쪽에서 관리 영역으로 새 연결을 시작하는 경로는 두지 않는다. 허용된 요청의 응답은 같은 연결로 돌아온다.

그림 2는 논리적 접근 경계를 나타낸다. 물리 서버 수, 장비 제품, 이중화 방식과 운영 포트는 구축 단계에서 정한다. 본문의 구성요소 하나가 반드시 물리 서버 한 대를 뜻하지는 않는다.

## 2 인증 및 신뢰체계

### 2.1 인증체계 구성

KR-TL에는 서로 다른 두 검증 경로가 만난다. 하나는 TL 자체가 신뢰할 수 있는 발행자가 서명한 정보인지 확인하는 경로다. 다른 하나는 가입자 인증서가 TL에 등재된 서비스의 신뢰점에 연결되는지 확인하는 경로다.

[도식 원본 — krtl-trust-connection](diagrams/krtl-trust-connection.drawio)

그림 3 TL 서명 검증과 가입자 인증서 검증의 연결

TL 서명 인증체계는 KISA TL RootCA → KISA TL CA → TL 서명 인증서로 구성한다. 이용환경은 KISA TL RootCA 인증서를 사전에 보유한다. 수신한 TL에 포함된 TL 서명 인증서와 KISA TL CA 인증서를 사전 신뢰앵커까지 검증하고, TL 서명 인증서의 공개키로 TL의 서명을 확인한다.

가입자 인증서의 검증은 검증된 TL을 기준으로 이어진다. 이용환경은 가입자 인증서 체인에서 등재된 RootCA 또는 CA를 찾고, 해당 서비스의 상태 이력과 서명 시각을 대조한다. TL 서명 인증서가 사업자 CA를 발급하는 구조는 아니다. TL이 사업자 서비스의 신뢰점과 상태를 서명된 정보로 연결한다.

그림 4 상세 간편인증 체계와 등재 레벨

가상 공동인증사업자 JA와 JB는 공동인증용 KISA RootCA 아래에 각각 CA를 둔다. 간편인증사업자 SA와 SB는 각각 자체 RootCA 아래에 CA를 둔다. 각 CA는 가입자 인증서와 OCSP·TSA 서비스 인증서를 발급한다. 공동인증용 KISA RootCA와 TL 검증용 KISA TL RootCA는 서로 다른 인증서다.

이 설계에서 JA·JB·SA·SB는 시험을 설명하기 위한 가상 사업자다. 실제 사업자나 실제 인정 결과를 나타내지 않는다. 인증체계 사이에 상호 인증을 추가하지 않고, 각 체계의 등재 대상과 인정 상태를 KR-TL로 함께 전달한다.

| 체계 | TL에 등재하는 서비스 | 신뢰점 레벨 |
| --- | --- | --- |
| JA 가상공동인증A | JA-01 CA, JA-02 OCSP, JA-03 TSA | CA 레벨 1 |
| JB 가상공동인증B | JB-01 CA, JB-02 OCSP, JB-03 TSA | CA 레벨 1 |
| SA 가상간편인증A | SA-00 RootCA 하나 | 레벨 0 |
| SB 가상간편인증B | SB-01 CA, SB-02 OCSP, SB-03 TSA | CA 레벨 1 |

전체 등재 예시는 사업자 4곳, 서비스 10개다. JA가 미등재된 초기 TL #1은 이 전체 목록에서 JA의 서비스들을 제외한 상태다. TL 서명 체계는 사업자 서비스 목록에 등재하지 않는다. TL 서명 인증서 체인은 TL의 서명 부분에 포함한다.

### 2.3 신뢰점 등재

[도식 원본 — krtl-anchor-levels](diagrams/krtl-anchor-levels.drawio)

그림 5 신뢰점 레벨과 검증의 끝

레벨 1에서는 등재된 사업자 CA가 가입자 인증서 경로의 신뢰점이다. JA를 정지해도 JB의 상태에는 영향을 주지 않는다. JA·JB의 상위인 공동인증용 KISA RootCA는 TL에 함께 등재하지 않는다.

레벨 0에서는 등재된 RootCA가 신뢰점이다. SA의 CA·OCSP·TSA 인증서는 SA RootCA까지의 인증서 체인으로 확인한다. Root의 서비스 상태는 그 아래 검증 경로 전체에 영향을 준다. 이 예시에서는 SA RootCA만 TL에 등재한다.

같은 체인에서 Root와 하위 CA를 동시에 CA 서비스의 신뢰점으로 두지 않는다. 하위 CA를 정지했는데 상위 Root가 인정 상태로 남아 있으면, 검증이 상위 Root로 우회해 정지의 의미가 달라질 수 있기 때문이다.

### 2.4 신뢰앵커와 인증서

신뢰앵커는 신뢰할 수 있는 설치 경로로 배포하고 인증서 지문을 대조한다. 자기서명이라는 사실만으로 그 인증서를 신뢰하는 것은 아니다. TL 배포 경로로 신뢰앵커를 자동 교체하지 않으며, KR-TL의 신뢰 기준은 HTTPS 서버 인증에 사용하는 일반 TLS 신뢰저장소와 구분한다.

| 인증서·키 | 용도 | 배치 원칙 |
| --- | --- | --- |
| KISA TL RootCA 인증서 | TL 서명 체인의 최종 검증 기준 | 이용환경에 사전 배포 |
| KISA TL CA·TL 서명 인증서 | TL 서명자 체인과 서명 검증 | TL의 서명 부분에 포함 |
| TL 서명 개인키 | TL 서명 생성 | 관리 영역의 HSM, PoC는 파일 키 |
| 사업자 Root·CA·OCSP·TSA 인증서 | 사업자 서비스의 디지털 ID와 경로 검증 | 등재 규칙에 따라 TL 또는 검증 증거에 포함 |
| 가입자 인증서 | 가입자 전자서명 확인 | 서명 문서의 검증 입력 |
| mTLS·HTTPS 인증서 | 제출·반출·배포 통신 보호 | 통신 경로에 배치, TL 인정 상태와 구분 |

TL 서명키를 바꾸더라도 새 서명 인증서가 같은 KISA TL RootCA 체인에 연결되면 이용환경의 신뢰앵커는 유지할 수 있다. 다만 서명자 인증서 폐지 확인과 전체 키 교체 운영 절차는 별도 운영 설계가 필요하다.

## 3 TL 데이터 구조

### 3.1 TL 구성

KR-TL은 발행 정보, 사업자 목록, 사업자별 서비스, TL 서명으로 구성한다. 서비스에는 유형과 이름, 디지털 ID, 현재 상태와 효력 시각, 과거 상태 이력이 들어간다. 본 설계는 ETSI TS 119 612 구조를 바탕으로 국내 서비스 명칭과 확장을 사용하는 XML 및 XAdES 단일 형식을 따른다.

TSL 규격 버전과 TL 일련번호는 별개다. 규격 버전은 문서 구조의 버전을 나타내고, 일련번호는 발행할 때 증가하는 TL의 순번이다. TSL 유형 KRlist도 XML이라는 파일 형식과 구분한다.

### 3.2 서비스 유형과 확장

CA는 인증서 발급, OCSP는 인증서 상태 확인, TSA는 시점확인 서비스다. 공동인증·간편인증이라는 신뢰 분야는 서비스 기능과 다른 분류이므로 서비스 유형과 별도로 기록한다. 신뢰점 레벨은 CA 서비스에 적용한다.

국내 인정 상태를 EU의 적격 여부와 동일하게 해석하지 않는다. 구조상의 대응과 국내 제도상의 의미를 구분해야 한다. 원격서명·본인확인·전자문서 보관 등 다른 분야는 확장 가능한 예약 유형이며, 이번 예시에서 등재·실행하는 서비스로 계산하지 않는다. CRL 유형과 국가 지정 상태도 정의와 실제 사용을 구분한다.

| 항목 | 설계 예시 값 |
| --- | --- |
| 서비스 유형 | urn:kr:krtl:svctype:CA / OCSP / TSA |
| 상태 | urn:kr:krtl:svcstatus:accredited / suspended / withdrawn |
| 신뢰 분야 | urn:kr:krtl:ext:domain:joint / simple |
| 신뢰점 레벨 | urn:kr:krtl:ext:anchor:0 / 1 |
| 사업자·서비스 ID | JA, JA-01 등 시험용 식별자 |

URI와 식별자는 원천 문서의 PoC 정의다. 운영 주소와 제도 연계 값으로 확정된 것으로 보지 않는다.

### 3.3 서비스 식별 정보

서비스 디지털 ID는 서비스를 식별하는 인증서와 공개키 정보다. 같은 공개키와 주체를 유지한 인증서 갱신은 같은 서비스에 인증서를 추가해 표현한다. 공개키가 바뀌면 새 서비스 ID로 등록하고 구 서비스의 상태 이력을 보존한다.

관리 시스템은 사업자 정보(D-01), 서비스 정보(D-02), 서비스 디지털 ID(D-04), 상태 이력(D-03), 제출 건(D-05), TL 버전을 구분해 관리한다. 제출 건에는 원문과 확인 결과를 남기지만 TL에는 확정된 서비스 정보만 싣는다. 개인키와 내부 심사 의견은 TL의 배포 대상이 아니다.

| 원천 정보 | TL의 대응 위치 |
| --- | --- |
| 발행 설정 | SchemeInformation |
| 사업자 이름·주소·정보 URI | TSPInformation |
| 서비스 유형·이름 | ServiceInformation |
| 서비스 인증서·공개키 식별 정보 | ServiceDigitalIdentity |
| 현재 상태·효력 시각 | ServiceStatus, StatusStartingTime |
| 과거 상태 | ServiceHistory |
| 신뢰 분야·레벨·정지 사유 | KR-TL 서비스 확장 |
| 서명 인증서 체인 | ds:Signature의 KeyInfo |

### 3.4 데이터 저장

원천 등재 정보와 발행한 TL은 관리 시스템이 보관한다. 배포 시스템은 서명된 TL의 사본과 게시·접속 기록을 보관한다. 이용환경은 신뢰앵커, 검증한 TL 보유본, TL에서 만든 신뢰 색인, 검증 결과를 갖는다.

신뢰 색인은 공개키 식별 정보로 사업자·서비스·상태 이력을 빨리 찾도록 구성한 파생 데이터다. TL이 교체되면 색인도 함께 다시 만든다. 색인만 따로 변경해 TL과 다른 신뢰정보를 유지하지 않는다.

## 4 상태 및 이력 관리

### 4.1 상태 정의

서비스 상태는 KISA가 확인한 인정 상태다. 인증서 폐지는 특정 인증서가 유효하게 사용될 수 있는지에 관한 별도의 정보다. 서비스가 인정 상태여도 가입자 인증서가 폐지됐다면 서명 검증은 실패할 수 있다. 반대로 가입자 인증서가 폐지되지 않았더라도 서명 시각에 서비스가 정지 상태라면 TL 판정은 실패한다.

| 서비스 상태 | 의미 | 해당 구간의 TL 판정 |
| --- | --- | --- |
| 인정 accredited | 그 시각에 인정 상태인 서비스 | 다른 검증 조건도 정상이면 통과 |
| 정지 suspended | 인정 효력이 정지된 구간 | 실패 |
| 철회 withdrawn | 인정이 철회된 이후 구간 | 실패 |
| 최초 인정 이전 | 상태 이력에 인정 근거가 없는 시각 | 판단 보류 |

### 4.2 상태 이력

[도식 원본 — krtl-state-history](diagrams/krtl-state-history.drawio)

그림 7 상태 변경과 서명 시각의 관계

상태 구간은 시작 시각을 포함하고 다음 상태의 시작 시각은 포함하지 않는다. 정지 효력 시각과 서명 시각이 같으면 정지 상태를 적용한다. 복원은 복원 이후 구간에 적용되며, 앞선 정지 구간을 지우지 않는다.

예를 들어 TL #4의 현재 상태가 인정으로 복원돼 있어도, 정지 구간에 작성한 S2는 정지 상태로 판정한다. TL #5에서 서비스가 철회된 뒤에도 과거 인정 구간의 S1·S3는 상태 이력으로 구분한다. 이 설명은 서명값·인증서 경로·폐지 상태 등 나머지 검증 조건이 정상이라는 예시 전제를 갖는다.

### 4.3 상태 효력 시각

새 상태의 효력 시각은 그 상태를 처음 담은 TL의 발행 시각보다 앞설 수 없도록 설계한다. 입력 단계에서 확인했더라도 실제 발행 직전에 다시 검사한다. 발행이 지연돼 효력 시각이 이미 과거가 됐다면 입력을 수정하고 다시 발행해야 한다.

본문의 사례에서는 새 상태의 효력 시각과 TL 발행 시각을 같게 두었다. 효력 시각, 발행 시각, 수신 시각, 실제 검증 시각은 서로 다른 값이며 화면과 기록에서도 구분한다. 관리 화면은 KST, TL XML은 같은 순간을 UTC로 표현한다.

### 4.4 이력 보존 및 인증서 갱신

상태를 바꿀 때 직전 상태를 이력으로 옮기고 새 상태와 시작 시각을 기록한다. 이력은 최신순으로 보관하며 과거 상태를 삭제해 현재 상태만 남기지 않는다.

| 변경 | 서비스 처리 | 과거 검증에 필요한 정보 |
| --- | --- | --- |
| 정지·복원·철회 | 같은 서비스에 상태 이력 추가 | 이전 상태와 각 효력 시각 |
| 같은 키·주체의 인증서 갱신 | 같은 서비스의 디지털 ID에 인증서 추가 | 기존 공개키와 인증서 |
| 공개키 교체 | 새 서비스로 등록 | 구 서비스·인증서·상태 이력 보존 |
| 서비스 운영 종료 | 상태 변경으로 표현 | 과거 인정 구간과 종료 이후 구간 |

PoC의 서명 시각은 서명에 기록된 값이다. TSA가 증명한 시각과 같은 보증 수준으로 해석하지 않는다. 장기 검증과 과거 폐지 증거의 평가 정책은 별도 설계 대상이다.

신뢰정보는 사업자가 제출한 내용에서 시작해 KISA가 확정한 등재 정보가 되고, TL 서명을 거쳐 외부에서 검증 가능한 정보가 된다. 이용환경은 배포 경로에서 받은 파일을 바로 사용하지 않고 TL 서명을 검증한 후 보유본으로 채택한다.

인증사업자의 제출은 신뢰정보 제출 경로(IF-01)로 접수한다. 사업자 연계 서버는 상호 TLS 인증(mTLS)으로 제출자를 식별하고 필수 항목과 형식을 확인한다. 통과한 제출만 내부 제출 전달 경로(IF-03)로 넘겨 확정 대기에 등록한다. 같은 제출 식별자(submissionId)로 다시 전달된 내용은 새 제출 건을 중복 생성하지 않고 기존 건에 연결한다.

| 제출 항목 | 내용 |
| --- | --- |
| providerId와 type | 사업자와 등록·변경·상태 신고 유형 |
| provider와 service | 사업자 정보, 서비스 유형·이름 |
| digitalIds | 등재 대상 서비스 인증서 |
| statusChange | 상태, 효력 시각, 사유 |
| submittedAt | 제출 시각 |

제출 JSON에 개인키를 넣지 않는다. PoC에서 별도의 제출서 전자서명은 두지 않으며 mTLS 인증과 형식 확인을 사용한다. 정상 접수도 자동 등재를 뜻하지 않는다. 관리자는 내용을 확정하거나 반려하고, 사업자는 접수 번호로 처리 결과를 조회한다.

| --- | --- | --- |

### 5.3 발행 관리

일련번호는 서명 성공 시 확정한다. 편성이나 서명에 실패하면 번호를 사용한 것으로 처리하지 않으므로 다음 시도에서 같은 예정 번호를 쓴다. 이미 서명한 발행본은 반출 실패 때문에 내용을 다시 만들거나 같은 번호로 바꾸지 않는다.

확정된 변경이 없어도 NextUpdate 갱신을 위해 재발행할 수 있다. 화면에는 변경 내용이 없다는 점을 표시한다. PoC는 한 번에 하나의 발행을 처리하고 자동 복구 대신 수동 재시도를 사용한다.

운영 주기와 목표 시간은 별도로 정한다. 원천 설계의 NextUpdate 7일, 긴급 반영 1시간, 이용환경 확인 10분, 사업자 제출 30일은 시험용 가정이며 운영 보장 수치가 아니다.

## 6 TL 배포 및 동기화

### 6.1 TL 반출 및 게시

TL 발행 서버는 서명된 TL 반출 경로(IF-06)로 서명된 TL XML 하나를 배포 WAS에 보낸다. 별도 매니페스트는 두지 않는다. 배포 WAS는 mTLS 연결을 확인하고 TL 서명과 일련번호를 검사한 뒤 버전별 보관과 최신 버전 교체를 처리한다.

| 수신 조건 | 게시 처리 |
| --- | --- |
| 정상 서명, 현재보다 큰 번호 | 새 버전 게시 |
| 같은 번호와 같은 내용 | ALREADY_PUBLISHED로 정상 재전송 처리 |
| 같은 번호와 다른 내용 | CONFLICT로 거부 |
| 현재보다 작은 번호 | VERSION_NOT_INCREASING으로 거부 |
| TL 서명 검증 실패 | SIGNATURE_INVALID로 거부 |

반출 연결이 끊기면 관리 시스템에는 발행 성공과 게시 실패를 함께 표시한다. 관리자는 동일한 서명본을 다시 반출한다. 새 번호로 발행해야 하는 상황과 같은 발행본을 재전송하는 상황을 구분해야 한다.

### 6.2 TL 수신 및 갱신

이용환경은 TL 조회·수신 경로(IF-07)를 사용해 공개 배포 경로에서 TL을 가져온다. 최신 정보 조회는 변경 여부 확인을 돕지만, TL 채택의 신뢰 근거는 서명된 TL 자체다. 배포 WAS가 제공하는 메타데이터만 보고 인정 상태를 바꾸지 않는다.

| 요청 | 의미 |
| --- | --- |
| GET /tl/v1/latest | 최신 TL XML |
| GET /tl/v1/{seq} | 지정 버전의 TL XML |
| GET /tl/v1/latest/meta | 일련번호·발행 시각·NextUpdate·해시 정보 |
| If-None-Match | 보유 ETag와 비교, 변경이 없으면 304 |

새 TL을 받으면 서명을 사전 신뢰앵커까지 검증하고, 일련번호가 보유본보다 큰지와 NextUpdate가 지나지 않았는지 확인한다. 통과한 경우에만 보유본을 교체하고 신뢰 색인을 다시 만든다. 화면의 ‘지금 확인’도 같은 가져오기 절차를 즉시 실행하는 동작이다.

| 수신 | 이용환경이 받아 검증하고 보유함 | 이용환경의 보유 TL |
| 적용 | 실제 서명 판정에 해당 TL을 사용함 | 검증 결과의 사용 TL 번호 |

배포 접속 기록은 요청 시각, 클라이언트 유형·버전, 요청 대상, 응답 결과, 전달한 TL 번호를 남긴다. 다운로드 성공 기록만으로 실제 검증에 적용됐다고 단정하지 않는다. 이용기관 등록과 식별 방식이 확정되지 않은 상태에서는 전체 미수신 기관을 빠짐없이 계산할 수도 없다.

### 6.4 예외 처리

새 TL 검증에 실패하면 새 파일을 채택하지 않고 기존 보유본을 유지한다. 다만 기존 보유본도 NextUpdate가 지나면 검증 기준에서 제외한다. 유효한 TL이 하나도 없으면 ‘사용 가능한 TL 없음(NO_VALID_TL)’을 사유로 판단을 보류한다. 과거 발행본과 시험 증거의 보존은 검증용 보유본의 사용 중단과 별개다.

배포 시스템이 잠시 중단돼도 이용환경은 기한 안의 보유본으로 판정할 수 있다. 관리 시스템이 중단돼도 배포 시스템은 마지막 게시본을 제공할 수 있다. 두 경우 모두 TL의 유효기한을 무한히 연장하는 예외는 두지 않는다.

## 7 신뢰 검증

### 7.1 TL 활용 구조

[도식 원본 — krtl-rp-tl-usage](diagrams/krtl-rp-tl-usage.drawio)

그림 11 이용환경의 TL 동기화와 신뢰 검증

이용환경은 TL 동기화와 개별 서명 검증을 나누어 수행한다. 동기화 모듈은 신뢰앵커로 TL 서명을 확인해 보유본과 신뢰 색인을 유지한다. 서명 검증은 그 시점에 채택된 TL을 사용하고, 사용한 일련번호를 결과에 남긴다.

그림 11은 개념상의 전체 활용 구조다. PoC의 브라우저 역할은 크롬 확장으로 대체하고, 표본 정보의 인증서 체인과 서명 시각으로 TL 요인을 판정한다. 확장이 PDF 서명값·문서 무결성·OCSP 검증까지 수행하는 것으로 표시하지 않는다. TSA 검증도 이번 PoC에서는 실행하지 않는다.

### 7.2 인증서 경로 검증

검증 입력에는 서명 문서, 서명자 인증서와 경로 구성에 필요한 인증서, 서명 시각, 검증 정책, TL 보유본과 폐지 정보가 포함된다. 전체 서명 검증에서는 서명값과 문서 무결성을 확인하고 인증서 체인을 구성한다.

TL 판정은 유효한 TL이 있는지 확인한 뒤 체인과 일치하는 등재 서비스를 찾는다. 레벨 1은 등재 CA에서, 레벨 0은 등재 Root에서 신뢰 경로를 끝낸다. 동일 체인의 더 높은 미등재 Root로 올라가 정지된 등재 신뢰점을 우회하지 않는다.

### 7.3 서비스 상태 확인

신뢰점을 찾으면 서명 시각을 확인한다. 서명 시각이 없으면 ‘서명 시각 없음(NO_SIGNING_TIME)’, 최초 인정보다 앞서면 ‘최초 인정 이전(NOT_ACCREDITED_AT_TIME)’을 사유로 판단을 보류한다. 시각이 상태 구간에 속하면 해당 구간의 인정·정지·철회 상태를 적용한다.

TL에 서비스가 전혀 없을 때에는 상태나 서명 시각을 조회할 대상도 없으므로 ‘미등재(NOT_IN_TL)’로 판단을 보류한다. 따라서 시각 없는 표본이라도 미등재 TL #1에서는 ‘미등재(NOT_IN_TL)’, 등재 이후 TL에서는 ‘서명 시각 없음(NO_SIGNING_TIME)’이 보류 사유가 된다.

### 7.4 폐지 확인 및 판정

가입자 인증서의 폐지 여부는 OCSP 등 기존 인증서비스로 확인한다. 레벨 1에서 OCSP 서비스는 별도 등재 정보와 공개키를 확인하고, 레벨 0에서는 등재 Root까지의 체인으로 확인한다. OCSP 서명자의 신뢰 확인과 응답에 담긴 가입자 인증서 폐지 상태는 별도의 확인 항목이다.

| 결과 | 뜻 | 대표 사유 |
| --- | --- | --- |
| 통과 | 필요한 검증 조건을 충족함 | OK |
| 실패 | 서명 또는 신뢰 조건 위반을 확인함 | 서비스 정지·철회, 인증서 폐지, 서명값 불일치 |
| 판단 보류 | 필요한 근거를 확보하지 못함 | 미등재, 유효 TL 없음, 서명 시각 없음 |

화면의 결과는 통과(TOTAL_PASSED), 실패(TOTAL_FAILED), 판단 보류(INDETERMINATE)로 표시한다. TL 사례의 통과는 다른 서명 검증 조건이 정상인 경우의 결과다. 브라우저 확장의 TL 요인 판정과 이용기관의 전체 PDF 검증 결과를 비교할 때에도 이 범위를 구분한다.

### 7.5 검증 결과

검증 결과에는 판정, 사유, 서명자, 사용한 신뢰점, 서명 시각, 그 시각의 서비스 상태, 사용 TL 번호·발행 시각, 검증 시각을 기록한다. 전체 검증 결과에는 폐지 확인 결과도 포함한다.

같은 결과를 기대하려면 서명 또는 대응 표본 정보, TL 버전, 정책, 기준 시각과 검증 증거가 같아야 한다. TL 버전만 같다는 이유로 서로 다른 입력과 정책의 전체 판정까지 같다고 단정하지 않는다.

## 8 관리 화면

### 8.1 화면 구성

관리 화면은 신뢰정보를 바꾸고 그 결과를 확인하는 순서로 배치한다. 사업자·서비스 상세에서 변경할 대상을 선택하고 상태·효력 시각·사유를 입력한다. 확정 화면에서는 제출 원문과 반영할 내용을 대조한다. 발행 화면에서는 직전 TL과의 차이를 본 뒤 발행한다.

| 화면 | 보여 줄 내용 | 다음 동작 |
| --- | --- | --- |
| M-01 현황 | 최신 발행·게시 번호와 주요 처리 상태 | 상세 화면 이동 |
| M-02 사업자·서비스 | 사업자, 서비스 유형, 인증서, 신뢰점 레벨 | 등록·변경 입력 |
| M-03 상태 변경 | 현재 상태, 효력 시각, 사유, 이력 | 입력 확인·확정 |
| M-04 제출 확인 | 제출 원문, 형식 확인 결과, 반영 내용 | 확정 또는 반려 |
| M-05 TL 발행 | 스냅숏, 직전 대비 차이, 예정 번호 | 편성·서명·발행 |
| M-06 게시 확인 | 발행 번호, 게시 번호, 오류 사유 | 동일 발행본 재반출 |
| M-07 수신 현황 | 접속 기록과 확인 가능한 보유 버전 | 이용환경 상태 확인 |
| M-08 결과 비교 | 변경 조건, 신뢰 경로, 사용 TL, 판정 | 표본·이용환경별 비교 |

PoC는 시연자 한 명이 로그인과 승인자 분리 없이 이 흐름을 조작한다. 입력 확정은 데이터가 발행 대상인지 구분하는 단계로 유지한다. 관리자 인증을 생략해도 TL 서명 검증과 사업자 연계 인증을 생략하지 않는다. 관리자 계정·권한·감사 무결성은 운영 설계에서 별도로 다룬다.

### 8.2 결과 비교

비교 화면은 상단의 변경 조건, 가운데 신뢰 경로, 하단의 이용환경 결과로 구성한다. 변경 조건에는 사업자·서비스·신뢰점 레벨, 새 상태와 효력 시각, 발행 TL을 표시한다. 경로에는 인증서 발급 관계와 TL 신뢰 관계를 별도로 그린다.

| 영역 | S2 정지 사례의 표시 예시 |
| --- | --- |
| 변경 조건 | JA-01, 레벨 1, 인정 → 정지, 효력 t2, TL #3 |
| 이용기관 경로 | 가입자 U → JA-01, TL #3의 정지 구간에 해당 |
| 브라우저 경로 | 가입자 U → JA-01, 갱신 전 TL #2는 인정으로 판단 |
| 이용기관 결과 | 사용 TL #3, 실패, SERVICE_SUSPENDED_AT_TIME |
| 브라우저 결과 | 사용 TL #2, TL 요인 통과; 갱신 후 #3으로 실패 |

상태 때문에 거부된 경로와 등재 신뢰점 자체를 찾지 못한 경로를 다르게 표시한다. 색상만으로 구분하지 않고 ‘정지 구간’, ‘미등재’, ‘유효 TL 없음’ 같은 사유를 함께 적는다. 시험 실행 ID로 변경 내용과 이용환경 결과를 묶는다.

### 8.3 오류 표시

서명 실패는 ‘번호 미사용’, 반출 실패는 ‘발행됨·게시 안 됨’으로 표시한다. 이용환경에서 새 TL을 거부했을 때에는 거부 사유와 유지한 보유 번호를 함께 보여 준다. 유효한 보유본이 없으면 기존 번호가 남아 있더라도 사용 가능한 상태로 표시하지 않는다.

이용환경 결과를 결과 비교 화면(M-08)으로 모으는 전달 방식과 시험 시계를 주입하는 방식은 PoC 구현에서 정할 사항이다. 이 설계는 결과의 내용과 비교 기준을 정의하며, 미정인 전달 API를 이미 구현된 기능처럼 가정하지 않는다.

## 9 검증 시나리오

### 9.1 시험 조건

주 사례의 인증서 체인은 공동인증용 KISA RootCA → JA-01 CA → 가입자 U로 고정한다. 대조군은 JB의 가입자 W, 레벨 0 비교는 SA의 가입자 V다. 시험 문서와 검증 정책을 유지하고 TL 등재 상태와 이용환경의 보유 버전을 바꾼다.

t0부터 t4는 하루 간격으로 설정한 시험 시점이며 각 시점은 해당 TL의 발행 시각이다. JA의 최초 인정은 t1, 정지는 t2, 복원은 t3, 철회는 t4에 시작한다. 실증용 가상 시간이며 실제 인정 이력을 뜻하지 않는다.

| TL | JA 상태 | 이력 | 비교 목적 |

| #1, t0 | 미등재 | JA 없음 | 인증서 체인이 있어도 TL 신뢰점 없음 |
| #2, t1 | 인정 | 인정 시작 | 등재 전후 비교 |
| #3, t2 | 정지 | 인정 → 정지 | 정지 전후·동기화 비교 |
| #4, t3 | 인정 복원 | 인정 → 정지 → 인정 | 과거 정지 구간 보존 |
| #5, t4 | 철회 | 앞선 이력 → 철회 | 철회 전후 구간 비교 |

[도식 원본 — krtl-trustpath](diagrams/krtl-trustpath.drawio)

그림 12 TL 변경 전후의 신뢰 경로와 S2 판정

그림 12 상세 미등재 등재 정지의 판정 변화

[도식 원본 — krtl-trustpath](diagrams/krtl-trustpath.drawio)

그림 12 상세 복원 철회 후에도 유지되는 정지 이력

S2는 정지 구간에 기록된 서명이다. TL #1에는 JA가 없어 판단을 보류한다. TL #2에는 JA가 인정 상태로만 기록돼 있어 통과한다. 정지 정보가 반영된 TL #3부터는 실패하며, 복원·철회가 이어져도 S2가 속한 정지 구간은 남는다.

그림 12의 위쪽은 TL의 등재·상태 관계, 아래쪽은 고정된 인증서 발급 관계다. 위쪽의 TL 서명 검증 경로는 그림 3의 KISA TL RootCA → KISA TL CA → TL 서명 인증서 관계를 참조한다.

| 표본과 서명 시각 | TL #1 | TL #2 | TL #3 | TL #4 | TL #5 |
| --- | --- | --- | --- | --- | --- |
| S0 최초 인정 전 | 보류 A | 보류 B | 보류 B | 보류 B | 보류 B |
| S1 첫 인정 구간 | 보류 A | 통과 | 통과 | 통과 | 통과 |
| SB 정지 효력과 같음 | 보류 A | 통과 | 실패 C | 실패 C | 실패 C |
| S2 정지 구간 | 보류 A | 통과 | 실패 C | 실패 C | 실패 C |
| S3 복원 구간 | 보류 A | 통과 | 실패 C | 통과 | 통과 |
| S4 철회 이후 | 보류 A | 통과 | 실패 C | 통과 | 실패 D |

표의 A는 미등재(NOT_IN_TL), B는 최초 인정 이전(NOT_ACCREDITED_AT_TIME), C는 서명 시각의 서비스 정지(SERVICE_SUSPENDED_AT_TIME), D는 서명 시각의 서비스 철회(SERVICE_WITHDRAWN_AT_TIME)를 뜻한다. 표는 TL 요인만 비교하며 서명값·인증서 체인·폐지 상태는 정상, 모든 사용 TL은 NextUpdate 이내라고 가정한다.

오래된 TL #2가 S2·S4를 통과로 판단하는 이유는 이후 정지·철회 정보를 아직 모르기 때문이다. TL #3은 복원을 모르므로 S3·S4를 정지로 판단한다. 최신 상태 이력을 받아야 각 시간 구간을 올바르게 구분할 수 있다.

### 9.3 상태별 판정

신규 등재 사례는 최초 인정 이후에 작성한 S1을 동일하게 사용한다. 미등재 TL에서는 보류, 등재 TL에서는 통과한다. 최초 인정 이전 S0를 새로 등재했다는 이유만으로 통과시키지 않는다.

정지 사례는 S1·SB·S2를 함께 비교한다. S1은 인정 구간, SB와 S2는 정지 구간이다. 복원 사례는 S2 실패가 유지되면서 S3가 통과하는지 확인한다. 철회 사례는 S4가 실패하고 과거 인정 구간 S1·S3가 구분되는지 확인한다.

### 9.4 동기화 및 대조 시험

| 상황 | 이용기관 | 브라우저의 TL 요인 판정 |
| --- | --- | --- |
| 한쪽만 TL #3 수신 | #3으로 S2 실패 | #2로 S2 통과 |
| 양쪽 모두 TL #3 수신 | #3으로 S2 실패 | #3으로 S2 실패 |
| JA 정지 중 JB 표본 W 검증 | JB 인정 상태로 통과 | 같은 조건이면 동일 |
| SA 표본 V 검증 | 신뢰점 SA-00 Root로 통과 | 레벨 0 경로 표시 |

이 비교는 변경의 원인을 드러낸다. JA 정지는 공동 상위 Root를 공유하는 JB까지 정지시키지 않는다. SA는 CA가 직접 TL에 없어도 등재 Root까지의 경로로 판정한다. 같은 체인이라도 이용환경이 서로 다른 TL을 보유하면 결과가 달라질 수 있다.

### 9.5 예외 상황

| 조건 | 채택 동작 | 판정에 미치는 영향 |
| --- | --- | --- |
| 내용을 바꾼 위조 TL #6 | 서명 실패로 거부, 유효한 #5 유지 | S4의 철회 실패 유지 |
| 이전 TL #2 재제공 | 구버전 거부, 유효한 #5 유지 | 과거 인정 상태로 되돌아가지 않음 |
| #5 기한 경과, 새 TL 없음 | #5를 검증 기준에서 제외 | NO_VALID_TL로 보류 |
| JA 등재, 서명 시각 없음 | 시간 구간 선택 불가 | NO_SIGNING_TIME으로 보류 |

시험 결과에는 실행 ID, 변경 내용·효력 시각, 발행·게시 번호, 이용환경별 사용 번호, 표본, 신뢰점, 판정과 사유를 함께 남긴다. 본 장의 표는 설계상 기대 결과이며 실제 구현의 시험 통과 기록은 아니다.

## 부록 B 판정 사유와 용어

### B.1 판정 사유

| 사유 | 판정 | 의미 |
| --- | --- | --- |
| OK | 통과 | 필요한 조건 정상 |
| SIGNATURE_INVALID | 실패 | 서명값·문서 무결성 불일치 |
| CERT_REVOKED | 실패 | 가입자 인증서 폐지 |
| SERVICE_SUSPENDED_AT_TIME | 실패 | 서명 시각이 서비스 정지 구간 |
| SERVICE_WITHDRAWN_AT_TIME | 실패 | 서명 시각이 서비스 철회 구간 |
| NOT_IN_TL | 보류 | TL의 등재 신뢰점과 연결되지 않음 |
| NO_VALID_TL | 보류 | 사용 가능한 TL 없음 |
| REVOCATION_UNAVAILABLE | 보류 | 필요한 폐지 상태를 확인하지 못함 |
| NOT_ACCREDITED_AT_TIME | 보류 | 최초 인정 이전의 서명 |
| NO_SIGNING_TIME | 보류 | 판정에 필요한 서명 시각 없음 |

서명 오류(SIGNATURE_INVALID)는 발생한 대상에 따라 구분한다. TL 파일 수신 과정에서는 TL 서명 오류를, 개별 서명의 검증 결과에서는 해당 서명값의 오류를 뜻한다. 오류가 발생한 대상과 단계를 함께 기록한다. 브라우저 확장의 TL 요인 판정에서는 PDF 서명값·폐지 상태 검증에 해당하는 사유를 자체 생성하지 않는다.

## 부록 C 참고 자료 및 도식

시스템 구성과 연계는 「시스템 구성도」(01)와 「IF 명세서」(06), 인증체계와 등재 예시는 「인증체계 설계」(07)·「신뢰 흐름 설계」(08)·「메타데이터 실제데이터」(14)를 바탕으로 정리했다.
