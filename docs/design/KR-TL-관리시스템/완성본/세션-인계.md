## 다음 세션에서 할 일

**다음 단계는 사용자가 구글독스 설계 문서를 직접 보면서 수정사항을 찾는 것이다.** 이번 세션은 로컬 검토표와 구글독스 반영 이력을 커밋하고 종료한다. 후속 작업에서는 사용자가 발견한 사항과 그때의 최신 구글독스를 기준으로 검토·수정한다. 현재 로컬 보관본으로 문서를 되돌리거나 기존 검토표의 항목을 무조건 다시 적용하지 않는다.

### 2026-10-06 구글독스 반영 완료

사용자의 ‘구글 독스를 수정한다’ 지시에 따라 원격 문서의 최신 내용을 읽고 IF 정정을 직접 반영했다. 본문 30개 문단의 내용을 수정하고, 주체·인증서·화면·IF·용어·도식 참조 표의 해당 셀을 수정했다. IF 목록은 IF-01~08로 정리하고 이전 IF-09 행을 삭제했다. TL 관리(IF-02)의 연결, TL 배포(IF-06)의 WAS → WEB 구간, 서명 검증(IF-08)의 두 경로와 시험 시나리오를 반영했다.

커넥터 재조회로 변경 내용을 확인했다. 기존 이미지 20개, 표 26개, 제목과 문서 서식을 보존했으며 기존 상태·시간 판정표는 변경하지 않았다. 그림 2·8·9·10의 이전 IF 표기는 그림을 수정하지 않고 본문에서 정정해 설명했다. 망 배치·게시 완료 확인 방식과 서비스 서명 시험 자료는 상세 설계에서 구체화할 사항으로 남겼다. PDF 변환과 페이지 배치 검사는 수행하지 않았다. 자동 목차 쪽수와 페이지 배치는 사용자가 문서에서 확인한다.

**로컬 통합 설계서 Markdown은 수정 전 보관본이다.** 다음 편집은 구글독스의 최신 본문을 읽어 시작하며 이 보관본을 원격 문서에 덮어쓰지 않는다. 아래 로컬 검토 결과는 반영 전 검토 이력으로 보존한다.

### 2026-10-06 로컬 검토 결과

사용자의 후속 지시에 따라 구글독스 대신 로컬 통합 설계서를 기준으로 검토했다. [IF 정정 수정 대상](IF-정정-수정대상.md)에 장·절별 위치, 변경 이유, 문장 보완안과 도식의 이전 IF 표기를 정리했다. 통합 설계서 본문과 그림, 구글독스는 변경하지 않았다. 아래의 ‘검토 예정’ 설명은 이전 세션 기록이며, 수정 대상 식별은 완료한 상태다.

다음 편집은 이 검토표를 사용한다. 구글독스는 향후 실제 수정할 때 최신 내용을 읽어 사람의 수정을 보존한다. 현재 로컬 검토를 위해 원격 문서를 먼저 읽을 필요는 없다. TL 관리(IF-02)의 연결, TL 배포(IF-06)의 WAS → WEB 구간, 서명 검증(IF-08)의 두 경로와 이전 IF-09 제외가 주요 반영 대상이다.

### 이전 세션 기록

**가장 먼저 [IF 정정 명세](IF-정정-명세.md)와 [수정된 draw.io 원본](diagrams/krtl-system.drawio)의 ‘KR-TL 시스템 구성도 수정’ 페이지를 읽는다.** 다음 작업은 이 IF-01~08을 기준으로 기존 문서를 재검토하고 수정할 내용과 위치를 찾는 것이다. IF-08은 검증 결과 전달이 아니라 서명 검증이다. 이용자 서비스가 서명한 내용을 사용자가 브라우저에서 검증하고, 사용자가 서명한 내용은 이용자 서비스가 검증한다. 기존 IF-09와 IF-06의 연결 구간도 함께 검토한다. 최신 사용자 정정은 아래 과거 기술 자료보다 우선한다.

이번 세션에서는 정정 명세와 원본을 저장했다. 통합 설계서와 기존 원천 문서의 IF 설명은 아직 전면 반영하지 않았으므로, 보관된 본문을 새 IF와 일치하는 문서로 간주하지 않는다. 앞선 세션에서 적용한 간략한 목차 변경도 이번 커밋에 포함한다.

사용자가 수동으로 수정한 파일을 먼저 읽고 보정 작업을 시작한다. 별도 파일이 지정되면 그 파일을 사용하고, 지정되지 않으면 위 구글독스의 최신 내용을 다시 읽는다. 현재 보관본을 원격 문서에 덮어쓰지 않는다.

1. 사람이 수정한 최신 본문과 표, 그림 설명을 읽고 이 보관본과 비교한다. 표현·구성·내용의 변경을 구분한다.
2. 사람이 바꾼 문장과 순서에서 읽기 쉬워진 이유를 확인한다. 실제 수정 사례를 근거로 문체와 구성 원칙을 기록하고 같은 성격의 문장에 적용한다. 모델 자체를 학습시켰다고 표현하지 않는다.
3. `humanize-korean` 스킬을 적용해 추가 윤문한다. 기술적 의미, 조건, 상태·시간 구간, 수치, 표의 판정 결과를 보존한다. 사람이 선택한 표현을 기계적인 병렬 문장으로 되돌리지 않는다.
4. 본문과 표, 도식 사이의 용어·식별자·신뢰 경로를 다시 확인한다. 사실 변경이 필요한 부분은 문체 보정과 구분해 검토한다.
5. 수정 결과는 구글독스에서 읽어 확인한다. 사람의 배치 조정을 보존하고, 형식 수정 범위를 불필요하게 넓히지 않는다.

## 반드시 유지할 사용자 지침

- 설계서는 KR-TL 개념을 명확히 설명하는 설계도다. PoC 구현 작업은 별도다.
- 연관 담당자가 읽고 이해할 수 있게 쓴다. 형식적인 목적·독자·범위 설명과 별도 ‘설계 결정 사항’ 장은 넣지 않는다.
- 본문은 이름을 먼저 쓰고 코드를 괄호에 넣는다. 예: 사업자 정보(D-01), 서비스 디지털 ID(D-04), 신뢰정보 제출 경로(IF-01), 결과 비교 화면(M-08). 코드 대응표는 유지한다. 사용자 예시의 코드와 명칭이 실제 사전과 다르면 실제 대응을 따른다.
- 목차와 본문 제목은 일반적인 용어로 간략하게 쓴다. 사용자의 수정 예: ‘참여 주체와 전체 연결’ → ‘시스템 구성도’. 이 원칙을 전체 제목에 적용했다. 설명형·문장형 제목으로 되돌리지 않는다.
- 오류 코드도 필요하면 한국어 의미를 먼저 쓴다. 예: 서명 시각 없음(NO_SIGNING_TIME).
- 시스템 구성, 요소 간 흐름, 신뢰체인의 연결을 구체적으로 보여 준다. 기존 상세 draw.io 도식을 활용한다.
- **PDF 변환을 하지 않는다. 배치 확인 목적의 PDF 변환도 하지 않는다.** 사용자 지시가 스킬의 PDF 검토 권고보다 우선한다.
- 그림은 draw.io에서 이미지 파일로 직접 내보내 문서에 삽입한다. 삽입이 불가능하면 문서에 파일 링크를 두고 사용자가 수동으로 작업할 수 있게 한다.
- 배치 조정은 사용자가 수동으로 한다. 별도 요청 없이 이미지를 재조정하거나 문서를 재가져오기하지 않는다.

## 기술 검토 때 놓치지 않을 사항

- TL 서명 체인(KISA TL RootCA → KISA TL CA → TL 서명 인증서)과 가입자 인증서 발급 체인을 구분한다. TL이 등재 서비스와 인정 상태를 연결하며, 두 인증체계가 상호 인증으로 연결되는 것은 아니다.
- Root 등재 레벨 0과 CA 등재 레벨 1, 서비스 상태와 인증서 폐지 상태를 구분한다.
- 상태 구간은 시작 시각을 포함한다. 복원 후에도 과거 정지 구간을 보존한다.
- 발행·게시·수신·실제 적용 버전은 별개다. 접속 기록만으로 실제 적용을 단정하지 않는다.
- 사례 표는 설계상 기대 결과다. 실제 구현 시험이 통과했다고 쓰지 않는다.
- 브라우저 PoC는 표본 정보로 TL 요인을 판정한다. 전체 PDF 서명·무결성·OCSP 검증과 동일시하지 않는다. TSA 검증은 이번 PoC에서 실행하지 않는다.

기술적 충돌은 원천 자료의 「설계 베이스라인」(24)에 따라 「신뢰경로 판정표」(18), 「변경 발행 수신 흐름」(19)·「시험데이터 비교화면」(20)을 우선 확인한다. 다만 사용자의 최신 명시적 수정 지시가 있으면 그 지시를 반영하고 변경 이유를 남긴다.
