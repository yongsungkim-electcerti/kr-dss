# 신뢰체인 흐름의 변경을 증명하는 PoC 설계 검토

> 기준일: 2026-10-05
> 검토 대상: KR-TL 관리 시스템 설계 문서 00~15의 관련 본문
> 확정된 방향: 관리자 인증 생략. 승인 분리·감사 기능은 핵심 범위에서 제외. 신뢰체인의 흐름이 변경되는 것을 증명하는 데 집중한다.
> 평가 대상: 설계의 적절성과 완성도. 구현 완료나 시험 통과를 평가한 문서가 아니다.

## 1 검토 결론과 핵심 명제

**TL의 등재 정보와 상태가 바뀌면 이용환경이 어떤 신뢰체인을 수용하거나 거부하는지, 그 판단이 시점에 따라 어떻게 달라지는지를 증명한다.** 이것이 이번 PoC의 중심이다.

시연은 신뢰정보 변경 → TL 발행·서명 → 배포·수신 → 신뢰 경로와 판정 비교로 구성한다. 관리 화면은 시험 조건을 입력하고 TL을 발행하는 도구다. 로그인, 역할 전환, 승인자 분리, 감사 무결성 검사는 이 흐름의 선행 조건이나 설계 완료 조건으로 두지 않는다.

현재 설계는 구성요소, 인증체계, TL 구조와 상태 이력이 상당히 구체화돼 있다. D0~D11의 분야 구분은 대체로 적절하다. 완성도를 높일 핵심은 **D4+의 신뢰 흐름, D3의 데이터, D7의 판정, D9의 시험을 변경 전후 비교로 연결하는 것**이다. 관리 기능의 개수나 운영 보안 설계의 분량으로 완성도를 판단하지 않는다.

### 1.1 신뢰체인에서 바뀌는 부분

신뢰 흐름은 다음 두 부분을 연결해 설명한다.

| 구분 | 검증 관계 | PoC에서 확인할 것 |
|---|---|---|
| TL의 출처 확인 | 사전 배포한 KISA TL RootCA를 기준으로 TL 서명 인증서 체인과 TL 서명을 검증 | 이 TL이 신뢰할 수 있는 발행자의 서명된 정보인지 |
| 가입자 서명의 신뢰 판단 | 검증된 TL의 사업자 RootCA 또는 CA를 신뢰점으로 삼아 가입자 인증서 체인과 서명을 검증 | 이 경로가 TL에 등재돼 있고, 기준 시각의 상태가 판정 정책을 만족하는지 |

**TL의 변경은 인증서 발급 관계를 다시 만드는 작업이 아니다.** 기존 인증서 체인이 그대로여도, TL에 등재된 신뢰점과 상태·이력에 따라 수용되는 신뢰 경로가 달라진다. 그림과 화면은 인증서의 발급 관계와 TL이 부여하는 신뢰 관계를 구분해야 한다. 모든 관계를 하나의 인증서 발급 체인처럼 표현하지 않는다.

핵심 시연에서는 시험 인증서 체인을 고정하고 TL의 등재·상태 및 이용환경의 보유 버전을 바꾼다. CA 키 교체로 인증서 체인 자체가 바뀌는 SC-02는 별도 확장 사례로 둔다.

### 1.2 증명 범위와 생략 범위

| 구분 | 이번 PoC의 범위 |
|---|---|
| 핵심 증명 | TL 등재에 따른 신뢰 경로 수용, 정지·복원·철회에 따른 시점별 판정, 동기화 전후 판단의 변화 |
| 핵심을 뒷받침하는 확인 | TL 서명 검증, 변조·구버전 거부, 유효한 TL이 없을 때의 처리 |
| 관리 조작 | 인증 없이 신뢰정보 입력·상태 변경·입력 확정·TL 발행·결과 비교 |
| 생략 | 관리자 로그인·계정·세션·역할 선택, 승인자 분리·자기 승인 거부, 감사 해시 체인·감사 무결성 검사 |
| 최소 기록 | 시험 실행 ID, 변경 내용, 상태 효력 시각, 발행·수신 TL 버전, 사용한 신뢰점, 판정과 사유 |
| 소프트웨어 대체 | 시험용 인증서, 파일 키·모의 HSM, 폴더·H2, 동일 장비의 프로세스·포트 분리 |

관리자 인증 생략은 TL 서명 인증서나 가입자 인증서·타임스탬프 검증을 생략한다는 뜻이 아니다. 인증사업자 제출서 검증과 연계 인증도 관리자 로그인과 별개이며 이번 지시로 삭제하지 않는다. 최소 시험 기록은 결과 재현용으로, 행위자 신원이나 감사 기록의 변조 방지를 증명하지 않는다.

기존 [03 시나리오](03-이용-시나리오.md)의 SC-11은 이번 방향에 따라 핵심 시연에서 제외한다. SC-08은 신뢰 경로에 사용하는 TL의 출처·무결성을 확인하는 보조 시연으로 둔다. SC-02·07·09·10·12 전체를 새로 핵심 시연에 포함하지 않되, 핵심 경로에 필요한 기본 실패 처리는 정의한다.

## 2 설계 단계와 적절성 검토

기존 D 번호는 문서 간 추적을 위해 유지한다. 아래 표의 깊이로 설계하면 PoC에 적절하다.

| 단계 | 단계의 목적 | 적절성 판단과 필요한 설계 깊이 |
|---|---|---|
| D0 범위·요구사항 | 무엇이 달라지는 것을 증명할지 결정 | 필수. 핵심 명제·시나리오·생략 범위·RFP 대응을 초기에 정리 |
| D1 시스템 구성 | 신뢰정보 생성·전달·사용 주체와 책임 정의 | 적절. 논리 구성과 PoC 모듈 대응으로 충분 |
| D2 인터페이스 | 신뢰정보와 TL이 이동하는 입력·출력 정의 | 적절. 실제 사용하는 메시지·서명 대상·오류를 중심으로 작성 |
| D3 데이터 | 신뢰점, 등재, 상태 이력, TL 버전 정의 | 핵심. 어떤 데이터 변경이 어느 판정을 바꾸는지 명시 |
| D4 인증체계 | 비교에 사용할 인증서 체인과 신뢰앵커 정의 | 필수 기반. 고정 시험 체인·용도·초기 배치·생성 입력을 재현 가능한 수준으로 작성 |
| D4+ 신뢰 흐름 | TL을 통해 경로가 수용·거부되는 원리 설명 | 핵심. 변경 전후 경로와 신뢰가 성립하거나 끊기는 지점을 명시 |
| D5 관리 기능·화면 | 신뢰 흐름을 바꿀 시험 조건 입력 | 축소가 적절. 인증·승인 분리·감사 없이 상태 변경·발행·결과 확인에 집중 |
| D6 배포 | 변경된 TL을 이용환경에 전달 | 핵심 연결. 게시·수신·동기화 전후 버전과 실패 처리를 정의 |
| D7 이용환경 검증 | 주어진 경로와 시점의 신뢰 여부 판정 | 최우선 핵심. 입력·정책·시각·증거·사유 코드가 결과를 결정하도록 명시 |
| D8 운영 절차 | 같은 시연을 다시 실행 | PoC 실행 절차로 한정. 시작·초기화·재실행·수동 재시도면 충분 |
| D9 시나리오·시험 | 변경의 원인과 결과를 비교해 개념 증명 | 필수. 예상 결과를 설계 초기에 정하고 데이터와 절차를 함께 구체화 |
| D10 구현 설계 | 설계를 실제 모듈과 작업에 연결 | 적절. 핵심 경로를 연결할 작업·의존관계·확인 시나리오 중심 |
| D11 검토·확정 | 설계의 일관성과 이관 가능성 확인 | 적절. 핵심 판정의 미결 사항을 닫고 기준 문서와 후속 범위를 기록 |

### 2.1 적절한 진행 순서

D9를 마지막에 처음 작성하면 무엇을 증명할지 늦게 정해진다. 기존 산출물을 활용하면서 다음 순서로 보완한다.

1. **D0·D9:** 변경할 조건, 고정할 조건, 비교할 결과를 먼저 정한다.
2. **D1·D4·D4+:** 시험 체인과 신뢰 흐름을 정하고 변경 전후 경로를 설명한다.
3. **D3·D7:** 등재·상태·이력·시각을 판정표와 연결한다.
4. **D2·D5·D6:** 인증 없는 관리 조작부터 TL 전달·검증까지 이어 붙인다.
5. **D8·D9:** 초기 데이터·조작·기대 결과·초기화 방법을 시연 명세로 완성한다.
6. **D10·D11:** 최소 구현 작업을 나누고 설계 정합성을 확인한다.

D11의 정합성 점검은 각 단계에서도 수행한다. 문서 수를 늘리기보다 기존 문서의 관련 내용을 연결하고 중복·불일치를 정리한다.

## 3 단계별 상태와 설계 완성도

### 3.1 평가 기준

설계 완성도는 ‘구현자가 신뢰 흐름과 판정 규칙을 추가로 추정하지 않고 시연을 구현할 수 있는가’로 평가한다.

- **충분:** 해당 단계의 PoC 목적·경계·관계가 명확하다.
- **대체로 충분:** 핵심은 작성됐고 예시·조건·연결을 보완하면 된다.
- **부분 구체화:** 개요는 있으나 핵심 동작이나 판정 조건을 더 정해야 한다.
- **정리 필요:** 분산된 내용을 실행 또는 확정 기준으로 묶어야 한다.

‘기존 표시’는 [00 진행계획](00-설계-진행계획.md)의 요약 상태이며, ‘검토 판단’은 이번 범위와 관련 본문에 따른 평가다. 승인 완료·구현 진척·시험 통과를 뜻하지 않으며 백분율로 환산하지 않는다.

## 4 개념 증명을 선명하게 만드는 시연 설계

### 4.1 비교할 조건을 고정한다

핵심 시연에서는 사업자·인증서 체인·문서·검증 정책을 가능한 한 고정하고, 각 비교에서 의도한 조건만 바꾼다. 정지 전후를 비교할 때는 서로 다른 시각의 서명 표본이 필요하므로 표본별 차이를 명시한다.

| 고정하거나 명시할 조건 | 바꿔 볼 조건 | 관찰할 결과 |
|---|---|---|
| 사업자·인증서 체인, 동일한 서명 파일, 검증 정책·증거 | 이용환경이 보유한 TL 버전과 등재 정보 | 어떤 TL 신뢰점에 연결됐는지, 연결되지 않은 이유 |
| 시험 체인·판정 정책, 각 표본의 검증된 타임스탬프 | 서비스 상태와 효력 시각, 정지·복원 이력 | 각 서명 시점의 수용·거부 경로와 사유 |
| 동일 서명·정책·기준 시각·검증 증거 | 이용자와 브라우저의 동기화 여부 | 구·신 TL 사용 결과 및 동기화 후 일치 여부 |
| 신뢰앵커·정상 보유 TL | 수신 TL의 변조 또는 이전 버전 재게시 | 새 TL 거부와 정상 보유본 유지 여부 |

타임스탬프 시각만 수동 입력해 검증을 대신하지 않는다. 시험 파일과 타임스탬프는 실제 검증 대상이며, 시간 제어가 필요하면 증거 생성·검증에 적용한 시험 조건을 명시한다.

### 4.2 권장 시연 순서와 기대 관찰

| 순서 | 조작과 비교 | 보여 줄 신뢰 흐름 | 관련 시나리오 |
|---|---|---|---|
| 1 초기 경로 | 이용환경이 사업자 미등재 TL을 보유한 상태에서 시험 서명을 검증 | 인증서 체인은 있어도 TL의 신뢰점에 연결되지 않는 상태 | SC-01 |
| 2 등재와 동기화 | 사업자를 등재한 TL을 발행·수신하고 같은 시험 서명을 다시 검증 | TL 등재를 근거로 신뢰 경로를 수용하는 변화 | SC-01·06 |
| 3 서비스 정지 | 정지 정보를 담은 TL로 정지 전·후 서명 표본을 검증 | 같은 인증서 체인이라도 기준 시각의 상태에 따라 경로 수용 여부가 달라짐 | SC-03 |
| 4 복원과 철회 | 복원·철회를 차례로 반영해 시간 구간별 표본을 검증 | 복원해도 정지 구간의 이력은 남고, 철회도 정해진 시점 규칙으로 적용됨 | SC-04·05 |
| 5 동기화 비교 | 이용자·브라우저 중 한쪽만 갱신한 뒤 양쪽을 갱신해 비교 | 결과 차이가 인증서 체인 자체보다 사용한 TL·상태 정보 차이에서 발생함 | SC-06 |
| 6 출처·무결성 확인 | 변조 TL 또는 보유본보다 이전 버전을 제공 | 잘못된 TL이 신뢰 경로 판단에 채택되지 않음 | SC-08 보조 시연 |

**1~2번의 시간 조건을 분명히 한다.** 동일 서명의 ‘미등재 TL에서는 판단 보류, 등재 TL에서는 통과’를 보여 주려면, 시험 서명은 최초 인정 효력 시각 이후에 생성하고 이용환경에 구 TL을 남겨 두는 방식으로 설계할 수 있다. 이는 시연 설계 제안이다. 최초 인정 이전의 타임스탬프가 있는 서명을 등재 후 무조건 통과시키는 예시와 혼동하지 않는다.

각 통과 예시는 서명값·인증서·타임스탬프·폐지 정보 등 다른 검증 조건이 정상이라는 시험 전제를 갖는다. 상태 정지·철회만으로 모든 과거 서명의 유효성을 일반화하지 않는다. 효력 시각과 발행 시각의 관계는 기존 D3 규칙과 일치시킨다.

### 4.3 비교 화면과 최소 증거

화면은 다음 세 영역이면 충분하다. 관리자 계정·승인 대기·감사 대시보드를 중심에 두지 않는다.

| 화면 영역 | 표시 내용 |
|---|---|
| 변경 조건 | 대상 사업자·서비스·신뢰점, 변경 상태와 효력 시각, 발행 TL 버전 |
| 변경 전후 신뢰 경로 | 고정된 인증서 체인, TL 등재 신뢰점, 기준 시각의 서비스 상태, 경로 수용·거부 지점 |
| 이용환경 결과 | 사용한 TL 버전, 서명 표본과 시각 근거, 적용 정책, 최종 판정·사유 |

최소 증거는 동일 시험 실행 ID로 연결된 ‘변경 데이터 + 발행 TL + 이용환경별 사용 버전 + 경로·판정 결과’다. 접속 기록은 전달 확인을 보조하고, 실제 적용은 이용환경이 기록한 사용 TL 버전과 결과로 확인한다. 별도 적용 확인 API나 운영용 이용기관 등록 체계를 필수로 만들지 않는다.

## 5 완성도를 높이는 우선 작업

| 우선순위 | 보완 작업 | 대상 단계 | 설계 완료 기준 |
|---|---|---|---|
| 1 | 변경 전후 신뢰 경로와 시간축 판정표 작성 | D3·D4+·D7·D9 | 등재·정지·복원·철회별로 어떤 경로가 어떤 시각에 수용·거부되는지와 사유가 결정됨 |
| 2 | TL 형식·상태·판정 코드 통일 | D2·D3·D7 | 05의 JWS 우선, 06의 병행, 15의 XML·XAdES 단일화 등 충돌이 해소되고 예시가 일치함 |
| 3 | 인증 없는 변경·발행·수신 경로 정의 | D2·D5·D6 | 단일 시연자가 입력 확정부터 발행·동기화까지 조작하며, 스냅숏·서명·게시 순서와 기본 오류가 명시됨 |
| 4 | 시험 데이터와 비교 화면 명세 완성 | D4·D7·D9 | 표본·체인·시각·정책·초기 TL·기대 경로·판정·사유를 고정해 비교할 수 있음 |
| 5 | 준비·초기화·재시연과 구현 작업 정리 | D8·D10 | 입력 파일·실행 순서·변경 모듈·의존관계·확인 시나리오가 연결됨 |
| 6 | 범위·요구사항·상태표 정합성 정리 | D0·D11 | 생략 범위가 관련 문서에 반영되고 핵심 미결 사항·후속 과제·기준 버전이 구분됨 |

1번과 4번을 중심으로 나머지 설계를 맞춘다. 관리자 기능을 줄였다는 이유로 D5를 자동 완료 처리하지 않는다. 인증 없는 조작 흐름과 발행 대상의 일관성은 여전히 정해야 한다.

### 5.1 기본 규칙으로 남길 사항

- TL 서명 검증, 이전 버전 거부, 유효한 TL이 없는 경우의 결과를 정한다.
- 동일 번호·동일 내용 재전송과 동일 번호·다른 내용의 충돌을 구분한다. 동시 발행·자동 복구의 복잡한 설계는 단일 발행·수동 재시도 가정으로 제한할 수 있다.
- 타임스탬프 없는 서명은 PoC용 정책을 명시한다. 두 정책을 비교한다면 각 결과에 정책을 표시한다.
- SDK와 브라우저의 일치 조건은 동일 서명·TL뿐 아니라 정책·기준 시각·검증 증거까지 포함한다.
- RFP의 인증서 자동 수집·주기적 동기화 요구와 현재 제출 방식의 대응은 별도로 설명한다. 관리자 인증 생략이 해당 요구의 삭제나 충족을 의미하지 않는다.
- OpenAPI는 기존 D2 산출물 계획에 따라 실제 사용하는 IF 중심으로 작성한다. 명세 파일의 존재보다 교환 메시지와 처리 규칙의 명확성을 먼저 평가한다.

본 문서는 검토 기준을 갱신한 것이다. 아래 원문 문서의 해당 내용은 후속 정합성 작업에서 반영해야 하며, 이미 수정됐다고 보지 않는다.

| 문서 | 맞춰야 할 내용 |
|---|---|
| 00 진행계획 | D5의 권한·감사 작업과 완료 기준을 핵심 범위에서 분리하고 단계별 상태에 근거 연결 |
| 01 구성도·08 신뢰 흐름 | 신뢰 경로 변경을 중심에 두고, 인증서 발급 관계와 TL 신뢰 관계 및 비교 증거를 구분 |
| 02 관리 화면·04 PoC 구성 | 역할 선택 로그인·승인자 분리·감사 검사를 제외하고 상태 변경·발행·비교 화면 중심으로 정리 |

| 05 설계 검토·15 코드 범위 | 핵심 작업에서 관리자 인증·승인 분리·감사 구현을 분리하고 시험 결과 기록과 구분 |
| 06 IF 명세 | IF-02의 관리자 세션·역할·자기 승인 거부 및 IF-05의 승인 기록 필수 전제를 조정. 입력 확정과 발행 대상의 일관성은 유지 |

## 6 후속 범위와 설계 종료 조건

실제 HSM·폐쇄망·VPN 구축, 고가용성·성능·재해복구, 상용 관리자 인증·승인·감사 체계, 전체 이용기관 관리, 장기 검증·PQC 정책과 전체 키 수명주기는 후속으로 구분한다. 소프트웨어 대체로 증명하는 것은 이번 시험 조건에서의 신뢰 흐름이며, 상용 운영 체계 전체의 안전성은 아니다.

설계 종료는 다음 항목으로 판단한다. 실제 구현과 시험 통과는 구현 단계에서 별도로 확인한다.

- [ ] 핵심 명제와 관리자 인증·승인 분리·감사 제외 범위가 일관되게 정의돼 있다.
- [ ] 인증서 발급 관계와 TL을 통한 신뢰 관계가 구분돼 있다.
- [ ] 변경 전후의 신뢰 경로와 수용·거부 지점이 등재·상태·이력에 연결된다.
- [ ] 최초 등재·정지·복원·철회 및 경계 시각의 기대 판정과 사유가 정해져 있다.
- [ ] TL 발행·서명·배포·수신·검증의 입력과 출력이 연결된다.
- [ ] 시험 데이터·정책·시각·초기 버전·조작·비교 증거·초기화 방법이 지정돼 있다.
- [ ] 구현 작업과 기준 문서, 남은 요구사항 확인 및 후속 범위가 구분돼 있다.
