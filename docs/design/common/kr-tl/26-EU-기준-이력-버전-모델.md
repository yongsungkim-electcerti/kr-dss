# 26. EU 기준 KR-TL 이력·버전 모델 상세안

작성일: 2026-10-07. 설계 구체화 단계이며 제품 코드 변경은 아니다.

2026-10-09 상세 보완: [PoC 프로파일 v1](../../poc/tl-management/profile-poc-v1.md)은 임시 상태·유형 URI, 분야·CA 레벨 및 critical 확장을 정의한다. [발행·복구 상세](../../poc/tl-management/issuance-recovery.md)는 요청 중복·실패·정상 기준 보존을 정의한다. 아래의 미정 매핑과 순번 제안 방식은 이 두 문서로 구체화하며, 국가 공표 규격으로 해석하지 않는다.

키 파일·인증서의 실제 생성 예정 위치와 발급 체인은 [27 PoC 키 파일 디렉터리 설계](../../poc/tl-management/pki/27-PoC-키파일-디렉터리-설계.md)를 따른다. 실제 생성과 디렉터리별 체인 설명 문서 작성은 후속 개발 작업이다.

## 1. 기준과 적용 범위

기존 설계와 같은 [ETSI TS 119 612 V2.4.1 (2025-08)](https://www.etsi.org/deliver/etsi_ts/119600_119699/119612/02.04.01_60/ts_119612v020401p.pdf)를 공식 원문으로 대조했다. 규격 판본 `2.4.1`, XML 형식 버전 `6`, KR 프로파일 버전, 개별 발행 순번은 서로 다른 값이다.

표준에서 채택하는 핵심 구조는 다음과 같다.

| 근거 | 채택 규칙 |
|---|---|
| §5.3.1·2 | TSLVersionIdentifier는 6. TSLSequenceNumber는 최초 1부터 발행마다 증가 |
| §5.3.12·14·15 | HistoricalInformationPeriod는 65535(이력 유지). 발행 시각·NextUpdate는 UTC. 유효기간 상한 6개월 |
| §5.5.10·5.6 | 현재 정보와 과거 정보를 분리. 이력은 최신순이며 최초 등재에는 없음 |
| §5.6.3 | 이력 디지털 ID에는 최소 X509SKI를 포함하고 인증서는 넣지 않음 |
| §5.5.5 | 새 상태 효력의 소급 금지. 변경하지 않은 상태의 시작 시각을 재발행 때 갱신하는 규칙은 아님 |
| G.4 | 새 키는 새 서비스. 같은 키·같은 X.509 Subject의 인증서 추가는 같은 서비스이며 상태 이력을 만들지 않음 |
| §5.5.4 | 비EU 상태 값은 운영자가 정의·공표 |

이하 자료형·저장 방식·오류 처리·알고리즘은 이 구조를 적용하기 위한 **KR-TL PoC 설계 제안**이다. EU 적격 지위를 국내 인정과 동일시하지 않는다. [25의 사용자 결정](../../../development/poc/tl-management/reviews/25-PoC-구현-차이-검토.md#3-확정된-poc-범위)을 따른다. 인증·감사·심사 업무는 제외하며, 여기서 이력은 신뢰 판정에 필요한 서비스 정보다. 시나리오·표본·시험 시계는 확정하지 않는다.

## 2. 세 종류의 데이터 분리

| 객체 | 역할 | 변경 가능 여부 |
|---|---|---|
| RegistryDraft | 발행 전 사업자·서비스 입력, 다음 상태 변경 요청 | 편집 가능. 심사·승인 상태는 없음 |
| TrustListSnapshot | 발행 시 고정한 전체 TL 데이터 | 불변. 서비스 현재 정보와 과거 이력 포함 |
| IssuedTrustList | 서명된 XML 바이트와 식별 정보 | 불변. issuanceId별 보관, 순번은 메타데이터, 재전송 시 그대로 사용 |

초안을 여러 번 편집해도 공개 서비스 이력은 늘지 않는다. 한 발행에서 반영하는 최종 변경만 새 스냅숏에 반영한다. 서비스 이력과 TL 발행본 보관은 별개다. 발행본은 당시 무엇을 공개했는지 보여주며, 서비스 이력은 해당 발행본이 설명하는 효력 구간이다. PoC에서는 오류 발행본도 별도 발행 ID로 보관한다.

## 3. 버전·발행 모델

| Java 필드 제안 | 자료형 | 저장·XML 연결 |
|---|---|---|
| formatVersion | int | SchemeInformation/TSLVersionIdentifier, 프로파일 상수 6 |
| sequenceNumber | BigInteger | SchemeInformation/TSLSequenceNumber, 양의 정수 |
| issuedAt | Instant | ListIssueDateTime |
| nextUpdate | Instant | NextUpdate/dateTime. 이번 활성 PoC에서는 필수 |
| historicalInformationPeriod | int | 65535, 관리 화면 편집 대상 아님 |
| profileVersion | String | 내부 프로파일 설정. XML 형식 버전으로 대입하지 않음 |
| listId | String | 내부 목록 식별자. 배포 URL이나 운영자 이름 변경으로 새 목록을 만들지 않음 |
| signedXmlSha256 | String | 최종 서명 바이트의 해시. 내부 저장·동일본 확인용 |

정상 TL의 논리 식별자는 `(listId, sequenceNumber)`다. 다만 PoC는 같은 순번의 다른 내용과 하위 순번 발행을 허용하므로, **실제 보관 키는 별도 `issuanceId`(UUID)**로 둔다. 순번은 보관 폴더의 유일 키가 아니다. 서비스별 순번은 추가하지 않는다. `draftRevision`이 필요하면 동시 편집 방지용 내부 값으로만 둔다.

운영자·제도·지역 등 기존 SchemeInformation 필드는 그대로 별도 유지한다. 위 표는 완전한 TL 스키마가 아니다. 정상값은 `issuedAt < nextUpdate`, UTC 달력 기준 최대 6개월로 제안한다. 기존 7일 설정은 조정 가능한 기본값이다. **관리 화면에서 이 규칙을 위반한 값도 발행할 수 있어야 한다.** 규칙은 수신 검증 모듈에서 강제한다. 종료 TL은 별도 범위이며 null을 무기한 유효로 해석하지 않는다.

### 발행 절차

1. 화면에 정상 권장값을 표시하고 사용자가 순번·시각을 덮어쓸 수 있게 한다. 자동 순번 제안의 기준과 실제 입력값을 분리한다.
2. 초안을 복사해 후보 스냅숏을 만든다. 새 상태의 시작 시각도 기본값을 제공하되 조정할 수 있다.
3. 형식·의미 검사 결과를 안내하고 키 파일로 서명한다. 의미 오류는 발행을 차단하지 않는다. 서명 후 자체 검사는 생성된 서명의 암호학적 성립을 확인한다.
4. `issuanceId`별 서명본·입력값을 임시 저장 후 확정한다. 파일 보관 성공은 신뢰 검증 통과를 뜻하지 않는다.
5. 사용자가 선택한 발행본을 Spring Boot WAS에서 제공한다. 의미 오류가 있거나 순번이 낮아도 제공할 수 있어야 한다. 수신 검증기가 이를 받아 판정한다.

키 읽기·암호 서명·파일 저장 실패는 생성 성공이 아니다. 반면 순번 역행·시각 모순은 의도적으로 생성 가능한 내용 오류다. 생성 요청 식별자로 응답 유실 시 기존 결과를 복구하며, 사용자가 새 재발행을 요청하면 같은 순번으로도 새 issuanceId를 만든다. 정상 재발행 기본 동작은 새 순번·발행 시각과 기존 서비스 이력 유지다. 보관된 파일은 덮어쓰지 않는다. 자동 제안 순번은 마지막 확정 BASELINE의 순번+1로 한다. TRIAL 최대 순번·현재 제공본·외부 수신자의 수용 순번은 제안값의 기준이 아니다.

### PoC 관리 화면과 검증 책임 (사용자 추가 결정)

| 화면에서 조정·선택할 항목 | 수신 검증 모듈의 확인 |
|---|---|
| 순번: 정상 증가·동일 번호·하위 번호 | 보유본 대비 증가/동일본/충돌/역행 판정 |
| 발행 시각: 과거·미래·직전보다 이른 시각 | 검증 기준 시각과 비교, 보유본 대비 시간 정합성 확인 |
| NextUpdate: 만료·발행 이전·과도한 기간 | 만료, issuedAt과의 순서, 유효기간 상한 검사 |
| 상태 시작 시각: 소급·구간 중복·순서 오류 | 새 상태의 소급 및 이력 정합성 검사 |
| 기존 발행본 재제공 / 같은 번호로 새 내용 발행 | 바이트 동일성 확인, 동일 번호 다른 내용 거부 |

화면에는 **입력값·생성 여부·현재 WAS 제공본·검증 결과**를 구별해 표시한다. 관리 화면의 사전 검사 결과는 안내이며, ‘생성 성공’을 ‘유효한 TL’로 표현하지 않는다. 화면 안내의 우회가 검증 모듈의 우회로 연결되어서는 안 된다. 인증·감사 기능은 추가하지 않는다.

시각·순번 오류 TL도 정상 키로 서명한다. 그러면 암호 서명은 통과하고 의미 검증에서 거부되는지를 확인할 수 있다. 서명 변조·XSD 파괴 등 추가 오류 생성 기능과 구체적 시나리오 목록은 향후 결정한다. 이번에는 최소한 XML로 표현 가능한 순번·시각 값의 의미 오류를 생성할 수 있게 한다.

검증은 생성 코드의 사전 검사 여부와 무관하게 실행한다. 검증 결과에는 실제 검사한 항목별 결과와 수용 여부를 분리한다. 제안 사유 코드는 `SEQUENCE_ROLLBACK`, `SEQUENCE_CONFLICT`, `ISSUE_TIME_IN_FUTURE`, `ISSUE_TIME_REGRESSION`, `INVALID_UPDATE_INTERVAL`, `TL_EXPIRED`, `RETROACTIVE_STATUS_CHANGE`, `INVALID_HISTORY`다. 미래 시각 허용 오차는 명시적 검증 설정으로 두고, 시나리오용 시계와 혼동하지 않는다. 비교할 보유본이 없는 최초 수신에서는 과거 발행본 대비 역행·이력 삭제를 확인할 수 없음을 결과에 남긴다.

수신 거부 시 기존 유효본을 유지하고, 기존본도 만료되었다면 유효 TL 없음으로 처리한다. 오류 발행본을 제공했다고 관리 저장소의 정상 서비스 이력을 지우거나 수신 캐시를 초기화하지 않는다. 재제공·오류 생성은 별도 후보 복사본에서 수행한다.

## 4. 서비스·이력 모델

```text
TrustService
  serviceId                 내부 불변 식별자
  current: ServiceInformation
  history: List<ServiceHistoryInstance>     최신순

ServiceInformation
  serviceTypeUri
  names: List<LocalizedName>
  digitalIdentity: CurrentDigitalIdentity
  statusUri
  statusStartingTime: Instant
  extensions: List<ServiceExtension>
  supplyPoints / definitionUris            현재 정보의 선택 필드

ServiceHistoryInstance
  serviceTypeUri
  names: List<LocalizedName>
  digitalIdentity: HistoricalDigitalIdentity
  statusUri
  statusStartingTime: Instant
  extensions: List<ServiceExtension>
```

`providerId`·`serviceId`는 관리 저장소의 키다. EU XML 요소로 임의 추가하지 않는다. XML에서 읽은 서비스는 유형·디지털 ID를 기준으로 연결하며, 이름만으로 동일성을 판단하지 않는다. 외부 공개 ID 확장이 필요해지면 별도 KR 프로파일에서 정의한다.

이력은 상태 enum만 저장하는 목록이 아니다. 해당 시점의 이름·유형·디지털 식별 정보·확장도 보존한다. 다만 현재 객체를 그대로 XML 이력으로 직렬화하지 않는다. 현재의 인증서 데이터와 이력의 식별자 표현이 다르기 때문이다.

| 디지털 ID 객체 | PoC 자료 제안 | 규칙 |
|---|---|---|
| CurrentDigitalIdentity | certificatesDer[], subjectName, subjectKeyIdentifiers[], spkiSha256 | 인증서 1개 이상. 같은 서비스의 인증서는 동일 공개키·Subject인지 확인 |
| HistoricalDigitalIdentity | subjectKeyIdentifiers[], subjectName(선택) | 인증서 필드 없음. XML 이력에는 X509SKI 표현 사용 |
| 내부 인증서 보관 | 인증서 지문 → DER | 이력 XML과 분리. 과거 자료 확인용 |

SKI만으로 신뢰를 부여하지 않는다. SKI로 후보를 찾은 뒤 현재 서비스의 실제 공개키·Subject와 인증서 경로를 확인한다. 내부 SPKI 해시는 조회 최적화 수단이며 서명·경로 검증을 대체하지 않는다. DER 배열과 목록은 방어 복사하고, 인증서 중복은 바이트 지문으로 제거한다.

## 5. KR 상태와 확장

내부 업무 상태는 `ACCREDITED`, `SUSPENDED`, `WITHDRAWN`, `SET_BY_NATIONAL_LAW`로 구별한다. XML 모델은 `statusUri`를 보존하고 명시적 매핑으로 내부 상태를 얻는다. 상태·확장 URI의 실제 주소는 별도 프로파일 설정에서 관리한다. 기존 임시 URI를 국가 공표 URI로 표현하지 않는다.

`GRANTED`라는 기존 Java 이름을 국내 인정에 계속 사용할 경우 EU qualified 의미와 혼동될 수 있으므로 `ACCREDITED`로 바꾸는 것을 제안한다. 기존 데이터 변환은 명시적으로 처리하고, 알 수 없는 URI를 WITHDRAWN이나 ACCREDITED로 자동 치환하지 않는다. 발행 입력의 미지원 값은 거부하고, 수신 데이터에서 해석할 수 없는 상태는 신뢰 판정을 보류한다.

공동·간편인증 분야, 신뢰점 레벨, 정지 분류는 KR 확장으로 유지한다. `ServiceExtension`은 확장 종류·critical 여부·값을 보존해야 한다. 판정에 필요한 확장 값을 현재 정보와 이력에 각각 저장하고, 현재 값을 과거 구간에 소급 적용하지 않는다. EU용 상태 변환은 향후 국제 연동 범위이며 이번 모델 변경에서 구현하지 않는다.

## 6. 변경별 처리

| 변경 | 처리 제안 |
|---|---|
| 최초 등재 | current 생성, history 빈 목록. XML에서는 빈 ServiceHistory를 출력하지 않음 |
| 인정→정지·철회 또는 복원 | 기존 current를 이력 표현으로 변환해 선두에 추가하고 새 current 생성 |
| 같은 상태·동일 데이터 저장 | 새 이력 없음 |
| 이름·판정 확장 변경 | 의미 있는 변경은 같은 상태라도 새 정보 구간 생성. 이전 값 보존 |
| 같은 키·같은 Subject의 인증서 갱신 | 현재 인증서 집합에 추가. 상태 시작 시각·이력 유지 |
| 새 공개키 | 새 serviceId로 등재. 기존 서비스와 이력은 유지. 기존 서비스 철회는 별도 변경 |
| 같은 키·다른 Subject | 정상 갱신 규칙에는 부적합. 별도 식별 정책 없이 자동 합치지 않음 |
| 서비스 종료 | 현재 상태를 철회로 바꾸고 항목·이력 유지 |
| 발행본 오류 발견 | 기존 바이트 수정 금지. 정정 발행 필요. 과거 효력 정정 정책은 별도 결정 |

정상 서비스의 구간 시작 시각은 엄격히 증가해야 한다. 동일 시각에 서로 다른 상태가 있으면 검증 오류다. 일반 편집은 발행 전 변경을 최종 값 하나로 합치며 과거 이력을 유지한다. PoC 오류 생성은 후보 복사본의 시각을 조정할 수 있고, 수신 검증 모듈이 충돌을 거부한다.

## 7. 시간 조회와 버전의 관계

새 상태의 소급 검사는 **그 상태가 처음 실리는 발행본**과 비교한다. 예를 들어 t0에 시작한 인정 상태를 t1에 단순 재발행하면 시작은 여전히 t0이다. `모든 statusStartingTime >= 최신 issuedAt` 검사는 잘못된 검사다.

상태 구간은 `[시작 시각, 다음 상태 시작 시각)`으로 계산하고 끝 시각은 파생값으로 둔다. current와 history를 합쳐 시작 시각으로 정렬한 뒤 대상 시각 이하의 마지막 항목을 선택한다. 최초 시작 전이면 근거 없음으로 반환한다. 경계에서는 새 항목이 선택된다.

조회 계약은 다음과 같이 제안한다.

```text
resolve(serviceIdentity, targetTime, acceptedSnapshot)
  → statusUri, effectiveFrom, effectiveUntil?, matchedIdentity,
    listId, sequenceNumber, resolutionReason
```

`targetTime`은 호출자가 전달한다. 모델이 시험 시계를 만들거나 현재 시각으로 대신 채우지 않는다. 서명 시각의 증거 수준·장기 검증·최종 문서 판정은 별도 검증 정책이다. 이 조회 결과만으로 PDF 서명 유효성을 확정하지 않는다.

설명 예시(확정 시나리오 아님): t0 인정 → t1 정지 → t2 복원이라면 최신 TL은 current=인정(t2), history=[정지(t1), 인정(t0)]를 담는다. t1 이상 t2 미만 조회는 정지다. 이후 TL을 재발행해도 이 구간은 그대로다.

수신 측은 서명·형식·유효기간 검증을 통과한 스냅숏만 원자적으로 적용한다. 같은 목록에서 낮은 순번은 거부, 같은 순번·같은 해시는 동일본, 같은 순번·다른 해시는 충돌로 처리한다. 더 큰 번호라도 검증 실패하면 교체하지 않는다. 만료본 파일 보관과 신뢰 판정에 사용 가능한 활성 캐시는 구별한다. 사용한 순번을 결과에 남겨 판정 근거를 식별한다.

## 8. 현재 코드 변경 단위

| 대상 | 변경 |
|---|---|
| KrTrustList.SchemeInformation | version을 formatVersion/sequenceNumber로 분리, 이력 보존 값 추가 |
| KrTrustList.TrustService | current/history와 다중 디지털 ID로 분리, 서비스 식별자 도입 |
| KrTrustListXml | 형식 버전 6과 순번 별도 출력, 이력은 X509SKI로 출력·복원, 미지원 상태 자동 치환 제거 |
| 발행 서비스 | 초안·스냅숏·서명본 분리, issuanceId별 보관, 순번·시각 조정 및 오류본 제공 |
| 이용기관 | 현재 상태만 보는 판정을 시점 조회로 연결, 사용 순번 반환 |

기존 `version`의 숫자만 보고 형식인지 순번인지 자동 추정하지 않는다. 기존 파일은 명시적인 구형 변환 경로로 읽고, 이력이 없는 서비스를 과거부터 인정된 것으로 보충하지 않는다. JWS 호출부 정리는 XML 전환 작업에서 별도로 처리한다.

기술 확인 항목은 필드 분리 왕복 변환, 상태 경계 조회, 재발행 시 이력 불변, 인증서 갱신과 키 교체 구별, 이력 XML에 인증서 미포함, 서명·저장 실패 시 순번 복구다. 이는 구현 검증 항목이며 D-06의 PoC 시나리오 확정이 아니다. 전체 XML 필수 필드·언어·확장 XSD 적합성까지 검사하기 전에는 EU 규격 완전 준수를 주장하지 않는다.
