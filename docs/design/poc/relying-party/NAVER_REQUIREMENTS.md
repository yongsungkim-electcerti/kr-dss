# 네이버 웨일 전자서명 검증 PoC 기능요구사항

## 1. 목적

네이버 웨일 및 협의된 문서 서비스 환경에서 KR-AdES 서명 PDF를 열람·검증하고, KR-TL 기반 신뢰 상태를 사용자에게 명확히 표시하여 표준 규격과 검증 SDK의 실제 서비스 적용 가능성을 확인한다.

## 2. 책임 경계

| 주체 | 책임 |
|---|---|
| 네이버 | 문서 선택 및 권한 동의, SDK 연동 지점, 결과 UI, 오류 구분, 실증 환경 제공 |
| 일렉서티 | 검증 SDK, 검증 알고리즘, 결과 스키마·코드, 샘플 문서, 연동 예제, 기술지원 |
| KISA | KR-TL 데이터, 배포·갱신·만료 정책, 신뢰목록 운영 기준 |

검증 알고리즘과 신뢰 판정은 SDK가 담당하고, 웨일은 문서 전달·결과 표시·사용자 상호작용을 담당한다.

## 3. 필수 기능요구사항

| ID | 기능요구사항 | 수용 기준 |
|---|---|---|
| NV-WV-01 | 사용자가 서명된 PDF를 열거나 선택하여 검증을 시작할 수 있어야 한다. | 파일 선택, 드래그 앤 드롭, 검증 버튼을 제공한다. |
| NV-WV-02 | 웨일은 검증 SDK에 문서 데이터를 전달하고 구조화된 결과를 받을 수 있어야 한다. | 요청 식별자, SDK 버전, 처리시간과 결과코드가 남는다. |
| NV-WV-03 | 무결성, 서명, 인증서, 인증서 경로, KR-TL, 정책 적합성을 분리 표시해야 한다. | 각 판정이 독립된 상태와 설명을 갖는다. |
| NV-WV-04 | 종합 상태를 `유효`, `경고`, `검증 불가`로 구분해야 한다. | 세 상태가 색상뿐 아니라 아이콘·문구로도 구분된다. |
| NV-WV-05 | 복수 서명 문서는 서명별 결과를 조회할 수 있어야 한다. | 서명자 목록을 선택하면 상세 결과가 바뀐다. |
| NV-WV-06 | 인증서 발급자·주체·유효기간·정책 OID·인증서비스 정보를 제공해야 한다. | 상세 패널에서 해당 값을 확인할 수 있다. |
| NV-SEC-01 | 로컬 문서 접근과 외부 전달 전에 사용자 동의를 받아야 한다. | 동의하지 않으면 문서 데이터가 처리되지 않는다. |
| NV-SEC-02 | 검증에 필요한 최소 데이터만 처리해야 한다. | 외부 전송 여부와 처리 위치를 사용자에게 알린다. |
| NV-SEC-03 | 문서 원문·인증서 개인정보를 브라우저 로그에 남기지 않아야 한다. | 운영 로그에 원문 및 개인정보가 존재하지 않는다. |
| NV-SEC-04 | SDK 출처, 통신 경로와 허용 도메인을 제한할 수 있어야 한다. | 승인되지 않은 출처와 통신이 차단된다. |
| NV-SEC-05 | 검증 실패와 문서 열람 실패를 혼동하지 않도록 표시해야 한다. | 문서 열람 상태와 서명 검증 상태가 별도 영역에 표시된다. |
| NV-SEC-06 | 권한 거부, 통신 오류, 미지원 파일, 응답 오류를 구분해야 한다. | 오류별 코드·설명·다음 조치가 제공된다. |
| NV-POC-01 | 실증 대상 웨일 버전과 운영체제를 확정한다. | 시험 결과에 브라우저·OS 버전이 기록된다. |
| NV-POC-02 | SDK 적용 지점과 API 호출 구조를 공동 검토한다. | 합의된 연동 구조와 데이터 흐름도가 승인된다. |
| NV-POC-03 | 정상·변조·미등록·오프라인·예외 시나리오를 공동 시험한다. | 시나리오별 기대 결과와 실제 결과를 기록한다. |
| NV-POC-04 | 오류 재현용 실행정보와 결과코드를 제공한다. | 버전, 실행시각, 요청 ID, 결과코드로 재현할 수 있다. |
| NV-POC-05 | 실증 화면 또는 확장 프로그램의 배포 방식을 협의한다. | 배포 채널, 접근 권한, 종료 기준이 문서화된다. |

## 4. 선택·확장 요구사항

- CPS 또는 인증서비스 정책정보 링크 제공
- 검증 결과 요약 및 상세보고서 다운로드
- HWP·XML·JSON·CMS·Markdown 포맷 확대
- B/T/LT/LTA 수준 및 복수 서명 고도화
- EU-TL 연계
- 브라우저 내장 기능 또는 정식 확장 프로그램 배포

## 5. 판정 원칙

- `서명의 암호학적 검증 성공`과 `KR-TL 등록 서비스 확인`은 별도 판정한다.
- KR-TL 미등록은 서명 위조를 뜻하지 않는다. 이 경우 종합 상태는 `경고`로 표시하고 “전자서명은 확인되었으나 KR-TL 등록 서비스인지 확인할 수 없습니다”라고 안내한다.
- 오프라인에서는 캐시의 발행시각·만료시각·사용 여부를 명확히 표시한다.
- 색상만으로 상태를 전달하지 않고 아이콘, 제목, 설명과 결과코드를 함께 제공한다.

## 6. 1단계 PoC 범위

- PDF 단일 포맷
- 명시적 사용자 동의 후 검증
- JavaScript/WASM SDK 또는 합의된 API 연동
- 정상, 변조, KR-TL 미등록, 오프라인 캐시, 서명 없음 시나리오
- 종합 상태와 세부 판정 표시
- 실행환경 및 결과코드 기록

## 7. 사전 확정 질문

1. 웨일 연동 방식은 실증 웹, 확장 프로그램, 브라우저 내장 기능 중 무엇인가?
2. JavaScript/WASM SDK 실행과 로컬 PDF 바이트 접근이 가능한가?
3. 문서 원문은 브라우저 내부에서만 처리해야 하는가?
4. 자동 실행과 사용자의 명시적 검증 요청 중 어느 방식으로 할 것인가?
5. 오프라인 KR-TL 캐시의 저장 주체, 유효기간과 갱신 방식은 무엇인가?
6. 문서편집·서명 생성 서비스가 실제 네이버 협업 범위에 포함되는가?
