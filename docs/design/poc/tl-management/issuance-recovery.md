# 발행·저장·제공의 트랜잭션과 복구

작성일: 2026-10-09. 단일 Spring Boot WAS·로컬 파일 저장을 전제로 한 구현 설계다. 감사·권한·다중 서버·DB를 추가하지 않는다.

## 보존할 조건

- 응답으로 발행 성공을 알린 issuanceId는 재기동 후 같은 바이트로 조회할 수 있어야 한다.
- 응답 유실 후 같은 요청은 같은 결과를 돌려준다. 재서명하지 않는다.
- 의미 오류 시험 발행은 정상 서비스 이력과 정상 권장 순번을 바꾸지 않는다.
- 발행 성공과 제공본 선택은 별도 변경이다. 제공 실패로 재발행하지 않는다.
- 한 GET의 헤더·본문·해시는 하나의 불변 발행본에서 가져온다.

구현 책임은 관리 PoC의 저장·발행 기능이다. 외부 검증기의 수용본·이력·캐시는 이 트랜잭션에 참여하지 않는다.

## 저장 배치와 권위

모든 경로는 `runtime/tl-management/` 아래이며 Git 비관리다.

| 경로 | 내용·권위 |
|---|---|
| registry/revisions/<revision>.json | 불변 초안 버전. 다음 저장은 새 revision |
| staging/<requestId>/ | 입력 고정본·서명 파일·manifest 작성 중. 외부 제공 금지 |
| issued/<issuanceId>/ | snapshot.json, signed.xml, signed.sha256, manifest.json, profile.json |
| publication/state.json | 활성 draftRevision, baselineIssuanceId, 정상 sequence, 발행 확정 목록·requestId 매핑, 제공 포인터·revision |
| requests/<requestId>.json | 진행/실패 진단. 성공 여부의 최종 권위는 state.json |
| pki/ | 파일 키·인증 체인. 발행 manifest에는 개인키를 넣지 않음 |

state.json의 committed 목록에 기록되고 파일 무결성도 확인되는 발행본만 확정본이다. issued 폴더가 있다는 이유만으로 성공 처리하지 않는다. 목록 크기 최적화·DB 전환은 이후 과제다. 현재는 작은 PoC의 단순 복구를 우선한다.

manifest는 requestId, issuanceId, listId, purpose, 입력 digest, 초안 revision, baseline ID, 실제 순번·시각, 최종 XML 해시·크기, 프로파일 해시, 서명 인증서 지문, 진단 목록을 담는다. XML 원문과 저장 digest를 비교한다. 동일 내용의 기준은 최종 서명 XML 바이트다.

## 동시성·초안·기준 이력

시작 시 저장 루트의 프로세스 잠금을 획득한다. 같은 루트를 사용하는 두 번째 작성 WAS는 시작을 실패시킨다. 한 WAS 안에서는 저장·발행·제공본 선택을 하나의 작성 잠금으로 직렬화한다. 읽기는 잠금 없이 검증된 불변 상태 스냅숏을 참조한다. 높은 처리량보다 PoC의 상태 일관성을 우선한다.

초안 저장·발행 요청은 기대 draftRevision을 가진다. 발행 잠금을 획득한 뒤 현재 revision과 다르면 충돌로 반환하며 사용자 입력을 덮어쓰지 않는다. 제공본 선택도 기대 publicationRevision으로 충돌을 검출한다. 네트워크 대기 중 잠금을 계속 보유하지 않도록 외부 호출 없는 로컬 발행으로 제한한다.

초안은 baselineIssuanceId와 아직 확정되지 않은 편집 내용을 가진다. 발행 후보에서 최종 변경만 상태 이력으로 반영한다. BASELINE 발행 성공 시 후보 스냅숏을 새 정상 기준으로 삼고, 변경분이 비어 있는 새 초안 revision을 함께 활성화한다. TRIAL 성공 시 기존 초안·기준 이력·정상 sequence는 그대로 둔다. 따라서 단순 재발행이 이전 변경을 중복 이력으로 추가하지 않는다.

정상 권장 순번은 마지막 확정 BASELINE의 순번+1, 최초에는 1이다. TRIAL의 최대 순번과 현재 제공본은 제안값의 기준이 아니다. 입력값이 기준 증가·시각·이력 정상 규칙을 위반하면 경고를 보존하고 TRIAL로 생성한다. 정상 판정은 생성기 사전 검사 범위이며 외부 신뢰 통과 의미가 아니다.

## 요청 식별과 중복 처리

관리 발행 요청에는 requestId(UUID), 기대 draftRevision, purpose 의도, 순번·시각 입력 및 시험용 override가 필요하다. 새 발행 버튼 동작마다 새 requestId를 만들고 같은 전송의 재시도에서는 유지한다. 포괄적인 REST 경로 변경은 이번 문서에서 정하지 않는다.

입력 digest는 명시적 요청 입력과 고정한 초안·baseline·프로파일·서명키 지문을 포함하는 버전 있는 결정적 직렬화로 계산한다. 최초에는 자동값을 해석한 고정 입력도 requests 기록에 저장한다. 재시도는 당시 자동값을 재사용하고 현재 시각이나 새 초안으로 다시 계산하지 않는다.

| 요청 상황 | 동작 |
|---|---|
| 같은 requestId·같은 명시 입력, 확정본 있음 | 저장된 결과 반환. 현재 draftRevision이 달라져도 기존 결과 반환 |
| 같은 requestId·다른 명시 입력 | REQUEST_CONFLICT. 기존 결과를 수정하지 않음 |
| 동일 요청 진행 중 | 진행 중 상태 반환. 중복 실행 금지 |
| 같은 requestId가 실패·중단으로 종결됨 | 기존 실패 결과 반환. 수정 후 새 시도는 새 requestId |
| 새 requestId | 새 생성 시도. 같은 순번도 새 issuanceId로 보관 가능 |

requestId 매핑은 세션 종료·재기동으로 지우지 않는다. 확정 발행본과 함께 유지한다. 이 설계는 중복 성공 방지 계약이며 실패한 모든 시도를 반드시 자동 재개한다는 뜻은 아니다.

## 확정 절차

1. 작성 잠금 아래 중복 요청을 먼저 조회한다. 신규 요청이면 revision을 확인하고 입력·프로파일·키 지문·issuanceId를 고정하여 요청 기록을 저장한다.
2. 후보 XML을 생성하고 파일 키로 서명한다. 실제 암호 서명 확인을 수행한다. 불가역한 의미 오류 교정은 하지 않는다.
3. staging에 XML·해시·스냅숏·manifest·프로파일을 쓰고 파일 기록을 완료한다.
4. 같은 파일 시스템의 issued/<issuanceId>로 원자 이동한다. 기존 issuanceId를 덮어쓰지 않는다.
5. BASELINE이면 새 초안 revision 파일을 미리 작성한다. 다음 state.json에 발행 확정·requestId 매핑과 baseline/초안/정상 sequence 변경을 한 번에 담는다. TRIAL이면 기준 관련 필드는 유지한다.
6. 임시 state 파일을 기록 완료한 후 기존 state.json을 원자 교체한다. **이 교체가 발행 확정 지점이다.** 메모리 읽기 스냅숏도 같은 상태로 전환한 뒤 성공을 반환한다.
7. requests의 진행 표시 갱신이 실패해도 state.json에서 확정 결과를 복구한다. 확정본을 지우거나 순번을 되돌리지 않는다.

상태 교체 지원 여부를 시작 시 점검하고, 지원하지 않는 파일 시스템에서 비원자 덮어쓰기로 조용히 대체하지 않는다. 지원 불가이면 관리 쓰기를 중단한다. Windows 파일 잠금·바이러스 검사 등으로 이동 실패 시 이전 상태를 유지하고 실패를 반환한다.

파일 기록 완료·원자 교체는 구현에서 파일 시스템 동작을 확인해야 한다. 프로세스 중단 복구를 목표로 하며 갑작스러운 전원 상실·디스크 고장까지 검증된 내구성이라고 주장하지 않는다.

## 장애 지점별 복구

| 장애 시점 | 재기동 처리 | 사용자 결과 |
|---|---|---|
| 서명 전/중 실패 | 요청을 FAILED로 종결, baseline·제공본 유지 | KEY_READ_FAILED / SIGNING_FAILED |
| 서명 자체 확인 실패 | 확정하지 않음 | SIGNATURE_CHECK_FAILED |
| staging 기록 실패 | 불완전 staging을 진단용 보존, 확정 목록 미반영 | STORAGE_FAILED |
| issued 이동 후 state 교체 전 중단 | 미확정 orphan으로 분류, 자동 제공·baseline 승격 금지 | INTERRUPTED, 새 requestId로 재시도 |
| state 교체 성공 후 응답 유실 | committed 매핑에서 기존 issuanceId 반환 | 동일 발행 성공 결과 |
| requests 진행 표시만 오래됨 | state 권위를 따라 표시 복구 | 중복 서명 없음 |
| 확정본 파일 누락/해시 불일치 | 손상 표시, 덮어쓰기·새 파일 자동 생성 금지 | 선택본이면 IF-07 503 |
| state 파일 해석/검증 실패 | 관리 쓰기 중단, 자동 최대 순번 선택 금지 | STATE_UNAVAILABLE |

기동 후 복구가 끝나기 전에는 발행·선택을 받지 않는다. 중단된 요청과 orphan은 자동 삭제하지 않으며 목록에 표시한다. 복구 가능한 정상 발행본을 관리자가 다시 선택하는 것은 새 발행이 아니다. 손상된 저장 상태의 수동 복원은 별도 운영 작업이고, 임의 파일을 정상본으로 간주하지 않는다.

## 제공본 선택과 읽기

선택 대상은 확정된 발행본이어야 하며 존재·해시를 확인한다. 의미 오류나 과거 순번은 선택 거부 사유가 아니다. 다음 state의 publicationRevision과 issuanceId만 바꾸고 원자 교체한다. 서명 XML은 손대지 않는다.

교체 전 실패하면 이전 제공본 유지, 교체 후 응답 유실이면 다시 상태를 읽어 실제 revision을 확인한다. 같은 기대 revision의 지연 요청으로 최신 선택을 덮어쓰지 않는다.

GET은 시작 시 하나의 상태 스냅숏과 issuanceId를 고정한다. 정상 제공 포인터가 없으면 404, state 손상·선택 파일 읽기 실패는 503이다. 운영 중 파일 손상 감지 시 신규 요청에는 503을 반환하고 정상본으로 자동 대체하지 않는다. 기존에 읽기 시작한 검증된 바이트 응답은 끝낼 수 있다.

XML GET과 해시 GET은 별개의 요청이므로 사이에 선택 변경이 가능하다. 한 요청 내부의 일관성은 보장하되 두 GET 전체를 하나의 트랜잭션으로 주장하지 않는다. 소비자는 불일치하면 재조회한다.

## 구현 검증과 인계

| 확인 항목 | 통과 기준 |
|---|---|
| 정상 발행·재기동 | 확정 ID·XML·해시·baseline·초안 revision 동일 |
| 큰 순번 오류 시험 | TRIAL만 추가되고 정상 권장값·이력 불변 |
| 응답 유실 후 재요청 | 같은 ID·바이트, 추가 서명 호출 없음 |
| 같은 ID 다른 입력 | 충돌, 기존 파일 불변 |
| 동시 편집·발행 | 오래된 revision 거부, 갱신 유실 없음 |
| 단계별 프로세스 중단 | state 교체 전에는 미확정, 교체 후에는 기존 성공 복구 |
| 제공본 변경·동시 GET | 각 응답 헤더·본문이 한 발행본에 대응 |
| 저장 손상 | 성공/유효 표시 금지, 503과 관리 진단 |
| 같은 키 인증서 갱신·단순 재발행 | 불필요한 서비스 이력 추가 없음 |

이 표는 실행할 기술 검증이다. 구현·중단 주입 시험·플랫폼의 원자 교체 검증은 아직 수행하지 않았다. 다중 작성자, 저장 매체 전원 장애 내구성, 자동 복원, 대량 발행 성능은 이번 단일 WAS PoC의 검증 범위에 포함하지 않는다.
