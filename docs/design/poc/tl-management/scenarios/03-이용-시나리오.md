# 03. 주체별 프로세스와 이용 시나리오

> 자료 분류: 기존 상세 설계·검토 자료. 현재 PoC 구현 범위는 [확정 범위](../scope.md)를 우선한다. 고정 시나리오·HSM·별도 WEB 등은 현재 필수 개발로 간주하지 않는다.

> TL을 여러 상황에서 관리해 보면서 **관리자 · 인증사업자 · 가입자 · 이용자 · 브라우저가 각각 어떻게 동작하고, 무엇을 검증해야 하는지**를 정리한다.
> PoC는 이 시나리오들을 실제로 돌려 보는 것으로 개념을 증명한다.
> **1차 설계 검토 반영 (2026-10-05):** 핵심은 인증서 체인을 고정하고 TL 등재 · 상태 · 보유 버전을 바꿔 **변경 전후 신뢰 경로와 시점별 판정**을 비교하는 것이다. 기대 판정의 기준은 [18 신뢰 경로 판정표](../../../common/kr-tl/18-신뢰경로-판정표.md). 관리자 인증 · 승인 분리 · 감사는 핵심 범위에서 뺀다.

## 1. 주체별 프로세스

### 1.1 관리자 (KISA)

```
신뢰정보 변경 발생 (사업자 제출 · 직권)
  → 입력 확정 (M-04)          확정 또는 반려
  → 상태 변경 (M-03)          효력 시각(KST) · 사유 기록 (소급 금지)
  → TL 발행 (M-05)            차이 확인 → 서명 → 반출
  → 결과 비교 (M-08)          변경 전후 신뢰 경로 · 이용환경 판정
  → 배포 확인 (M-06)          게시 성공 여부
  → 수신 확인 (M-07)          미수신 이용자 확인 · 안내
```

### 1.2 인증사업자

```
등록 신청 / 서비스 변경 / 상태 신고   ─ IF-01 (VPN · mTLS, 제출 내용 JSON)
주기적 갱신 제출 · 처리 결과 조회     ─ IF-01
```

### 1.3 가입자 (서명 주체)

```
인증서 발급 (CA) → 문서 전자서명 (KR-AdES, 서명 시각 기록) → 이용자에게 제출 (기존 서비스 채널)
```

- 가입자는 TL을 직접 다루지 않는다. 그러나 **TL 변경의 영향을 받는 쪽**이다. 자기 인증사업자가 정지되면 그 뒤에 한 서명은 거부된다.
- 서명에 기록된 서명 시각(KST)으로 판정하므로, 나중에 사업자가 정지·철회되어도 **그 이전 서명은 유효**하게 남는다. 이것이 가입자 측에서 PoC가 보여 줄 핵심이다. (PoC는 TSA로 서명 시각을 증명하지 않는다.)

### 1.4 이용자 (검증) — 검증 프로세스

```
[A] TL 확보
  A1  캐시된 TL이 있고 다음 발행 예정(NextUpdate) 전이면 → 버전 확인만 (IF-07, 변경 없으면 그대로)
  A2  새 버전이면 다운로드
  A3  TL 서명 검증 — TL 서명 인증서 → KISA TL CA → KISA TL RootCA(미리 보유한 신뢰 기준)까지 체인 확인
  A4  일련번호가 캐시보다 큰지 확인 (예전 TL로 되돌리기 공격 방지)
  A5  실패하면 새 TL을 버리고 캐시 유지 + 경보

[B] 전자서명 검증
  B1  서명값 · 문서 무결성 확인
  B2  서명자 인증서 → 발급 CA 인증서 체인 구성
  B3  체인의 CA 인증서가 TL의 서비스 인증서(D-04)와 일치하는지 → 없으면 "신뢰할 수 없는 발급자"
  B4  서명 시각 확인 — 서명에 기록된 서명 시각(KST). 없으면 판단 보류 (18 §1)
  B5  B4 시각에 해당 서비스의 TL 상태(D-03 이력) 확인
  B6  가입자 인증서 폐지 여부 확인 (OCSP·CRL — 기존 서비스 채널)
  B7  판정 + 근거 + 사용한 TL 버전 기록 (D-11)
```

| 조건 | 판정 |
|---|---|
| B1~B6 모두 정상, 서명 시각에 서비스가 granted | **PASSED** |
| 서명 시각에 서비스가 suspended·withdrawn, 또는 인증서 폐지, 서명값 불일치 | **FAILED** |
| 발급 CA가 TL에 없음, 서명 시각이 최초 인정 이전, 서명 시각 없음, TL이 기한 경과, 폐지 상태 확인 불가 | **INDETERMINATE** |

> 기한 지난 TL은 EU 기준대로 버린다. 경계 시각 · 최초 인정 이전 · 서명 시각 없음 규칙은 [18](../../../common/kr-tl/18-신뢰경로-판정표.md) §1.

### 1.5 브라우저 (웨일) — 서명된 결과 확인

```
TL 수신 (IF-07)        이용자와 같은 방식: 버전 확인 → 다운로드 → TL 서명 검증 → 일련번호 역행 거부
서명된 결과 수신 (IF-08) 이용자 시스템이 제공한 서명 문서·증명서
서명 결과 검증 요청 (IF-09) 가입자가 자기 서명 결과를 브라우저에서 확인
서명 검증             1.4의 [B] 절차와 같음 (인증서 상태 확인은 OCSP)
결과 표시             판정과 사용한 TL 버전을 사용자에게 보여 줌
```

- 이용자는 서비스를 처리하기 위해, 브라우저는 **결과를 받아 보는 사람의 입장**에서 검증한다.
- 같은 서명을 같은 TL 버전으로 검증하면 **이용자와 브라우저의 판정이 같아야 한다.** TL 버전이 다르면 판정이 달라질 수 있고, 그 차이가 TL 동기화의 중요성을 보여 준다.

## 2. 시나리오 목록

PoC 핵심 시연은 ★ 표시. 기대 판정은 [18 판정표](../../../common/kr-tl/18-신뢰경로-판정표.md) §5를 기준으로 한다.

| ID | 시나리오 | 무엇을 증명하는가 |
|---|---|---|
| ★SC-01 | 신규 사업자 등재 | TL에 실려야만 신뢰된다 |
| SC-02 | 서비스 인증서 갱신 | 신·구 인증서 공존 기간에도 검증이 끊기지 않는다 |
| ★SC-03 | 서비스 정지 (긴급 발행) | 정지가 시점까지 정확히 반영된다 |
| ★SC-04 | 정지 해제 | 이력이 남은 채로 다시 신뢰된다 |
| ★SC-05 | 인정 철회 | 철회 이후만 무효, 이전 서명은 유효 |
| ★SC-06 | 이용자·브라우저 동기화와 미수신 추적 | 관리자가 반영 범위를 확인할 수 있다 |
| SC-07 | TL 기한 경과 | 갱신이 멈추면 이용자가 알아챈다 |
| ★SC-08 (보조) | 배포된 TL 변조 · 이전 버전 | 배포 시스템이 뚫려도 위조 TL은 통하지 않는다 |
| SC-09 | TL 서명키 교체 | 서명키를 바꿔도 이용자·브라우저의 신뢰 기준(KISA TL RootCA)은 그대로다 |
| SC-10 | 관리·배포 시스템 장애 | 한쪽이 멈춰도 검증은 계속된다 |
| SC-11 | 내부 통제 (**핵심 범위 제외**) | 승인 분리 · 감사 — 후속 범위 |
| SC-12 | 잘못된 제출 반려 | 검증되지 않은 정보는 TL에 들어가지 않는다 |

## 3. 시나리오 상세

공통 준비: 인증서 체인은 고정 — 가상공동인증A CA(JA-01) → 가입자 U. 이용자 R(KR-DSS SDK), 웨일 브라우저. TL #1~#5, 서명 표본 S0 · S1 · SB · S2 · S3 · S4 ([18](../../../common/kr-tl/18-신뢰경로-판정표.md) §3 · §4).

### ★SC-01 신규 사업자 등재

| 단계 | 조작 | 이용자 |
|---|---|---|
| 1 | 이용자가 **TL #1 (JA 미등재)** 보유 | 표본 S1 검증 → **보류 · `NOT_IN_TL`** (체인은 있으나 TL 신뢰점에 닿지 않음) |
| 2 | JA 등재 확정 → **TL #2** 발행 (인정 효력 t1 = 11-02T10:00+09:00) → 이용자 동기화 | — |
| 3 | 같은 S1 다시 검증 | **통과** (신뢰점 JA-01) |

**시간 조건:** S1의 서명 시각(11-02T15:00)은 최초 인정 효력 시각(t1) 이후다. t1 이전 서명(S0)은 등재 뒤에도 **보류 · `NOT_ACCREDITED_AT_TIME`** 이다.

**검증 포인트**: 같은 서명이 TL 등재 전후로 판정이 바뀐다 · 검증 결과에 사용한 TL 버전(#1/#2)이 남는다.

### SC-02 서비스 인증서 갱신

| 단계 | 관리자 | 인증사업자 | 가입자 | 이용자 |
|---|---|---|---|---|
| 1 | | CA-A 키 교체 — 새 CA 인증서 제출 | | |
| 2 | 확정 → 다음 TL에 **새 CA를 새 서비스로** 등재 (구 CA 서비스는 유지) | 새 CA로 발급 시작 | U(구 CA)·U2(신 CA) 각각 서명 | 둘 다 **PASSED** |
| 3 | 구 CA 운영 종료 → 구 서비스 철회 (#44), 이력 유지 | | | 철회 이전 서명은 이력으로 판정 |
| (참고) | 키는 그대로 두고 인증서만 갱신 → 같은 서비스에 인증서 추가, 이력 없음 | | | |

**검증 포인트**: 키가 바뀌면 새 서비스, 인증서만 바뀌면 같은 서비스 (EU G.4와 같음, [12](../../../common/kr-tl/12-상태-이력-모델.md) §2.3) · 갱신 기간에 검증 중단 없음.

### ★SC-03 서비스 정지 (긴급 발행)

| 단계 | 조작 | 이용자 (TL #3 수신 후) |
|---|---|---|
| 1 | JA 정지 입력, 효력 t2 = 11-03T10:00+09:00, 즉시 발행 → **TL #3** | — |
| 2 | 표본 검증 | S1 **통과** · SB(t2와 같은 시각) **실패** · S2 **실패** (`SERVICE_SUSPENDED_AT_TIME`) |
| 3 | TL #2에 머문 이용환경 | S2를 **통과**로 판정 — 동기화가 필요한 이유 (SC-06) |

**검증 포인트**: 서명 시각 기준 판정(이력 기반) · 경계 시각은 새 상태 적용 · 즉시 발행이 정기 주기와 무관하게 나간다.

### ★SC-04 정지 해제

| 단계 | 조작 | 이용자 (TL #4 수신 후) |
|---|---|---|
| 1 | JA 복원, 효력 t3 = 11-04T10:00+09:00 → **TL #4** | — |
| 2 | 표본 검증 | S2 여전히 **실패** · S3 **통과** |

**검증 포인트**: 복원해도 정지 구간 이력이 지워지지 않는다 (인정 → 정지 → 인정).

### ★SC-05 인정 철회

| 단계 | 조작 | 이용자 (TL #5 수신 후) |
|---|---|---|
| 1 | JA 철회, 효력 t4 = 11-05T10:00+09:00 → **TL #5** | — |
| 2 | 표본 검증 | S1 · S3 **통과** · S2 **실패(정지 구간)** · S4 **실패 · `SERVICE_WITHDRAWN_AT_TIME`** |

**검증 포인트**: 철회 이전 인정 구간의 서명은 계속 유효하다 — TL #5 한 버전 안에서 구간별로 판정이 갈린다.

### ★SC-06 이용자·브라우저 동기화와 미수신 추적

| 단계 | 관리자 | 이용자 |
|---|---|---|
| 1 | TL #3 발행 | 이용자는 #3 수신, 웨일은 아직 #2 |
| 1a | 같은 표본 S2 검증 | 이용자 **실패** / 웨일 **통과** — 차이는 체인이 아니라 TL 버전에서 생김 |
| 1b | 웨일 동기화 후 다시 검증 | 둘 다 **실패** — 같은 서명 · 같은 TL · 같은 정책이면 같은 판정 |
| 2 | | R1은 변경 감지 → 다운로드 / 변경 없을 때는 버전 확인만 (트래픽 최소) |
| 3 | M-07: 이용자별 최신·미수신, 브라우저 수신 건수·버전 분포 표시 | |

**검증 포인트**: 변경 없을 때 다운로드하지 않음 · 배포 WAS에 접속 기록이 남고 수신 현황(M-07)에 나타남

### SC-07 TL 기한 경과

| 단계 | 관리자 | 이용자 |
|---|---|---|
| 1 | 발행 중단 (장애 가정), 보유 TL의 NextUpdate 경과 | |
| 2 | | 동기화 시도 → 새 버전 없음 → 캐시 TL 기한 경과 → **TL을 버림** → 유효한 TL이 없으므로 **INDETERMINATE** + 경보 (EU 기준) |

**검증 포인트**: 오래된 TL을 조용히 계속 쓰지 않는다.

### ★SC-08 배포된 TL 변조

| 단계 | 공격 | 이용자 |
|---|---|---|
| 1 | 배포 WAS에 보관된 TL에서 철회된 CA를 granted로 고쳐 놓음 | |
| 2 | | 이용자·브라우저 모두: 다운로드 → TL 서명 검증 실패 → 새 TL 버리고 캐시 유지 + 경보 |
| 3 | 예전 버전(#40)을 최신인 것처럼 게시 | 일련번호 역행 → 거부 |

**검증 포인트**: 배포 시스템에는 서명키가 없으므로 위조 불가 · 되돌리기 공격 차단.

### SC-09 TL 서명키 교체

| 단계 | 관리자 | 이용자·브라우저 |
|---|---|---|
| 1 | HSM에서 새 서명키 생성 → KISA CA가 새 TL 서명 인증서 발급 | |
| 2 | 새 키로 #50 서명, 새 인증서 체인을 TL에 실음 | 체인을 KISA TL RootCA까지 확인 → #50 검증 성공 (신뢰 기준 변경 없음) |
| 3 | 구 TL 서명 인증서 폐기 | 구 인증서로 서명된 새 TL이 오면 거부 |
| 4 | (대조) KISA CA가 발급하지 않은 인증서로 서명한 TL | 체인이 Root CA에 닿지 않아 거부 |

**검증 포인트**: 서명키 교체가 이용자 쪽 설정 변경 없이 끝난다 · KISA 인증체계 밖의 인증서로 서명한 TL은 통하지 않는다.

### SC-10 관리·배포 시스템 장애

| 상황 | 기대 동작 |
|---|---|
| 관리 시스템 중지 | 배포 시스템은 마지막 TL 계속 제공, 이용자 검증 정상 |
| 배포 시스템 중지 | 이용자는 캐시 TL로 NextUpdate까지 검증, 이후 SC-07 |
| 반출 중 끊김 | 재반출 시 같은 버전은 한 번만 게시 |

### SC-11 내부 통제 — 핵심 범위 제외

1차 설계 검토에 따라 승인 분리(작성자 ≠ 승인자)와 감사 기록 무결성은 PoC 핵심 범위에서 뺀다. 운영 단계의 후속 범위로 둔다.

### SC-12 잘못된 제출 반려

| 단계 | 인증사업자 | 관리자 |
|---|---|---|
| 1 | 형식이 맞지 않는 제출 / 등록되지 않은 사업자 인증서로 제출 | 사업자 연계에서 즉시 반려, 심사 대기에 올라가지 않음 |
| 2 | 정상 제출이라도 | 심사 대기로만 등록, TL 자동 반영 없음 |

## 4. 시나리오별로 필요한 기능 (요약)
