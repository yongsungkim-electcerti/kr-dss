# 14. 메타데이터 정의와 실제 데이터 (D3-6 · D3-8)

> 자료 분류: 기존 상세 설계·검토 자료. 현재 PoC 구현 범위는 [확정 범위](../scope.md)를 우선한다. 고정 시나리오·HSM·별도 WEB 등은 현재 필수 개발로 간주하지 않는다.

> [13 데이터 변환](../../../common/kr-tl/13-데이터-변환-설계.md) §3 대응표를 기준으로 폴더 메타데이터 파일을 정의하고, PoC에서 쓸 실제 값을 정한다.
> 정해지지 않은 값은 **PoC 값으로 임의 설정**한다. 모든 이름·번호·OID는 가상이다.

## 1. 식별 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| 사업자 ID | 영문 대문자 2~6자 | `JA`, `SA`, `KISA-TL` |
| 인증서 ID | `<사업자>-<번호>` | `JA-01`, `SA-00`, `T-02` |
| 폴더 이름 | `<인증서 ID>-<유형>` | `JA-01-ca`, `SA-03-tsa` |
| 서비스 ID | 인증서 ID와 같음 (키가 바뀌면 새 ID) | `JA-01`, 키 교체 후 `JA-04` |
| URI 접두어 (PoC) | `urn:kr:krtl:` | `urn:kr:krtl:svcstatus:accredited` |
| OID 접두어 (PoC) | `2.999.1` — ITU-T 예시용 OID 영역 | `2.999.1.1.1` |

`2.999`는 문서·예시용으로 예약된 OID 영역이라 실제 OID와 겹치지 않는다.

## 3. 메타데이터 파일 정의

### 3.1 `krtl/scheme.json` — 발행 설정 (관리 시스템)

| 항목 | 값 (PoC) | TL 요소 |
|---|---|---|
| `operatorName` | 한국인터넷진흥원 (KISA) | SchemeOperatorName |
| `schemeName` | KR-TL 전자서명 신뢰목록 (PoC) | SchemeName |
| `schemeInfoUri` | `https://krtl.example.kr/scheme` | SchemeInformationURI |
| `tslType` | `…/TSLType/KRlist` | TSLType |
| `territory` | `KR` | SchemeTerritory |
| `schemeRules` | 전자서명법 · 전자서명인증사업자 인정제도 | SchemeTypeCommunityRules |
| `statusApproach` | 인정평가 결과 반영 | StatusDeterminationApproach |
| `policyNotice` | PoC 고지 문구 | PolicyOrLegalNotice |
| `historicalPeriod` | `65535` | HistoricalInformationPeriod |
| `pointers` | `[{ operator: "KISA", uri: null }]` | PointersToOtherTSL |
| `distributionPoints` | `["https://krtl.example.kr/tl/v1/latest"]` | DistributionPoints |
| `nextUpdateDays` | `7` | NextUpdate 계산 |
| `lastSequence` | 발행할 때마다 +1 | TSLSequenceNumber |

### 3.2 `provider.json` — 사업자 정보

| 항목 | 설명 | TL 요소 |
|---|---|---|
| `providerId` | 사업자 ID | — |
| `name` · `tradeName` | 이름 · 상호 | TSPName · TSPTradeName |
| `address` · `infoUri` | 주소 · 정보 URI | TSPAddress · TSPInformationURI |
| `accreditation` | `{ number, date, scope, uri }` — PoC 임의 값 | TSP 정보 확장 |
| `anchorLevel` | 0 또는 1 — 이 사업자 CA 서비스의 신뢰점 레벨 | 서비스 확장으로 복사 |

### 3.3 `meta.json` — 인증서 (인증기관 PoC `pki/`)

| 항목 | 설명 |
|---|---|
| `id` · `name` | 인증서 ID · 이름 |
| `type` | `root` · `ca` · `ocsp` · `tsa` · `tl-signer` · `subscriber` |
| `issuerId` | 발급자 인증서 ID (Root는 자기 자신) |
| `providerId` | 사업자 ID |
| `tlListed` | TL 등재 대상 여부 — 신뢰점 레벨에 따라 결정 (§4.3) |
| `fingerprint` | SHA-256 지문 |
| `status` | `active` · `revoked` (인증서 자체 상태 — TL 상태와 별개) |

### 3.4 `service.json` — 등재 서비스 (관리 시스템 `krtl/registry/`)

| 항목 | 설명 | TL 요소 |
|---|---|---|
| `serviceId` | 서비스 ID | — |
| `serviceType` | 서비스 유형 URI | ServiceTypeIdentifier |
| `serviceName` | 서비스 이름 (한글) | ServiceName |
| `digitalIds` | 같은 공개키의 인증서 파일 목록 + SKI | ServiceDigitalIdentity |
| `status` · `statusStartingTime` | 현재 상태 · 효력 시각 (TL 발행 시각 이후만) | ServiceStatus · StatusStartingTime |
| `history[]` | `{ status, startingTime, serviceType, serviceName, ski, reason }` 최신순, 지우지 않음 | ServiceHistory |
| `domain` | 신뢰 분야 URI | additionalServiceInformation |
| `anchorLevel` | CA 서비스만. 0 또는 1 | additionalServiceInformation |
| `suspendReason` | 정지 상태일 때 사유 | additionalServiceInformation |

## 4. 실제 데이터 (PoC)

### 4.1 사업자

| ID | 이름 | 신뢰 분야 | 신뢰점 레벨 | 인정 번호 (임의) | 인정 일자 (임의) |
|---|---|---|---|---|---|
| `KISA-TL` | KISA (TL 서명 체계) | — | — | — | — |
| `KISA-J` | KISA (공동인증 최상위) | 공동인증 | — | — | — |
| `JA` | 가상공동인증A | 공동인증 | **1** | KR-ACC-0001 | 2026-10-10 |
| `JB` | 가상공동인증B | 공동인증 | **1** | KR-ACC-0002 | 2026-10-10 |
| `SA` | 가상간편인증A | 간편인증 | **0** | KR-ACC-0003 | 2026-10-10 |
| `SB` | 가상간편인증B | 간편인증 | **1** | KR-ACC-0004 | 2026-10-10 |

- 공동인증 사업자는 레벨 1로 둔다. 사업자마다 CA를 따로 등재해야 JA만 정지하는 식으로 **사업자별 상태 관리**가 가능하기 때문이다.
- 간편인증은 SA를 레벨 0, SB를 레벨 1로 둬서 **두 레벨을 모두 시연**한다.

### 4.2 인증서

| ID | 주체 DN | 발급자 | 프로파일 | 키 · 유효기간 (PoC) |
|---|---|---|---|---|
| T-00 | `CN=KISA TL RootCA, O=KISA, C=KR` | 자기 자신 | Root | EC P-256 · 20년 |
| T-01 | `CN=KISA TL CA, O=KISA, C=KR` | T-00 | CA | EC P-256 · 10년 |
| T-02 | `CN=KISA TL Signer, O=KISA, C=KR` | T-01 | TL 서명 | EC P-256 · 3년 |
| K-00 | `CN=KISA RootCA, O=KISA, C=KR` | 자기 자신 | Root | EC P-256 · 20년 |
| JA-01 | `CN=가상공동인증A CA, O=가상공동인증A, C=KR` | K-00 | CA | EC P-256 · 10년 |
| JA-02 | `CN=가상공동인증A OCSP, O=가상공동인증A, C=KR` | JA-01 | OCSP | EC P-256 · 3년 |
| JA-03 | `CN=가상공동인증A TSA, O=가상공동인증A, C=KR` | JA-01 | TSA | EC P-256 · 3년 |
| JB-01~03 | 가상공동인증B — JA와 같은 형식 | K-00 / JB-01 | CA · OCSP · TSA | 같음 |
| SA-00 | `CN=가상간편인증A RootCA, O=가상간편인증A, C=KR` | 자기 자신 | Root | EC P-256 · 20년 |
| SA-01~03 | 가상간편인증A CA · OCSP · TSA | SA-00 / SA-01 | CA · OCSP · TSA | 같음 |
| SB-00 | `CN=가상간편인증B RootCA, O=가상간편인증B, C=KR` | 자기 자신 | Root | EC P-256 · 20년 |
| SB-01~03 | 가상간편인증B CA · OCSP · TSA | SB-00 / SB-01 | CA · OCSP · TSA | 같음 |
| xx-EE | 개인 `CN=<성명>, serialNumber=<가상번호>` / 법인 `CN=<법인명>, O=<법인명>, OU=<가상 사업자번호>` | 각 사업자 CA | 가입자 (정책 OID `2.999.1.1.1` / `.2`) | EC P-256 · 2년 |

- 키 · 유효기간은 `krdss-cli cert` 기본값(EC P-256)을 따른 PoC 값이다.

### 4.3 TL 등재 결과 (신뢰점 레벨 적용)

| TSP | 등재 서비스 | 인증서 | 서비스 유형 | 레벨 |
|---|---|---|---|---|
| 가상공동인증A | 인증서 발급 · 상태 확인 · 시점확인 | JA-01 · JA-02 · JA-03 | CA · OCSP · TSA | CA = 1 |
| 가상공동인증B | 인증서 발급 · 상태 확인 · 시점확인 | JB-01 · JB-02 · JB-03 | CA · OCSP · TSA | CA = 1 |
| 가상간편인증A | 인증서 발급 (Root) | **SA-00 하나** | CA | 0 |
| 가상간편인증B | 인증서 발급 · 상태 확인 · 시점확인 | SB-01 · SB-02 · SB-03 | CA · OCSP · TSA | CA = 1 |

합계: TSP 4 · 서비스 10

가상미등재사업자(UN-00~03)는 TL 미등재 대조군으로 키 체인만 만들고 위 등재 목록에 넣지 않는다([27](../pki/27-PoC-키파일-디렉터리-설계.md) §1).

**레벨 0은 RootCA 하나만 등재한다** (2026-10-05 결정). Root가 검증의 끝이므로, Root 아래 CA · OCSP · TSA 인증서는 모두 Root까지의 체인으로 확인한다. 레벨 1은 CA · OCSP · TSA를 각각 등재한다.

**등재 규칙 — 한 체인에는 신뢰점이 하나다.** 같은 체인에서 상위(Root)와 하위(CA)를 동시에 CA 서비스로 등재하지 않는다. 상위 Root가 인정 상태로 남아 있으면 하위 CA를 정지해도 Root까지 올라가 검증이 통과될 수 있기 때문이다.

- 그래서 공동인증 사업자를 레벨 1로 등재하면 **KISA RootCA(K-00)는 등재하지 않는다.** `국가 지정` 상태는 정의만 두고 PoC에서는 쓰지 않는다.
- 이 결과 [07 인증체계](../../../common/trust-framework/07-인증체계-설계.md) §7의 등재 목록(TSP 5 · 15장)은 위 표(TSP 4 · 서비스 10)로 바뀐다.

## 5. 인증서 구축 명세

### 5.1 구축 명세 형식 (안) — `pki-build.json`

체인을 Tree로 적고, 폴더(`pki/`)와 `meta.json`을 한 번에 만든다.

```json
{
  "outDir": "pki",
  "keyAlg": "EC", "keySize": 256,
  "nodes": [
    { "id": "T-00", "type": "root", "provider": "KISA-TL", "subject": "CN=KISA TL RootCA,O=KISA,C=KR", "days": 7300,
      "children": [
        { "id": "T-01", "type": "ca", "subject": "CN=KISA TL CA,O=KISA,C=KR", "days": 3650,
          "children": [ { "id": "T-02", "type": "tl-signer", "subject": "CN=KISA TL Signer,O=KISA,C=KR", "days": 1095 } ] } ] },
    { "id": "K-00", "type": "root", "provider": "KISA-J", "subject": "CN=KISA RootCA,O=KISA,C=KR", "days": 7300,
      "children": [
        { "id": "JA-01", "type": "ca", "provider": "JA", "subject": "CN=가상공동인증A CA,O=가상공동인증A,C=KR", "tlListed": true,
          "children": [
            { "id": "JA-02", "type": "ocsp", "subject": "CN=가상공동인증A OCSP,O=가상공동인증A,C=KR", "tlListed": true },
            { "id": "JA-03", "type": "tsa",  "subject": "CN=가상공동인증A TSA,O=가상공동인증A,C=KR", "tlListed": true } ] }
        /* JB-01 … 같은 형식 */ ] }
    /* SA-00 (tlListed: true, 레벨 0) → SA-01 · SA-02 · SA-03 (tlListed: false — Root 체인으로 확인) */
    /* SB-00 (tlListed: false)        → SB-01 (tlListed: true, 레벨 1) → SB-02 · SB-03 */
  ]
}
```

### 5.2 현재 도구와의 차이

현재 `krdss-cli cert chain`은 Root → Sub → EE **한 줄 체인**만 만들고, 출력도 `<이름>.crt` · `<이름>.key` 파일이다. 위 명세를 처리하려면 아래 기능이 더 필요하다 (D3-7 · D10 구현 범위).

| 필요 기능 | 내용 |
|---|---|
| Tree 구축 | 한 Root 아래 여러 CA, CA 아래 OCSP · TSA |
| 유형별 프로파일 | OCSP(EKU OCSPSigning), TSA(EKU timeStamping, critical), TL 서명(EKU tslSigning) |
| 폴더 출력 | `<ID>-<유형>/cert.pem · key.pem · meta.json` |
| 정책 OID | 가입자 인증서에 `2.999.1.1.x` |

## 6. 인증기관 PoC 화면 항목 (07 §11 상세)

|---|---|
