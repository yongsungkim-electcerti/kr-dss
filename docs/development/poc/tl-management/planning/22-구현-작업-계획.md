# 22. 구현 작업 계획 (D10 · 검토 우선 작업 5)

> 자료 분류: 기존 상세 설계·검토 자료. 현재 PoC 구현 범위는 [확정 범위](../../../../design/poc/tl-management/scope.md)를 우선한다. 고정 시나리오·HSM·별도 WEB 등은 현재 필수 개발로 간주하지 않는다.

> **2026-10-07 범위 결정:** 이 문서는 이전 작업 분해 이력이다. 실제 착수에는 [25의 확정된 PoC 범위](../reviews/25-PoC-구현-차이-검토.md#3-확정된-poc-범위)를 우선 적용한다. 인증·감사와 HSM 연계는 제외하고 키 파일로 서명한다. 접수·심사·보완·반려는 메뉴만 제공하며, 최신 IF-01~08 및 Spring Boot WAS만 구현한다(별도 WEB 제외). 아래 mTLS 제출, 고정 표본, 시험 시계, R1~R6, 비교·초기화 도구를 현재의 필수 작업으로 해석하지 않는다. PoC 시나리오는 향후 결정한다.

> 1차 설계 검토([16](../reviews/16-설계-보완사항-조치목록.md)) §5 우선 작업 5 — D10.
> **완료 기준:** 작업마다 모듈 · 선행 작업 · 검증할 판정표 칸이 정해져, 이 목록만 보고 브랜치를 나눠 시작할 수 있다.
> 범위는 [20](../../../../design/poc/tl-management/scenarios/20-시험데이터-비교화면.md)의 R1~R6을 돌리는 데 필요한 것만이다. 운영 시스템 요건은 넣지 않는다.

## 0. 미결 항목 (논의 후 결정)

| # | 항목 | 영향 작업 |
|---|---|---|
| 1 | 이용환경 판정 결과(D-11)를 M-08로 모으는 방법 | W-06 · W-09 · W-10 |

| 3 | 에이전트별 작업 분담 · 브랜치 | 전체 (§4) |

- 웨일은 **크롬 확장으로 우선 대체**한다 (W-10). 웨일 탑재는 범위 밖.
- 확장은 TL을 쓰는 부분만 한다. PDF 서명 값 · 문서 무결성 검증은 웨일의 역할이므로 확장이 직접 하지 않는다. 확장의 입력은 W-01이 만든 표본 정보(서명자 체인 · 서명 시각)이고, 사유 코드 중 `SIGNATURE_INVALID` · `CERT_REVOKED` · `REVOCATION_UNAVAILABLE`은 확장에서 나오지 않는다.

## 2. 선후 관계와 단계

```
단계 A  W-12 ─┐
              ├─ W-01 ─────────────────────────────┐
단계 B  W-02 ─┼─ W-03 ─┐                          │
              └─ W-04 ─┴─ W-05                     │
단계 C          W-06(W-03) · W-07(W-03) · W-08(W-01) · W-09(W-04 · W-05)
단계 D          W-10(W-07 · W-05 규칙) · W-11(W-01 · W-06 · W-07)
```

| 단계 | 끝나면 할 수 있는 것 |
|---|---|
| A | 체인 3종 · 표본 9개가 고정된다 (20 §1) |
| B | 라이브러리 수준에서 TL #1~#5를 만들고 표본을 판정한다 — **18 판정표를 단위 시험으로 재현** |
| C | 관리 → 배포 → 이용기관으로 R1~R5 (확장 제외) |
| D | 확장 포함 R1~R6 전체, 초기화 · 재실행 |

- W-05는 Java(이용기관)와 JS(확장) 두 구현이 같은 규칙을 따라야 한다. 판정 규칙의 **공통 시험 벡터**(표본 × TL → 판정 · 사유)를 W-05에서 만들어 W-10이 같은 벡터로 시험한다.

## 4. 분담 원칙 (배정은 논의 후 결정)

- 한 작업 = 한 브랜치(`feat/<agent>-krtl-w<번호>-<주제>`), 모듈 단위 점유 (AGENTS.md 4.2 · 4.3).
- 같은 모듈을 쓰는 작업은 같은 에이전트에 묶는다: W-02 · W-03 · W-04 (`kr-tl`), W-06 · W-07.
- W-12는 단계 A 시작 직후 단독으로 먼저 병합한다.

## 5. 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 표본 정보와 실제 PDF의 불일치 | 확장 · 이용기관 판정 차이 | 표본 정보는 W-01이 PDF에서 추출해 함께 만든다. 이용기관 판정의 체인 · 서명 시각과 대조 |
| 확장의 XAdES(TL 서명) 검증 | W-10 | xadesjs 등. TL 하나 · 형식 고정이라 범위가 좁다 |
| EU DSS가 KR-TL을 EU TL로 해석 | W-03 · W-05 | TL 검증은 서명 검증만 DSS로, 상태 판정은 W-05가 직접 한다 |
| 시험 시계가 모듈마다 다름 | 판정 불일치 | 미결 2번 결정 시 한 방식으로 통일 |
| 인증서 재생성 | 기대 결과 깨짐 | W-01 산출물을 한 번 만들고 고정 (21 §2) |

## 6. 범위 밖

관리자 인증 · 역할 · 승인 분리 · 감사 기록 무결성, HSM 연동(키 파일 사용), TSA, 사업자 제출 화면의 운영 수준 검증, 웨일 탑재, 다국어 변환기, 정기 발행 스케줄러, 접속 통계.

## 7. 착수 전 확인

- `kr-dss-trust`의 기존 클래스(장치 신뢰목록 · Attestation)는 1차 범위 밖이다 — W-05는 별도 패키지로 추가하고 기존 것은 건드리지 않는다.
- `KrTrustListXmlSigner`는 `poc-relying-party`에 있다. W-03으로 옮길 때 이용기관 쪽 참조를 함께 바꾼다.
- 시작 전 `git fetch origin && git rebase origin/main`, 커밋 전 `./gradlew build` (AGENTS.md 4.4).
