# 30. 수정 개념 설계 v02의 TL 관리 PoC 영향 검토

검토일: 2026-10-09. 코드 기준: `9e4117ffe36a82efae634ad23ae7fee958b5eb27`(main 병합본).
상태: 설계·구현 차이 검토. 아래 제안은 제품 코드에 적용하지 않았다.

## 1. 결론

TL 관리 PoC의 기본 개발 방향은 유지할 수 있다. 개정안의 서비스 단위 관리, 상태 이력, 키 교체, 서명된 XML 보관은 기존 상세 설계 26~28과 대부분 일치한다. 다만 **운영 배포 정책과 오류 TL 시험 정책을 구별하고, 실제 발행 처리와 화면의 성공 표시를 연결해야 한다.**

가장 중요한 설계 차이는 개념 설계 §4.4.1의 WAS 게시 거부 정책이다. 기존 PoC는 낮은 순번·동일 순번 다른 내용·잘못된 시각의 TL도 정상 키로 서명하여 제공하도록 확정했다. 운영 정책을 그대로 적용하면 이 시험 기능이 막힌다. 기존 사용자 결정을 유지하고 PoC의 의도적인 예외를 문서·화면에 명시하는 것이 권고안이다.

현재 코드에 필요한 수정의 상당수는 개정안 때문에 새로 발생한 작업이 아니라, 이미 계획했으나 구현되지 않은 작업이다. 접수·심사 업무, HSM, 별도 WEB, 관리자 권한·감사, IF-08 검증기 개발을 이번 범위에 추가할 근거로 해석하지 않는다.

### 3.1 운영 게시와 PoC 오류 제공

개정안의 정상 게시 규칙은 큰 순번 채택, 동일 순번·동일 내용 재전송 수용, 동일 순번·다른 내용 및 낮은 순번 거부다. 반면 현 PoC는 수신 검증기가 바로 이 오류를 판별할 수 있도록 원본을 제공해야 한다.

권고 문구:

> 이 PoC의 WAS는 관리자가 선택한 발행본을 제공한다. 순번·시각 등 의미 오류가 있는 발행본도 시험 목적으로 제공할 수 있다. 이는 목표 운영 시스템의 공식 게시 수용 정책과 다른 PoC 예외다. 관리 화면의 생성 성공과 외부 검증기의 채택 성공은 구별한다.

별도 WEB이나 별도 포트를 새로 만들 필요는 없다. 정상 권장값과 의미 오류 경고를 표시하되, 현재 합의된 오류 발행·선택 기능을 유지한다. 암호 서명 실패·키 읽기 실패·파일 저장 실패는 의미 오류와 다르므로 정상 발행 성공으로 처리하지 않는다. 변조된 서명 자체의 생성 기능은 현 확정 범위가 아니다.

‘일련번호별 보관’이라는 개념 표현 때문에 순번을 물리 저장소의 유일 키로 바꾸면 안 된다. 같은 번호의 두 내용을 비교하려면 기존 issuanceId 구조가 필요하다.

### 3.2 순번 확정과 실패 복구

개정안은 서명 성공 때 번호를 확정하고 배포 재시도에는 동일 번호·서명본을 사용한다고 정의한다. 실제 프로그램에서는 파일 저장 성공까지 연결해야 재기동 후 확정 결과를 찾을 수 있다.

권고 구현 순서:

1. 초안 복사본과 요청 식별자를 고정하고 권장 순번·시각을 제시한다.
2. 입력값으로 XML 생성·서명 후 암호 서명을 확인한다.
3. XML·해시·메타데이터를 임시 위치에 기록하고 issuanceId 발행본을 원자적으로 확정한다.
4. 저장된 발행 결과를 반환한다. 응답 유실 후 동일 요청 재시도는 기존 발행본을 반환한다.
5. 제공본 선택은 별도 처리한다. 제공 실패가 새 서명이나 순번 증가를 유발하지 않게 한다.

서명은 성공했으나 저장은 실패한 경우 완료된 발행본으로 노출하지 않는다. 시도 기록과 확정 번호의 처리 방식을 상세 설계에 적어야 한다. 정상 권장 순번 관리와 오류 시험용 직접 입력값도 구별한다.

### 3.3 서비스 데이터와 상태 URI

개정안 §4.3.4의 같은 키·주체 인증서 갱신, 새 키의 새 서비스 등록은 상세 설계 26과 일치한다. 새 요구로 다시 설계하기보다 기존 작업을 구현한다.

현재 XML 파서는 알 수 없는 상태 URI를 WITHDRAWN으로 치환한다. 이는 ‘해석 불가’와 ‘철회 확인’을 섞으므로 수정해야 한다. 원 URI를 보존하고 명시적 프로파일 매핑을 적용한다. 개념 설계의 accredited 단어를 근거로 XML URI를 단순 문자열 치환하거나, 기존 granted를 국내 공표 URI라고 단정하지 않는다.

그림 5에 있는 운영자·체계명·관할·정보 URI·이력 보존 기간과 사업자 주소 등도 XML 필드 매핑표에 포함해야 한다. 그림의 ‘인정 정보(PoC 임의 값)’만으로 접수·심사 workflow를 추가하지 않는다. 미정인 다른 TL 포인터나 공표 URI를 가짜 운영값으로 채우지 않는다.

## 5. 개념 설계 자체의 보완점

1. **PoC 적용표 추가:** 전체 운영 설계와 이번 PoC의 구현·대체·제외를 한 표로 연결한다. 특히 §4.4.1의 게시 거부 규칙에 PoC 예외를 표시한다.
2. **신뢰점 레벨 표현 통일:** §3.3.2는 레벨을 CA 서비스에 적용한다고 명시하지만 그림 3은 CA·OCSP·TSA 묶음에 ‘레벨 1’을 붙이고 §4.5.4도 레벨별 OCSP/TSA 검증을 설명한다. 서비스의 CA 레벨 필드와 서비스군의 등재 방식 설명을 구별해야 한다. 권고: CA 서비스만 ROOT/CA 레벨을 갖고, OCSP/TSA는 직접 등재 또는 등재 RootCA와의 연결 정책으로 설명한다. 확정 전 모든 서비스에 동일 level 값을 강제하지 않는다.
3. **상태 URI·확장 명세 연결:** accredited/suspended/withdrawn의 업무 의미와 XML URI·critical 확장·공동/간편 분야 매핑을 별도 프로파일 표로 연결한다.
4. **‘같은 내용’ 정의:** 게시 충돌 판단은 저장된 최종 서명 XML의 바이트/SHA-256 기준으로 명시한다. 같은 XML 데이터에 새로 서명한 결과가 동일 재전송이라고 가정하지 않는다.
5. **주기 조회의 비교 위치 명확화:** §4.4.2의 순번 비교는 이용환경이 수행하는 수용 판단이다. IF-07 ETag/304와 병행하며 순번만 보고 교체하지 않는다. 관리 PoC에 수신 검증 API를 새로 만들 필요는 없다.
6. **NextUpdate까지 재발행의 책임 명확화:** 요구 자체는 확인되나 무인 자동 발행까지 명시한 것은 아니다. 이번에는 기한 표시·수동 재발행을 우선하고 자동화 여부를 별도 결정한다.
7. **서명 설명 교정:** §3.3의 ‘XML 형식으로 구성(XAdES)’은 XML 데이터 형식과 XAdES 서명을 구별해 표현한다. 그림 5의 ‘서명 인증서 신뢰(KISA TL RootCA)’는 RootCA가 직접 TL에 서명한다는 의미가 아님을 유지한다.

위 항목은 로컬 검토 의견이며 Google 원문에는 반영하지 않았다. 본문에 참조된 최신 별지와 draw.io 원본의 내용 일치까지 확인한 것은 아니다.

이는 관리 시스템 구현의 기술 확인 항목이다. 이용기관의 최종 판정 알고리즘 개발이나 별지 시나리오 확정을 포함하지 않는다. 외부 검증기에는 정상본·오류본의 XML·해시·입력값을 인계한다.

- 개정 원문 전체를 로컬 Markdown·구조 JSON·HTML과 그림으로 보관했다.
