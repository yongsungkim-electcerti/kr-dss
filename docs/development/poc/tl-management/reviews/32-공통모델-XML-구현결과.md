# 32. 공통 TL 모델·XML 변환 구현 결과

작성일: 2026-10-09. 작업 브랜치: `feat/codex-tl-model-xml`.

## 구현 범위

| 대상 | 구현 내용 |
|---|---|
| KrTrustList | formatVersion과 BigInteger sequenceNumber 분리, 이력 보존 기간, 내부 providerId/serviceId, current/history |
| 디지털 ID | 현재 다중 인증서·SKI·Subject, 과거 SKI·Subject. 과거 모델에는 인증서 필드를 두지 않음 |
| 불변성 | 목록 방어 복사, 바이너리 값의 입력·출력 배열 복사와 내용 기반 동등성 |
| PocTrustListProfile | PoC 전용 상태·유형 URI, 분야와 CA 전용 레벨의 critical 확장 생성 |
| TrustServiceTimeline | 최신순 이력 검사, 시작 포함·다음 시작 제외 시점 조회, 중복·역순 이력 오류 반환 |
| TrustServiceChanges | 동일 공개키·Subject 인증서 추가·중복 제거, 새 키·Subject의 별도 서비스 요구, 정보 변경 시 과거 이름·확장·SKI 보존 |
| KrTrustListXml | 형식/순번 개별 왕복, 다국어 서비스명·다중 디지털 ID·ServiceHistory·확장 XML 보존 |
| 파싱 오류 | 미지원 상태 URI 보존, 잘못된 숫자·시각·namespace·중복 단일 필드·이력 인증서·DTD 거부 |
| 오류 시험 데이터 | 표현 가능한 순번·발행/만료 시각의 의미 모순을 임의 수정하거나 일괄 거부하지 않음 |

XML 구조 검토에는 [ETSI TS 119 612 V2.4.1](https://www.etsi.org/deliver/etsi_ts/119600_119699/119612/02.04.01_60/ts_119612v020401p.pdf)과 기존 상세 모델 26을 참조했다. 현재 변환기는 모델이 지원하는 필드만 다루며 전체 스키마 검증기나 서명 검증기가 아니다.

## 호환 처리

- 기존 Java 생성자·조회 메서드를 유지했다. 구형 SchemeInformation 생성자의 첫 인수는 발행 순번으로 명시하고 형식 버전은 6으로 분리했다.
- 구형 JSON의 version은 LegacyKrTrustListJson에서 순번으로 변환한다. 신·구 형식 필드 혼합은 거부하며, 숫자 크기로 형식 버전 여부를 추정하지 않는다.
- 엄격한 fromXml과 구형 시연 자료용 fromLegacyXml을 구별했다. 호환 경로는 누락된 이력 보존 기간만 기본값으로 처리하고 순번·형식 버전은 각각 읽는다.
- 기존 이용기관의 업로드 경로는 명시적 호환 파서를 사용한다. 검증 리포트 version은 큰 순번이 잘리지 않도록 십진 문자열로 변경했다. 해당 JSON 필드는 이전 정수에서 문자열로 바뀌므로 외부 클라이언트는 이 표현을 따라야 한다.
- 기존 JWS 경로의 서명·읽기 회귀 테스트를 유지했다. 관리 WAS의 실제 XML 서명 기능을 구현한 것은 아니다.
- GRANTED는 기존 시연 호환 상태로 남겼다. 새 PoC ACCREDITED URI를 기존 소비자가 자동 GRANTED로 취급하게 하지 않았다.

## 검증 결과

`gradlew.bat build` 통과: 167개 작업, 39개 실행·128개 최신 상태. 저장된 JUnit 결과는 29개 suite, 126개 test, 실패·오류 0건이다. 이번에 추가한 테스트는 22건이다. 일부 기존 작업은 Gradle의 최신 상태 결과를 재사용했다.

추가 테스트는 큰 순번/형식 버전, 현재/이력 ID, 상태 경계·복원 후 정지 이력, 방어 복사, 미지원 URI·중첩 critical 확장·상위 namespace 보존, 잘못된 XML 입력, 구형 JSON/XML, 인증서 갱신/키 교체/Subject 변경, 상태 변경 때 기존 인증서 유지, JWS 왕복, 보고 순번 문자열을 확인한다.

Javadoc의 주석 누락 및 구형 호환 API 사용 경고는 남아 있다. 빌드 성공을 규격 완전 준수나 관리 PoC 완료로 표현하지 않는다.

## 남은 작업과 한계

다음 단계는 사업자·서비스 관리 API와 초안 저장이다. 입력 정합성 검사, 임시 프로파일의 필드별 진단, 발행 후보 생성과 저장 트랜잭션을 연결해야 한다.

- 목록 운영 정보·주소·정책·URI 등 전체 ETSI 필드와 XSD 적합성은 아직 완료되지 않았다. XML을 파싱 후 재생성하면 모델 밖 필드는 보존을 보장하지 않는다. 원본 서명 바이트는 반드시 별도로 유지한다.
- 확장은 XML payload와 critical 여부를 보존한다. 미지원 critical 확장의 수용 여부와 최종 TL 신뢰 판정은 외부 검증기 책임이며 구현 완료로 간주하지 않는다.
- 시점 조회의 FOUND는 구간을 찾았다는 뜻이다. 해당 상태가 인정인지, 서명·체인·정책이 유효한지는 별도 판단한다.
- 정상 변경 연산에 필요한 과거 SKI는 현재 디지털 ID에 명시적으로 제공해야 한다. 인증서 입력에서 SKI 추출·검증하는 관리 입력 경로는 후속 작업이다.
- 의미 오류 후보는 직접 불변 레코드로 구성할 수 있다. 정상 변경 연산은 새 효력 시각의 소급을 거부한다.
- 내부 ID는 XML에 임의 추가하지 않는다. XML import 이후 기존 서비스와의 연결은 관리 저장소에서 수행해야 한다.
- 파일 키 생성, 새 TL 인증 체인, 영속 저장, XML 실제 서명·배포 선택·IF-07 제공·관리 화면 연결은 아직 구현하지 않았다.

이전 상세 설계 보완 문서와 이번 코드 변경은 인계 브랜치 `feat/codex-tl-model-xml`에 함께 커밋한다. [Claude 인계](../handoff.md)에 후속 작업을 정리했다. 원격 원문·main의 로컬 백업은 변경하지 않았다.
