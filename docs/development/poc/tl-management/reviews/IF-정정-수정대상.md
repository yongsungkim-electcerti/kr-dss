## 핵심 수정 사항

TL 관리(IF-02)는 관리 콘솔과 신뢰정보 관리 서버 사이의 연계다. 기존 부록의 ‘관리자 → 관리 콘솔’은 관리자의 조작을 설명한 것으로, 새 구성도의 연결 구간과 다르다.

TL 배포(IF-06)는 배포 WAS에서 배포 WEB으로 이어지는 구간이다. 기존 본문은 발행 서버에서 배포 WAS로 전달하는 구간에 이 번호를 붙였다. 발행본 전달과 외부 제공을 나누어 설명해야 한다. 수정 구성도에도 발행 서버에서 WAS로 향하는 연결은 있지만 IF 번호는 없다.

서명 검증(IF-08)은 두 경로를 포함한다. 이용자 서비스가 서명한 내용을 사용자가 브라우저에서 검증하고, 사용자가 서명한 내용은 이용자 서비스가 검증한다. 기존 IF-08과 IF-09를 단순히 하나의 번호로 바꾸면 이 역할 차이가 드러나지 않는다. 현재 인터페이스 목록은 IF-01~08로 정리하고, 이전 IF-09는 현재 명세에서 제외한다.

## 문장 보완안

아래 문장은 실제 반영 전 검토용이다. 구글독스나 통합 설계서 본문에 적용하지 않았다.

### 시스템 구성도

사용자는 서명 앱으로 작성한 내용을 이용자 서비스에 전달하고, 이용자 서비스는 KR-DSS SDK로 그 서명을 검증한다. 반대로 이용자 서비스가 서명한 내용을 사용자에게 제공하면, 사용자는 브라우저의 문서검증 모듈로 서명을 검증한다. 두 경로를 서명 검증(IF-08)으로 정의한다. 각 검증 환경은 TL 조회(IF-07)로 받은 신뢰목록을 확인한 뒤 서명자의 신뢰 여부를 판단한다.

이 문서에서 사용자는 그림의 가입자 측 사람을, 이용자 서비스는 그림의 이용자 시스템을 가리킨다. 기존 문서의 이용기관은 해당 서비스를 운영하는 기관을 뜻하며, 시스템 동작을 설명할 때는 이용자 서비스 또는 이용자 시스템으로 구체화한다.

### TL 배포

TL 발행 서버는 서명된 발행본을 배포 WAS에 전달한다. 배포 WAS는 전달받은 TL을 확인하고, TL 배포(IF-06)를 통해 배포 WEB에서 제공할 수 있도록 한다. 브라우저의 문서검증 모듈과 이용자 시스템은 TL 조회(IF-07)로 배포 WEB에서 TL을 받는다. 발행본 전달, 외부 제공, 이용환경의 TL 채택은 서로 다른 단계다.

이 설명은 연결의 역할을 나타낸다. WEB과 WAS 사이의 전송·중계 방식, 게시 완료 확인 방식과 재시도 절차는 기존 상세 설계와 대조해 정한다.

### 신뢰 검증

TL 서명(IF-05)은 신뢰목록을 발행할 때 수행하는 서명이다. 각 이용환경은 받은 TL의 서명을 사전에 보유한 신뢰앵커까지 확인한다. 서명 검증(IF-08)은 이렇게 확인한 TL을 사용해 사용자 또는 이용자 서비스가 서명한 내용을 검증하는 기능이다. TL 자체의 출처·무결성을 확인하는 과정과 개별 문서의 서명을 검증하는 과정을 구분한다.

## 유지할 내용과 확인할 사항

TL 서명 체인과 업무 서명자의 인증서 발급 체인은 계속 구분한다. 두 인증체계가 상호 인증으로 연결되는 구조를 새로 만들지 않는다. 서비스 상태와 인증서 폐지의 구분, 상태 구간의 시작 시각 포함, 복원 후 과거 이력 보존, TL 유효기한·버전 검사와 기존 판정표도 유지한다. 최신 구성도에 TSA가 표시되지 않았다는 이유로 기존 서비스 데이터에서 TSA를 삭제하지 않는다.

상세 내용을 바꾸기 전에 확인할 사항은 다음과 같다.

- **배포 처리:** WAS와 WEB의 논리적 망 배치, 제공 방식, 게시 완료 판단 기준. 데이터 흐름 방향과 네트워크 연결 시작 방향은 별개다.
- **서비스 서명 사례:** 서비스가 사용하는 서명 인증서와 시험 문서·증거. TL 서명 인증서를 업무 문서 서명용으로 재사용한다고 가정하지 않는다.
- **PoC 범위:** 두 경로를 개념으로 설명하는 것과 실제 브라우저에서 전체 서명 검증을 구현하는 것은 구분한다. 기존 TL 요인 판정의 구현 범위를 이번 정정만으로 확대하지 않는다.

후속 편집은 부록의 IF 표와 1장 역할 설명, 5~6장 발행·배포, 7~9장 검증·시나리오 순으로 진행하면 연결 관계를 일관되게 정리할 수 있다. 마지막으로 그림 참조와 원천 문서의 이전 IF 안내를 확인한다.
