# 05. 관리 시스템 설계 검토

> 자료 분류: 기존 상세 설계·검토 자료. 현재 PoC 구현 범위는 [확정 범위](../../../../design/poc/tl-management/scope.md)를 우선한다. 고정 시나리오·HSM·별도 WEB 등은 현재 필수 개발로 간주하지 않는다.

> 01~04를 기준으로 **현재 코드가 시나리오를 돌릴 수 있는지** 점검하고, PoC에서 먼저 메울 부분을 정리한다.
> 점검일: 2026-10-04 · 기준 브랜치: `feat/claude-krtl-admin-design`

## 1. 검토 요약

| 영역 | 현재 | 시나리오에 필요한 것 | 판단 |
|---|---|---|---|
| KR-TL 모델 (`kr-tl-model`) | 서비스마다 **현재 상태 1개 + 시작 시각**, 서비스 인증서 **1개** | 상태 **이력**(SC-03·04·05), 인증서 **복수**(SC-02) | ❗ 모델 확장 필요 — 가장 먼저 |
| TL 생성·서명 (`kr-tl-builder`) | JWS 서명 동작, TS 119 612 XML 직렬화 있음 (XML 서명은 없음) | 이력·복수 인증서 직렬화 | 모델 확장에 맞춰 수정. TL 형식은 **XML + XAdES 단일** (JWS 출력 제거, 15 · 22 W-03) |
| 이용자 SDK 판단 (`kr-dss-trust` `TrustServiceRegistry`) | **현재 상태만** 보고 판단 | **서명 시각 기준** 상태 판단, 사용 TL 버전 기록 | ❗ 핵심 증명 지점. 수정 필요 |
| TL 수신 (`kr-tl-client`) | 인터페이스만 (`getTrustList`/`refreshTrustList`) | 버전 확인, TL 서명 검증, 일련번호 역행 거부, 기한 경과 판단 | 구현 필요 |
| 관리 시스템 (`poc-kisa-tl`) | 대시보드·발행 API 2개, 데이터 하드코딩 | M-01~09, F-01~08 | 재구성 (화면 틀은 재사용) |
| 배포 시스템 | 없음 | 배포·버전 확인·접속 기록·패키지 게시 | 신규 `poc-krtl-dist` |
| 인증사업자 (`poc-tsp-sim`) | CA·RA·OCSP | 신뢰정보 제출(IF-01) | 기능 추가 |
| 서명 시각 | PoC는 서명에 기록된 서명 시각(KST)을 기준으로 한다. **TSA는 쓰지 않는다** (18 §1) | SC-03·05의 시점 증명 | 서명 시각을 지정한 표본 생성 (22 W-01). TSA · 타임스탬프 부착 없음 |

## 2. 주요 검토 의견

### R-1. 시점 판단이 PoC의 중심이다
정지·철회 시나리오에서 "언제 서명했는가"에 따라 판정이 갈리는 것을 보여 주는 것이 TL 관리의 핵심 가치다. 이를 위해 세 곳이 함께 바뀌어야 한다.
- 관리 시스템: 상태 변경에 효력 시각 저장 (F-01)
- KR-TL 모델·builder: 상태 이력을 TL에 싣기
- 이용자 SDK: 서명 시각(서명에 기록된 KST)으로 이력 조회

셋 중 하나라도 빠지면 SC-03~05가 성립하지 않는다.

### R-2. 이용자 쪽 검증이 관리 시스템만큼 중요하다
관리를 아무리 잘해도 이용자가 (1) TL 서명을 검증하지 않거나 (2) 예전 TL로 되돌려도 받아들이거나 (3) 기한 지난 TL을 계속 쓰면 체계가 무너진다. SC-07·08이 이를 보여 준다. `kr-tl-client` 구현을 관리 시스템과 같은 우선순위로 둔다.

### R-3. 반영 확인은 배포 시스템에서 본다
TL 발행으로 끝나지 않고 이용자·브라우저가 실제로 받았는지 봐야 긴급 정지(SC-03)가 의미를 가진다. 시연에서는 별도 통계 서버 없이 **배포 WAS의 수신 현황(M-07)** 으로 확인한다.

### R-4. 개념으로 남겨 두는 정책 (향후 결정)
아래 두 가지는 지금 수치나 기준을 정하지 않는다. 설계에는 **개념과, 정책을 바꿔 끼울 수 있는 자리**만 둔다.

| 개념 | 내용 | 설계에 반영한 것 |
|---|---|---|
| 효력 시각 소급 | 상태 변경의 효력 시각을 과거로 잡으면 이미 통과한 서명의 판정이 바뀐다 | 효력 시각·사유 기록, 소급 여부 표시 (M-03) |
| 서명 시각 없는 서명 | PoC는 판단 보류(`NO_SIGNING_TIME`)로 정했다 | 18 §1 |

발행 주기·반영 시간은 EU 기준 규칙에 PoC 값(7일·1시간)을 임의 설정했다 ([10](../../../../design/common/kr-tl/10-TL-구조.md) §7.2). 효력 시각 소급은 금지로 확정했다.

## 3. PoC 작업 순서 (제안)

| 단계 | 작업 | 열리는 시나리오 |
|---|---|---|
| 1 | KR-TL 모델 확장(상태 이력 · 같은 키의 인증서 여러 장) + builder 반영 (XML + XAdES) | — |
| 2 | 이용자 SDK: 시점 기준 판단, 사용 TL 버전 기록 / `kr-tl-client`: 수신·서명 검증·역행 거부 | SC-01 (수동 배포로) |
| 3 | `poc-kisa-tl` 재구성: 신뢰정보 입력 · 확정, 상태 변경(소급 금지), TL 발행, 결과 비교 화면 (로그인 · 승인 분리 · 감사 없음) | SC-01, 03~05 |
| 4 | `poc-krtl-dist` 신규 + TL 반출(IF-06) | SC-06, SC-08 |
| 5 | 배포 시스템 수신 현황(M-07), tsp-sim 제출 기능 | SC-06, SC-12 |
| (병행) | 서명 시각이 다른 서명 표본 생성 (18 §4) | SC-01, 03~05 |
| 6 | 나머지 시나리오 (SC-02, 07, 09, 10) | 2차 · SC-11은 핵심 제외 |
