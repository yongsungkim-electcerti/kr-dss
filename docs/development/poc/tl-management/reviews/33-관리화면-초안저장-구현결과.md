# 33. 관리 화면·초안 저장 구현 결과

작성일: 2026-10-09. 브랜치 `feat/claude-tl-admin`. 사용자 지시에 따라 REST 계약 문서와 외부 사업자·서비스 관리 인터페이스는 만들지 않았다. 관리자가 PoC 관리 화면에서 사업자를 직접 등록하고 서비스 인증서를 입력한다.

## 구현 범위

| 구분 | 내용 | 소스 |
|---|---|---|
| 초안 모델 | 목록 운영자, 사업자(providerId), 서비스(serviceId·유형·분야·레벨·상태·시작 시각·사유), 인증서 원문과 추출값 | `registry/RegistryDraft` |
| 인증서 해석 | PEM 묶음·DER, Subject·발급자·일련번호·유효기간·공개키 해시·SKI(확장값, 없으면 공개키 SHA-1 계산) 추출, 유형별 사전 경고 | `registry/CertificateInspector` |
| 편집 규칙 | 같은 Subject·공개키만 한 서비스로 묶음, 다른 서비스와 공개키 중복 금지, 같은 키 갱신은 서비스 ID·상태 시작 유지, 새 키는 새 서비스, CA만 레벨 지정, 정상 상태 전이와 소급 금지 | `registry/RegistryService` |
| 저장 | 불변 `registry/revisions/r-NNNNNNNN.json`, `publication/state.json`의 활성 revision·파일 해시, 임시 파일 기록·동기화 후 원자 교체, 기대 revision 충돌 검사, 프로세스 잠금 | `registry/RegistryStore` |
| 복원 | 기동 시 state·해시·revision 일치 확인. 불일치·state 누락이면 최대 revision 자동 선택 없이 쓰기 중단 | `RegistryStore.recover` |
| 화면 | 운영 현황(저장 상태 집계·인증서 기한 알림), 사업자·서비스 등록·수정·삭제, 인증서 미리 해석·추가·내려받기, 상태 변경, 초안 XML 미리보기, 저장 이력, 목록 운영자 설정. 발행은 ‘개발 예정’, 접수·심사는 ‘범위 제외’ 메뉴만 둔다 | `static/index.html` |
| 화면 전용 엔드포인트 | `/api/admin/*`. 외부 계약이 아니며 IF-07과 분리 | `web/RegistryAdminController` |

기존 `KrTlAdminController`의 고정 숫자·“배포 완료” 응답은 삭제했다. 화면의 숫자는 저장된 초안에서만 계산한다.

## 설계상 결정

- 정상 기준(BASELINE) 발행 전에는 편집이 서비스의 현재 정보만 바꾼다. 서비스 이력(ServiceHistory)은 발행 단계에서 기준 발행본 대비 최종 변경만 반영한다([발행·복구 계약](../../../../design/poc/tl-management/issuance-recovery.md)). 따라서 초안 모델에 이력 필드를 아직 두지 않았다.
- 삭제와 상태 시작 시각 정정은 `baselineIssuanceId`가 없을 때만 허용한다. 기준 발행 후에는 철회로 처리한다.
- 변경 사유는 관리 메타데이터이며 XML에 싣지 않는다.
- 인증서 경고(만료, CA 아님, OCSP/TSA 확장키용도 없음, RootCA 비자체발급, SKI 계산)는 저장을 막지 않는다. 체인·인정 검증이 아니다.
- 내용이 바뀌지 않은 저장은 새 revision을 만들지 않는다.
- 저장 루트는 `krtl.admin.storage-root`(기본 `runtime/tl-management`, Git 비관리). `bootRun`은 저장소 루트에서 실행한다.

## 검증

- `gradlew.bat build` 통과. poc-kisa-tl 신규 JUnit 19건(저장소 8, 편집 11) 실패 0.
  - 재기동 복원, 오래된 revision 거부, state 교체 직전 중단 시 기존 초안 유지와 잔여 revision 구별, 두 번째 프로세스 기동 실패, 활성 revision 변조 시 쓰기 중단, state 없는 revision 미선택, 무변경 저장
  - PEM/DER 입력, SKI 계산, 같은 키 갱신, 새 키 거부·별도 서비스 등록, 공개키 재사용 거부, 혼합 키 거부, 레벨 규칙, 상태 전이·소급 거부, 초안 XML 왕복
- 임시 저장 루트로 기동해 API 흐름(등록·갱신·충돌·상태 변경·기한 알림·XML)과 화면 렌더링을 확인했다.

## 한계와 다음 단계

- 단일 WAS 안의 직렬화와 프로세스 중단 복구까지만 다룬다. 전원 상실 내구성은 주장하지 않는다.
- 초안 XML은 서명 전 미리보기다. 순번·시각은 임시값이다.
- 다음 순서: XML 생성·키 파일 서명 → 불변 발행본(issuanceId) 보관 → 제공본 선택 → IF-07 → 관리 화면의 발행·제공 연결. 발행 시 BASELINE 기준 이력 반영과 TRIAL 분리를 구현한다.
